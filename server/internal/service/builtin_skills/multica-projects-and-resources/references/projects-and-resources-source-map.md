# Projects and resources source map

- `server/cmd/multica/cmd_project.go` registers project `list`, `get`, `create`, `update`, `delete`, and `status`.
- The same file registers `project resource list/add/update/remove`.
- `project create --repo` attaches `github_repo` resources during project creation.
- `project create` / `project update` accept `--start-date` / `--due-date` (calendar days, `YYYY-MM-DD`), mapping to the project `start_date` / `due_date` columns (migration `166_project_dates`); an empty `--start-date ""`/`--due-date ""` on update clears the date, mirroring the issue date flags in `cmd_issue.go`.
- `project resource add` supports shortcuts for `github_repo` (`--url`, non-JSON `--ref` for checkout ref, `--default-branch-hint`) and `local_directory` (`--local-path`, `--daemon-id`, `--ref-label`, `--execution-mode`), or generic JSON `--ref '<json>'`.
- `local_directory.execution_mode` is validated in `server/internal/handler/project_resource.go` (`validateLocalDirectoryRef`); the daemon reads it in `server/internal/daemon/local_directory.go` (`localDirectoryAssignment.UsesWorktree`) and builds the per-task worktree in `server/internal/daemon/execenv/local_worktree.go`.
- The branch a worktree task delivers on is chosen by `resolveTaskBranch` in `server/internal/daemon/execenv/local_worktree.go`: one branch per conversation (issue, else chat session — `localWorktreeConversation`), task-scoped only when there is no conversation or when a sibling task already holds the conversation's branch. Continuing one requires proving ownership (`branchOwnedBy`): the branch record must carry this workspace/agent/conversation AND its checkpoint (the record commit's second parent) must still be an ancestor of the branch tip, so a same-named branch that was deleted and recreated or force-moved is refused. An unowned branch pushes the task onto `<branch>-<fingerprint>`. The checkpoint is always a commit the branch could not sit at without this conversation's work: every branch this mode creates gets a baseline commit of its own (`commitBaseline`, empty when the user's tree was clean), and every later turn that replays user edits commits its own baseline too. `Finalize.verifyDeliveryPoint` requires the delivered tip to be its own branch's and to still contain `LocalWorktree.BaseCommit` — the commit THAT turn started from, which is later than any earlier checkpoint once the user has committed on the branch themselves. A turn whose replay conflicted has no baseline until the agent resolves, so it only advances the recorded snapshot when the branch moved past where that turn found it. `Finalize` records the tip it delivered before removing the worktree, and fails the task — keeping the worktree — when the delivery cannot be verified or the record cannot be written.
- The user's directory is captured as one commit including untracked files (`captureUserSnapshot`, built in a private index under the task env root) and recorded at `refs/multica/local-state/<branch>` once the branch carries it. A follow-up turn replays only the difference (`replayUserState`); an unmergeable difference is left in the worktree for the agent, announced by `buildWorktreeReplayConflictBlock` in `server/internal/daemon/prompt.go`, and `Finalize` refuses to commit while any path is still unmerged. Orphaned refs are dropped by `pruneOrphanedStateRefs` on the next prepare in that repo.
- Saving `execution_mode=worktree` is gated on the daemon having advertised the `local-worktree-v1` capability (`protocol.DaemonCapabilityLocalWorktreeV1`), checked by `requireWorktreeCapableDaemon` in `server/internal/handler/project_resource.go` against the daemon's most recently seen runtime row; not capable → HTTP 422 `daemon_version_unsupported`. The authoritative gate is at claim time (`worktreeClaimBlockReason` in `server/internal/handler/daemon.go`), which reads the capability off the claim request itself and cancels the task with a reason. `MinLocalWorktreeCLIVersion` is only the number shown to the user; nothing gates on it.
- `project resource update` merges shortcut edits with existing `resource_ref` so a partial edit does not clobber required fields; non-JSON `--ref` updates `github_repo.resource_ref.ref`.
- `server/cmd/server/router.go` exposes `/api/projects` plus `/api/projects/{projectId}/resources` routes.
- `server/pkg/db/queries/project_resource.sql` is the CRUD query surface for `project_resource` rows.
- Project resources are written into `.multica/project/resources.json` for agent workdirs.
- `github_repo.resource_ref.ref` is lifted into daemon `RepoData.Ref` by `server/internal/handler/daemon.go`; `server/internal/daemon/daemon.go` stores it per task, and `server/internal/daemon/health.go` uses it as the default `/repo/checkout` ref when the checkout request does not explicitly pass one.
- Referring to a project in a comment: `[Label](mention://project/<uuid>)` is a render-only link. `util.MentionRe` (`server/internal/util/mention.go`) does NOT include `project` in its type group, so the backend never parses it and it can enqueue nothing — deliberately weaker than `agent` / `squad`. Presentation differs by client and the skill says so: web and desktop render a chip in `RichLink` (`packages/views/rich-content/rich-content.tsx`) and the editor's `MentionView` (`packages/views/editor/extensions/mention-view.tsx`), while mobile has no chip — `apps/mobile/lib/markdown/markdown.tsx` leaves the default enriched-link styling and only routes the tap (`onLinkPress`). Unfurling a bare in-app project/issue URL is web/desktop only, via `parseWorkspaceEntityLink` (`packages/views/editor/utils/link-handler.ts`), which requires same origin (resolved through `URL`, not a prefix test), no query/fragment, the current workspace slug, and an id that addresses one entity — a UUID, or an issue identifier (`MUL-123`), which is the form `copyLink` produces and which falls back to the plain link when it resolves to nothing (MUL-5499). On mobile a bare URL still goes to `Linking.openURL`. The agent-facing line lives in the runtime brief's Mentions section (`writeMentions`, `server/internal/daemon/execenv/runtime_config_sections.go`).
- A project's `description` is injected as durable context for every task in the project. The claim handler (`server/internal/handler/daemon.go`) reads `proj.Description` onto the claim response (`ProjectDescription`, `server/internal/handler/agent.go`); the daemon carries it through `Task` (`server/internal/daemon/types.go`) and `TaskContextForEnv` (`server/internal/daemon/execenv/execenv.go`) into the brief's `## Project Context` section (`server/internal/daemon/execenv/runtime_config.go`) and into `.multica/project/resources.json` as `project_description` (`server/internal/daemon/execenv/context.go`).

## Shared project memory

- `server/internal/handler/project_memory.go`: GET/PUT `/api/projects/{id}/memory`, owner/admin human publication, 20 rules of 500 characters, optimistic revision check, reviewer metadata, optional `source_review_id` promotion from a project-linked `changes_requested` delivery review, paginated GET `/api/projects/{id}/memory/history`, restoration and expiration at claim time.
- `server/internal/handler/project_memory_usage.go`: GET `/api/projects/{id}/memory/usage` — 30-day prepared-context coverage for non-chat issue runs on the project (`prepared_runs` per revision); not proof of model use.
- `server/internal/handler/project_resource.go`: `resolveClaimProjectContext` includes reviewed rules in the claim-only project description, with project/workspace isolation.
- `server/pkg/db/queries/project_memory.sql`, `project_memory_usage.sql`, and `server/migrations/472_project_memory.up.sql`: atomic conditional publication on the project row; deletion of the project also removes its rules.
- `server/migrations/499_project_memory_correction_source.up.sql` and `500_project_memory_correction_identity.up.sql`: `memory_source_review` / version `source_review` JSONB plus unique (project, review_id) identity.
- `server/internal/handler/project_memory_test.go` / `project_memory_usage_test.go`: publication, stale revision rejection, role and machine-credential gates, scoped injection and clearing, correction promotion/idempotency/foreign-project refusal, usage coverage/privacy.
- No project-memory CLI command exists. Agents propose changes; humans publish them in the project UI or via **Promote to project memory** on a delivery correction.

- `server/migrations/478_project_memory_versions.up.sql` and `479_project_memory_version_identity.up.sql`: preserve existing current versions, expiration and immutable version identity; no FK/cascade.
- `server/internal/handler/project.go` and `server/pkg/db/queries/workspace.sql`: explicit history cleanup in project/workspace deletion.
