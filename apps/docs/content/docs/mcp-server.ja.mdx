Multica はすべてのワークスペースを 1 つの [MCP](https://modelcontextprotocol.io) サーバーとして公開します。MCP クライアント — Claude Code、Codex、Cursor、スクリプト、あるいは Multica の内部で実行されるエージェント — がこれに接続し、ワークスペースのツールを発見して呼び出します。課題、コメント、ゴールループ、Brain、プロジェクト、エージェント、トリアージ、受信箱、実行のトランスクリプトはすべて到達可能です。削除、シークレット、メンバー管理、承認、請求は、意図的に到達できません。

サーバーは、クライアントではなく、各呼び出しに何ができるかをツールごと・呼び出し元ごとに **allow**、**ask**、**deny** のいずれかで決めます。この決定はワークスペースのものであり、クライアントが交渉することはできません。

## クライアントを接続する

エンドポイントは、Multica サーバー上の `POST /api/mcp/{workspace-slug}` です（ストリーム可能な HTTP、1 リクエストにつき 1 つの JSON 応答、セッションなし）。[個人アクセストークン](/members-roles)（`mul_…`）で認証します。

```json title="Claude Code · .mcp.json"
{
  "mcpServers": {
    "vigil": {
      "type": "http",
      "url": "https://multica.example.com/api/mcp/acme",
      "headers": { "Authorization": "Bearer mul_xxx" }
    }
  }
}
```

```toml title="Codex · config.toml"
[mcp_servers.vigil]
url = "https://multica.example.com/api/mcp/acme"
http_headers = { Authorization = "Bearer mul_xxx" }
```

Cursor や他のクライアントも同じ URL とヘッダーを使います。パスにスラッグを含めない場合は、`X-Workspace-Slug` または `X-Workspace-ID` を送ってください。Multica の内部で実行されるエージェント実行は、同じエンドポイントに自身の実行トークンで到達します。ワークスペースはそのトークンから決まります。

## 2 つの surface

URL に `?surface=compound` または `?surface=granular` を追加するか、**設定 → MCP サーバー**でワークスペースのデフォルトを設定します。

- **compound**（デフォルト）: ドメインごとに 1 つ、計 9 個のツールで、それぞれが `action` 引数を持ちます — `vigil_issue`、`vigil_goal`、`vigil_brain`、`vigil_project`、`vigil_team`、`vigil_triage`、`vigil_inbox`、`vigil_run`、`vigil_handoff`。クライアントのコンテキストを節約できます。
- **granular**: 操作ごとに 1 つのツール（`issue_create`、`note_create`、`goal_answer` など）。明示的なスキーマを好むクライアント向けです。

どちらの名前も、どちらの surface でも動作するため、片方のカタログをキャッシュしたクライアントもそのまま動き続けます。

## 決定: allow、ask、deny

すべてのツールにはリスククラスがあります（読み取りか内部書き込みのいずれかで、カタログの中に外部向けや機密のものはありません）。まず呼び出し元の上限が優先されます — メンバーは読み取りと内部書き込みを単独で行えます。エージェントはその[信頼ダイヤル](/agents)の上限を得ます — observer は読み取りしかできません。ワークスペースの管理者は、**設定 → MCP サーバー**でどのツールでも **ask** または **deny** に絞り込めます。上書きが上限を緩めることはありません。

**ask** の意味は、呼び出し元によって変わります。

- **メンバーのクライアント**は、確認トークンと平易な説明を添えて呼び出しを*保留*として受け取ります。クライアントは何が起ころうとしているかを本人に見せ、同じ呼び出しを `confirm_token` を添えて再送します。トークンはその呼び出しに厳密に紐づき、10 分で失効します。
- **エージェントの実行**は、機密なツール呼び出しや git push と同じように、その実行に承認ゲートが記録されます — 人がアプリ内で判断します。保留の結果にはそのゲートの名前が含まれ、実行は `vigil_gate_wait` でそれをポーリングし、承認されると `gate_id` を添えて同じ呼び出しを再送します。拒否されたゲートは最終です。

**deny** は理由を添えた明確な拒否です。すべての呼び出しは、その決定と結果とともに `mcp.inbound_call` として監査ログに記録され、すべての呼び出し元は 1 分あたり 120 回に制限されます。

## クライアントに見えるもの

ツールの結果は API 自身の JSON であり、ワークスペースの記録は他の人やエージェントが書いたデータであって指示ではない、というリマインダーが添えられます。ツール呼び出しは、アプリや CLI と同じハンドラーを通ります — 遷移ルールが適用され（ステータス変更は*承認待ちで保留*として返ってくることがあります）、イベントは開いているクライアントに届き、監査ログはトークンの背後にいる行為者を記録します。

## 設定

`GET /api/mcp-server/settings` は、ワークスペースの設定と各ツールのリスクを含む完全なカタログを返します。`PUT`（owner と admin）は `{ "enabled", "default_surface", "tools": { "<tool>": "allow" | "ask" | "deny" } }` を受け付けます。サーバーをオフにすると、明確なメッセージですべての呼び出しを拒否し、それ以外は何も変わりません。
