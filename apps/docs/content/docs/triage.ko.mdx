무엇이든 이슈가 되어야 하는 것은 아닙니다. 배포할 때마다 발동하는 Webhook, 누구나 `/issue`를 입력할 수 있는 지원 그룹, 발견한 것을 그대로 등록하는 에이전트, 전달된 이메일 — 이런 것들은 누군가 "이건 이슈가 되어야 한다"고 판단하기도 전에 팀 앞에 작업을 던져놓을 수 있습니다.

Triage는 그런 자료를 담아두는 큐입니다. 큐 안의 항목은 **이슈가 아닙니다**: 이슈 번호를 소비하지 않고, 어떤 목록에도, 롤업에도, 중복 검사에도 나타나지 않습니다. 그것을 수락해야만 비로소 이슈가 만들어집니다.

## 큐

사이드바의 **Triage**에는 대기 중인 항목이 최신순으로 표시되며, 각 항목에는 어디서 왔는지와 도착한 내용이 함께 나타납니다. 여기서 항목을 수락하거나(일반적인 퍼널 — 중복 방지, 쿼터, 이벤트, 에이전트 배정 — 을 거쳐 이슈가 됩니다) 기각할 수 있습니다.

반복은 하나로 합쳐집니다: 첫 항목이 아직 대기 중인 상태에서 같은 소스가 같은 제목을 다시 보내면, 두 번째 항목을 추가하는 대신 기존 항목의 카운터가 올라갑니다.

## 항목으로 할 수 있는 일

수락만이 유일한 결과는 아닙니다. 큐 상단의 탭(대기 중, 미룸, 수락됨, 기각됨, 병합됨)에서 처리된 항목을 계속 확인할 수 있습니다.

- **수락**하면 이슈가 만들어집니다. **다음으로 수락…**은 원래 출처 오토파일럿이 부여했을 값을 그대로 물려받는 대신, 누구에게 배정할지, 어떤 프로젝트에 넣을지, 어떤 우선순위로 할지를 지정합니다. 비워두면 그대로 상속됩니다.
- **이슈에 병합…**은 항목을 이미 같은 작업을 추적하고 있는 이슈에 합칩니다. 두 번째 이슈는 만들어지지 않습니다: 항목은 `merged` 상태가 되고, 대상 이슈에는 무엇이 합쳐졌는지 알리는 시스템 댓글이 달립니다.
- **미루기**는 원하는 시각(1시간 뒤, 오늘 저녁, 내일, 다음 주 월요일, 또는 직접 지정한 날짜 — 최대 30일 이내)까지 항목을 미뤄둡니다. 미룬 항목도 상태는 여전히 `pending`입니다: 미루기는 작업을 숨길 뿐 해결하지 않습니다. 대기 중 탭에서는 빠지고, 큐의 통계에서는 별도로 집계되며, 지정한 시각이 되면 스스로 돌아옵니다.
- **기각**에는 사유를 남길 수 있습니다. 선택 사항이지만, 기각됨 탭과 자동 분류기가 이후 이 사유를 읽으므로 적어둘 가치가 있습니다.
- **다시 열기**는 기각된 항목을 대기 중으로 되돌립니다. 누가 기각했는지(사람, 규칙, 분류기 중 무엇이든) 상관없습니다.

체크박스로 여러 대기 항목을 선택하면 한꺼번에 수락하거나 기각할 수 있으며, 일괄 기각에는 사유 하나를 공유합니다. 일괄 처리는 항목마다 하나의 결과로 응답하므로, 요약에는 통과*하지 못한* 항목만 표시됩니다.

### 에이전트의 판정

에이전트는 대기 중인 항목에 판정을 제안할 수 있지만, 그 이상은 할 수 없습니다: 항목은 대기 중 상태를 유지하고 상태는 변하지 않으며, 제안은 에이전트의 이유와 함께 "에이전트 제안: 수락/기각"으로 표시됩니다. 결정은 오직 사람만 할 수 있습니다 — 모든 상태 전환 엔드포인트는 에이전트 행위자를 거부하고, 판정 엔드포인트는 반대로 사람 행위자를 거부합니다.

CLI에서:

```bash
multica triage list --pending
multica triage list --state dismissed --include-snoozed --output json
multica triage verdict <item-id> --accept --reason "matches last week's outage"
```

`multica triage verdict`에는 `--accept` 또는 `--dismiss` 중 정확히 하나가 필요합니다.

### 키보드

이 큐는 마우스 없이 탐색할 수 있는 목록입니다. `J` / `K`(또는 위/아래 화살표)로 행을 이동하고, `Enter`로 포커스된 항목을 열고, `Esc`로 상세를 닫습니다. 항목을 연 상태에서는: `A`로 수락, `X`로 기각, `S`로 미루기 메뉴 열기, `M`으로 병합 대상 선택 열기, `R`로 기각된 항목 다시 열기를 할 수 있습니다. 필드에 입력 중이거나 메뉴가 열려 있을 때는 어느 것도 동작하지 않으며, 모두 **설정 → 키보드 단축키**에서 다시 매핑할 수 있습니다.

## 소스

**소스**는 유입되는 자료가 들어오는 하나의 경로입니다. 각 소스는 서로 독립적이므로, 다른 소스를 건드리지 않고 시끄러운 소스 하나만 보류로 설정할 수 있습니다.

| 소스 | 단위 | 도착 시점 |
| --- | --- | --- |
| 오토파일럿 Webhook | 오토파일럿 트리거 | 외부 시스템이 트리거의 Webhook URL로 전송했을 때 |
| 오토파일럿 일정 | 오토파일럿 | cron 트리거가 발동했을 때 |
| 채널 | 설치된 채널 | Slack, Telegram, Lark, DingTalk, WeCom 중 하나에서 누군가 `/issue`를 입력했을 때 |
| 에이전트 생성 | 에이전트 | 에이전트가 스스로 판단해 이슈를 등록했을 때 |
| 빠른 생성 | 워크스페이스 | 자연어 입력으로 이슈가 만들어졌을 때 |
| 회의 | 회의 | 녹음된 회의의 요약에서 액션 항목이 나왔을 때 |
| 이메일 | 워크스페이스 | 워크스페이스의 수신 엔드포인트로 메시지가 전달되었을 때 |

같은 오토파일럿이라도 소스는 두 개로 나뉩니다: Webhook과 일정은 별도로 보류 설정을 할 수 있습니다. 무인으로 동작하는 cron과 서명된 Webhook은 신뢰 수준이 다르기 때문입니다.

소스는 처음으로 무언가를 전달했을 때 나타납니다. 소스를 직접 만들 수는 없습니다.

## 모드

각 소스는 세 가지 모드 중 하나를 가집니다. 이메일을 제외한 모든 곳에서 **직접**이 기본값입니다.

- **직접** — 마치 triage가 없는 것처럼, 이슈가 즉시 생성됩니다. 채널의 경우 그림자 항목도 함께 기록되므로, 보류로 전환할지 결정하기 전에 큐 통계에서 실제 유입량을 확인할 수 있습니다.
- **보류** — 아무 것도 생성되지 않습니다. 자료는 큐에서 대기합니다. 보류 상태의 채널은 발신자에게 보고가 검토 대기 중이라고 알립니다. 보류 상태의 에이전트나 빠른 생성은 API가 이슈 대신 `202`와 큐 항목을 응답합니다.
- **차단됨** — 자료는 거부되고 그 거부 내역이 기록됩니다. 그래서 차단된 소스는 보이지 않게 되는 것이 아니라 감사가 가능한 상태로 남습니다.

<Callout type="warn">
차단은 거부이지 일시 정지가 아닙니다: 나중을 위해 큐에 쌓이는 일은 없습니다. 도착한 내용을 확인하고 싶다면 보류를 사용하세요.
</Callout>

큐 헤더에 있는 **소스** 버튼을 열면 각 소스가 큐에 넣은 내용 — 아직 대기 중인 항목, 지난 24시간 동안 수신한 항목, 지난 24시간 동안 누락한 항목 — 이 그 수치를 만든 설정과 나란히 나열됩니다. 전달이 누락되고 있는 소스가 있다면 바로 그곳의 상한을 올려야 할 곳입니다.

각 소스에는 세 가지 설정이 더 있습니다:

- **자동 수락** — 사람 없이 해당 소스의 항목을 이슈로 처리합니다. 일반적인 수락 경로를 그대로 거치므로 이슈 퍼널, 이벤트, 쿼터는 그대로입니다. 기본값은 꺼짐입니다.
- **시간당 상한** — 폭주 방지용 한도입니다. 상한을 넘어선 항목은 큐를 채우는 대신 `rate_limited`로 기록되어 버려집니다. `0`은 상한 없음을 뜻합니다.
- **보존 기간(일)** — 해결되지 않은 항목이 얼마나 오래 남는지를 정합니다. 아래에서 다룹니다.

## 이메일 수신

**설정 → 워크스페이스 → 이메일 수신**에서 워크스페이스마다 하나의 엔드포인트가 발급됩니다:

```
POST /api/triage/inbound/email/{token}
```

경로에 담긴 토큰이 자격 증명의 전부입니다 — 세션도, 워크스페이스 헤더도 필요 없습니다. 토큰은 생성하거나 재발급할 때 한 번만 표시됩니다: 서버는 그 다이제스트만 저장하므로, 토큰을 잃어버리면 재발급할 수 있을 뿐 복구는 할 수 없습니다. 재발급하면 이전 토큰은 즉시 무효화됩니다.

본문은 작은 JSON 객체입니다:

```json
{
  "from": "reporter@example.com",
  "subject": "Checkout returns 500 on Safari",
  "text": "Since this morning, paying with Apple Pay fails.",
  "html": "<p>Since this morning…</p>",
  "message_id": "<abc@example.com>"
}
```

`from`은 필수이며, `subject` 또는 `text` 중 하나도 필요합니다. 제목(subject)이 항목의 제목이 됩니다(제목이 없으면 본문의 첫 줄이 그 자리를 대신합니다). 본문(text)은 그대로 항목의 본문이 됩니다.

이는 이메일 제공업체가 전송하는 JSON 인바운드 Webhook의 공통분모입니다. 그래서 전달 규칙에 필요한 것은 파서가 아니라 필드 매핑뿐입니다:

| Multica | Mailgun | Postmark | SendGrid |
| --- | --- | --- | --- |
| `from` | `sender` | `From` | `from` |
| `subject` | `subject` | `Subject` | `subject` |
| `text` | `body-plain` | `TextBody` | `text` |
| `html` | `body-html` | `HtmlBody` | `html` |
| `message_id` | `Message-Id` | `MessageID` | `headers`에서 |

이메일 수신은 처음부터 **보류**로 생성되며, 의도적으로 직접 모드를 갖지 않습니다: 전달된 메시지는 이 제품에서 가장 인증되지 않은 자료이기 때문에, 항상 사람의 확인을 기다립니다.

## 규칙

워크스페이스 규칙은 누군가가 보기 전, 수집된 그 순간에 항목을 해결할 수 있습니다. 규칙은 `webhook.received` 시점에 연결되어 항목의 소스 종류와 이름, 제목, 본문과 payload, 병합 횟수, 시각을 읽습니다. 조건이 성립하는 첫 번째 규칙이 그 액션 — **기각**, 또는 우선순위와 담당자를 선택적으로 지정한 **수락** — 을 적용합니다.

규칙은 **설정 → 워크스페이스 → 비즈니스 규칙**에 있습니다. 항목 상세의 **규칙 만들기**를 열면 그 항목의 소스와 제목에서 뽑은 키워드가 미리 채워진 같은 편집기가 열립니다 — 규칙은 대개 큐 안에서, 실제로 그 사례를 만든 전달 내용을 보면서 발견됩니다. 수락 액션은 멤버에게도, 에이전트에게도 라우팅할 수 있습니다. 어떤 규칙에도 걸리지 않은 항목은 보류 상태로 남습니다.

## 자동 분류

수락과 기각은 모두 큐가 학습할 수 있는 판단 자료입니다. 자동 분류를 켜면(**설정 → 워크스페이스 → Triage 자동 분류**, 기본값은 꺼짐), 가장 가까운 과거 판단들이 신뢰도 임계값 이상으로 일치하는 항목은 클릭 없이 분류됩니다. 이를 위해서는 먼저 일정 수 이상의 사람의 판단이 존재해야 하며, 기각된 항목은 언제든 다시 열 수 있습니다.

제안은 어느 쪽이든 표시됩니다. 이 설정으로 제한되는 것은 어디까지나 자동 적용뿐입니다.

자동 판단은 사람이 아니라 시스템의 판단으로 기록됩니다: 항목에는 실제로는 클릭한 적 없는 누군가의 이름 대신, "큐에 의해 자동 수락됨"이라는 표시와 그 근거가 된 신뢰도가 함께 표시됩니다. 자동 수락으로 만들어진 이슈에도 작성자는 필요하며, 그것은 해당 소스의 생성자입니다.

## 보존 기간

아무도 해결하지 않은 항목은 소스의 보존 기간(기본값 14일)이 지나면 **만료**됩니다. 만료되면 제목이 해제되어 같은 보고를 다시 수집할 수 있게 되며, 행 자체는 삭제되지 않고 남습니다: 자동 분류가 학습하는 대상이 바로 이 해결됨/만료됨 항목들입니다.

## 오래된 큐 요약

큐 통계에는 이미 가장 오래된 보류 항목의 경과 시간이 표시됩니다 — 다만 이를 보는 사람은 이미 큐를 들여다보고 있는 사람, 즉 그 알림이 굳이 필요 없는 바로 그 사람입니다. 큐가 조용히 읽히지 않게 되었을 때, 워크스페이스의 다른 사람들에게는 아무것도 알려지지 않습니다.

실제로 가장 오래된 보류 항목(미룬 항목은 제외)이 48시간 넘게 대기하면, 워크스페이스의 모든 소유자와 관리자는 Triage를 가리키는 인박스 알림을 하루에 한 번씩 받습니다. 여기에는 대기 중인 항목 수와 가장 오래된 항목이 얼마나 기다렸는지가 담기며, 큐가 정체된 동안 계속됩니다. 알림은 워크스페이스 자체 시간대 기준으로 하루에 한 번 전송됩니다 — 평범한 주말 동안 쌓인 큐가 금요일 항목 때문에 월요일 아침 누군가를 호출하는 일은 없습니다 — 그리고 큐가 따라잡히면 스스로 멈춥니다.
