An agent is a collaborator in a [Multica workspace](/workspaces). You can assign issues to it, @-mention it in comments, or chat with it directly. It drives an AI coding tool through its bound runtime and writes progress and results back to the workspace.

An agent is not a continuously running process. It is a reusable identity and configuration; it only produces concrete [runs](/tasks) when work arrives.

## Agent configuration

| Setting | What it does |
|---|---|
| **Name, avatar, and description** | Tell the team who the agent is and what it is good at. The description is display-only and never enters the execution prompt. |
| **Instructions** | Define its responsibilities, working style, boundaries, and delivery requirements. Used on every run. |
| **Conversation starters** | Give people up to three agent-specific examples, shown when they open a new chat with the agent. Selecting one fills the composer without sending. |
| **Skills** | Provide reusable methods, reference material, and supporting files. |
| **Runtime, model, and thinking level** | Decide which runtime, AI coding tool, and model it runs on; some tools (such as Codex) also offer a service tier. |
| **Access** | Decides which members can run it. |
| **Execution settings** | Include the concurrency limit, environment variables, CLI arguments, MCP, and external integrations. |

Switching models or editing instructions does not create a new agent, and past issues, comments, and run history are not lost.

## Agents, runtimes, and runs

| Concept | Responsibility |
|---|---|
| **Agent** | Decides who does the work and how |
| **Runtime** | Decides which computer and which AI coding tool executes it |
| **Run** | Records the process and result of one run |

One runtime can host multiple agents, and one agent can complete many runs over time. When the runtime is offline, the agent's identity and history remain, but new runs wait until the runtime comes back.

## Ways an agent participates

- **Own an issue** — set the agent as the assignee; it starts once the run is enqueued.
- **Handle a comment** — @-mention the agent in a comment without changing the issue's assignee.
- **Continue a discussion** — reply to the agent's comment; the new information feeds into subsequent runs.
- **Chat directly** — start a conversation that isn't attached to an issue.
- **Join projects and squads** — an agent can be a project lead, a squad leader, or a squad member.
- **Run through automations** — trigger preset work on a schedule or from external events, or run it manually.

Agents can create issues, post comments, and change work status, but they have no inbox and don't receive `@all`. An @-mention of an agent is an execution trigger, not a notification.

## Permissions and Access

Every agent has one owner and an Access setting:

| Access | Who can run it |
|---|---|
| **Only me** | Only the agent owner. |
| **Entire workspace** | Every member of the workspace. |
| **Specific people** | The agent owner and the selected members. |

New agents default to **Only me**.

<Callout type="info">
Workspace `owner`s and `admin`s can see and manage every agent, but cannot bypass Access to run someone else's "Only me" agent. Regular members only see agents they own or are allowed to run.
</Callout>

**Seeing** an agent is determined by ownership, workspace admin roles, and Access together; **modifying** is open to the agent owner and workspace owners/admins, except Access itself, which only the agent owner can change.

Configuration that may contain credentials, such as environment variables and MCP, has stricter read rules — see [Create and configure an agent](/agents-create#environment-variables-and-credentials).

## Online, offline, and workload status

The agent list shows two kinds of status side by side:

- **Availability** comes from the runtime — online, offline, or unstable.
- **Workload** comes from runs — working, queued, or idle.

"Offline" does not mean the agent was deleted. Already-enqueued runs wait for the runtime to recover; only "archived" means it can no longer take new work.

## Archive and restore

Agents you no longer use can be archived. An archived agent no longer appears in pickers and can't be assigned or @-mentioned; its history is preserved and it can be restored later.

<Callout type="warning">
Archiving cancels all of the agent's unfinished runs, including queued and running ones.
</Callout>

The agent owner and workspace `owner`s and `admin`s can archive or restore an agent.

## Memory and corrections

The **Memory** tab stores short facts for an agent. The latest 50 active, unexpired memories are included in new run briefs. Changes do not rewrite runs already started.

Set an optional expiration in the memory editor using your local time. Expired memories stay visible but are excluded from new runs. Editing their text or approving them preserves the expiration; explicitly change or clear the date to renew them. Changing an expiration does not approve a pending suggestion. Expired entries still count toward the 200-entry limit.

- **Add memory** creates an active fact directly. Each fact is limited to 500 characters.
- Suggestions extracted after completed runs await human review. Private chat runs are excluded from extraction.
- In **Activity**, **Teach a correction** records a proposed rule tied to a finished, failed, or cancelled run. Open **Memory** to inspect its source, edit it, and approve or reject it. Editing a suggestion does not approve it.
- **Stop using** removes a fact from future briefs while preserving it. **Review again** returns it to the review queue. Deletion is permanent.

Use **History** to inspect versions and preview a restoration. Restoring creates a new version with the selected text, review state and expiration, attributed to the person restoring it. An active, unexpired version can be used by new runs; a pending version still needs approval. A concurrent change requires returning to history and reviewing the latest state before trying again. History starts with the state preserved at upgrade; older edits cannot be reconstructed. Deleting a memory permanently deletes its history too.

Only the agent owner and workspace owners/admins can change memory; machine credentials cannot approve it. Reviews record the human and time. If the memory changed since it was displayed, reload before approving.

An agent holds up to 200 memories, including pending and rejected suggestions. Extraction stops at capacity and never evicts reviewed facts. Delete an unwanted entry to make room. Keeping a rejected suggestion also prevents exact normalized duplicates from being extracted again.

When upgrading to memory review, existing suggestions extracted from runs move to the review queue; manual facts remain active. Approval controls what is used next. Manual approval alone does not measure whether the rule improves results.

**Evaluations** opens imported offline comparisons for a memory. Human agent managers can import a JSON report (up to 2 MiB, 10 reports per memory), inspect baseline/candidate results and reserved validation cases, export or remove reports, and adopt an eligible revision after reviewing the evidence. The CLI also supports `multica agent memory evaluate`, `publish`, and `adopt`. Adoption checks the complete active memory context atomically and records the resulting revision; a changed context requires another evaluation. Reports are human-supplied evidence, not server-attested executions or proof of production improvement. Cost and human effort remain unknown. Removing a report does not undo adoption; deleting a referenced memory removes reports containing its text, including baseline copies. Use memory history to restore a previous version. This workflow is available on web and desktop.



In a run’s **Run details**, expand **Memory prepared for this run** to inspect the agent memory IDs and revisions and the project memory revision selected for its latest finalized dispatch. A failed memory read is distinct from a successful read with no eligible memories. Older runs show unrecorded context. Reclaiming before execution replaces this snapshot; it is not a history of every dispatch, an acknowledgement of receipt, or proof that the model followed the rules. Run history retains version references, not a copy of deleted memory text.

**Memory across runs** shows the last 30 days of retained, started runs with an identifiable non-chat origin. Chats remain excluded after deletion; older runs with an unknown origin are also excluded. Counts distinguish memory included, no eligible memory, a failed memory read and unrecorded context. Expand the version list to see how often each revision was prepared and when its last run started. Current text is labelled separately; **History** opens the available versions. Statistics refresh every minute. They do not measure model adherence or improvement, and failed requests show an error rather than zero.
