エージェントが実行を受け取ると、デーモンは AI コーディングツール（Codex、Claude Code など）を子プロセスとして起動します。このプロセスが何に触れられるかを理解することが、セキュリティモデルのすべてです。

## 境界はデーモンを実行しているユーザー

デフォルトでは、実行は**デーモンを実行している OS ユーザーの全権限**で動きます。そのユーザーが読み書きできるファイルはすべて読み書きでき、そのユーザーの認証情報を利用でき、ネットワークにも制限なくアクセスできます。

Multica はファイルシステムのサンドボックスを一切保証しません。現時点で例外は 1 つだけ、Windows で Codex のネイティブサンドボックスを明示的に有効にした場合です。そもそもどのプラットフォームと設定の組み合わせでサンドボックスが効くかはツールのバージョンとともに変わる互換性上の詳細です。すべての実行をサンドボックスなしとみなし、境界はデーモンの外側に用意してください。

<Callout type="warning">
Multica はファイルシステムのサンドボックスを提供しません。デーモンを個人アカウントで動かしている場合、実行は SSH 秘密鍵を読み、シェルの設定を書き換え、ドキュメントを削除できます。分離はデーモンの外側に用意する必要があります。
</Callout>

これは意図的な設計です。エージェントには依存関係のインストール、ビルドの実行、クラウド CLI の利用が求められ、これらのツールは通常のホームディレクトリがあることを前提にしています。中途半端なファイルシステムサンドボックスは、こうした作業を診断しづらい形で壊します（ツールが「ログインしていません」と言う、あるいは黙って別のアカウントを使う）。しかも最も重要な部分は守れません。実行が認証情報を読み取ってネットワーク経由で送信することは止められないからです。

そのため Multica は自らを境界とは称しません。外側に境界を用意してください。

## 推奨構成

インフラに合うものを選んでください。軽いものから順に挙げます:

1. **専用 Unix ユーザー。** `multica` ユーザーを作成し、エージェントに必要なリポジトリと認証情報だけを与えて、そのユーザーでデーモンを実行します。自分のアカウントは影響を受けません。
2. **コンテナ。** 必要なマウントとシークレットだけを与えたコンテナ内でデーモンを実行します。
3. **仮想マシン。** 分離は最も強固ですが、マシンの用意が必要です。

いずれの場合も、その環境から到達できる認証情報は「エージェントが使う可能性のある認証情報」として扱ってください。トークンの権限は最小限にし、個人の SSH 鍵ではなく用途別のデプロイキーを使い、無関係な本番環境の認証情報をそのユーザーのホームに残さないようにします。

## Multica が実際に分離しているもの

以下は実在する分離ですが、利便性と影響範囲の縮小のためのものであり、能動的に脱出を試みる実行に対するセキュリティ境界では**ありません**:

- **実行ごとの作業ディレクトリ。** 各実行は `~/multica_workspaces/` 配下に専用の workdir を持ち、同時に進む実行が同じチェックアウトで衝突しません。
- **実行ごとのエージェント状態。** Codex の各実行には専用の `CODEX_HOME` があり、設定・セッション・スキルを保持するため、`~/.codex/` を汚しません。
- **実行スコープの API トークン。** 実行に渡される `MULTICA_TOKEN` はサーバー側でそのエージェントと実行に紐づけられており、実行が Multica API 上であなたや他のエージェントとして振る舞うことはできません。

## 境界ではないもの

- **コーディングツール自身のサンドボックスと承認設定。** Multica はエージェントを無人で実行するため、承認要求は自動的に応答されます。デフォルトの経路ではファイルシステムのサンドボックスも無効で、Codex は `sandbox_mode = "danger-full-access"`、Claude Code は `--permission-mode bypassPermissions` で動作します。例外は Windows です。Codex のネイティブサンドボックス（`windows.sandbox = "unelevated"` または `"elevated"`）を明示的に設定した場合、Multica はそのオプトインを尊重し、該当実行では `workspace-write` を維持します。使える場面では有効ですが、1 つのプラットフォームの 1 つのツールに限られる話であり、デーモンユーザーの権限をどこまで絞るべきかという判断は変わりません。
- **`HOME` ディレクトリの構成。** 実行はデーモンユーザーの実際の `HOME` と `XDG_*` 変数を引き継ぎます。だからこそ `gh`、`aws`、`kubectl`、`gcloud`、`glab` などのホスト CLI がシェルと同じように実行内で動作します。同時に、そのホーム配下のすべてに到達できるということでもあります。

<Callout>
Linux では以前、Codex 実行は `workspace-write` サンドボックスと実行ごとにリダイレクトした `HOME` の下で実行されていました。この仕組みは削除されました。ホスト CLI が実行内で未設定状態になるうえ、書き込みしか制限しないため、認証情報の読み取りと持ち出しは元から防げていなかったからです。現在 Linux は macOS と Windows のデフォルトと同じ挙動です。
</Callout>

## レビューと操作の承認は別物

Multica は**ワークフローの合図**、**デリバリーの評価**、**操作の承認**を区別します。これらを混同すると、実在しない鍵をあると思い込むことになります。

| 合図 | 意味すること | 意味し**ない**こと |
| --- | --- | --- |
| ボードのステータス `in_review`（同じカテゴリのカスタムステータスを含む） | 結果がボード上で人の対応を待っている | デリバリーの受け入れ、マージやデプロイの承認、コーディングツールの操作の承認 |
| デリバリーの**受け入れ** / **修正依頼** | そのスナップショットについて、受け入れ基準と根拠への評価を人が記録した | GitHub/GitLab のマージ権限の変更、デプロイの実行、ツールの承認プロンプトの再有効化 |
| ボードのステータス `done` | Multica のボード上でスコープが閉じた（多くは人の確認後、または Multica が観測した締めの PR マージイベント後） | 本番デプロイが成功したことの証明 |

issue を `in_review` に動かすと、Multica の内部だけに閉じた副作用はあります。autopilot の実行を確定し、過去の実行失敗通知をアーカイブできます。いずれも Multica の帳簿の中にとどまり、マージやデプロイの権限ではありません。

コーディングツールは無人で動きます。承認プロンプトは自動で応答されます（既定の経路では `bypassPermissions` / `danger-full-access`。[境界ではないもの](#境界ではないもの)を参照）。Multica のレビューボタンは、すでに動いている agent プロセスに対してこれらのプロンプトを戻すことはできません。

### Multica が実際に拒否する境界

以下は Multica が制御する境界であり、プロンプトでもボードのラベルでもありません。

- **ワークスペースのメンバーシップ** — メンバーでない人はワークスペースの資源を読むことも変更することもできません。
- **プライベート agent の起動** — issue が見えることは、プライベート agent を動かす権利（割り当て、メンション、再実行）を与えません。
- **実行スコープの `MULTICA_TOKEN`** — 実行が Multica API 上であなたや別の agent として振る舞うことはできません。
- **デリバリーレビューの CAS** — 古いスナップショットや同時レビューは競合で敗れます。マージが解錠されるわけではありません。
- **決定は宛先の人だけ** — 構造化された決定の依頼に答えられるのは、宛てられた本人だけです。
- **CLI 認証は操作者だけ** — あるマシンのログイン/ログアウトのコードは、認可された操作者の手元にとどまります。
- **記憶の評価は人が採用** — オフラインや接続状態の評価レポートは、人が採用する経路を通らずに記憶を昇格させません。

マージやデプロイを本当に止めたいなら、その仕組みはコードホスト、デプロイ用の資格情報、あるいは外部のポリシーエンジンに置いてください。デーモンユーザーが持つ周囲のアクセス権の外側にある、制限された identity と併せてです。Multica は `in_review` というラベルからその境界を作り出したりはしません。

## 実行に実際に適用されたモードを確認する

実行がサンドボックスなしで起動すると、デーモンは warn レベルでログを出します:

```bash
multica daemon logs --lines 200 | grep "codex sandbox"
```

Codex の実効設定を確認するには、その実行の `CODEX_HOME` にある `config.toml` の管理ブロックを見てください。`# BEGIN multica-managed` と `# END multica-managed` に挟まれた部分は、実行のたびにデーモンが書き込みます。
