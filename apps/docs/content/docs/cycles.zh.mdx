周期是某个[项目](/projects)的一段定期迭代：一个开始日期、一个结束日期，以及团队在这段时间里承担的任务。

项目回答"我们在做什么"，周期回答"接下来两周我们做什么"。没有交付节奏的项目不需要周期。

## 周期的组成

| 部分 | 作用 |
|---|---|
| **名称** | 这次迭代的叫法，例如"Sprint 14""十月发布"。 |
| **项目** | 它规划的那一个项目。周期只接收该项目的任务。 |
| **开始与结束日期** | 时间范围。状态由日期决定：周期进入进行中，是因为日历翻页，而不是有人点了开始。 |
| **人的容量 / 智能体容量** | 两个独立的数字。任何一个都可以留空，表示"未设置上限"。 |
| **负载属性** | 可选的工作区数字属性，其值代表单个任务的负载。不设置时，负载就是任务数。 |
| **顺延** | 周期结束时是否把未完成的工作移到下一个周期。默认开启。 |

同一项目的周期可以重叠——支持周期与功能周期并行是正常安排，不是错误。

## 人和智能体的容量分开统计

Multica 把这两类分开统计，因为它们不能互相替代：一个对人来说排得下的迭代，对智能体可能完全排不下，而合并成一个"团队容量"恰好会把这一点掩盖掉。

任务落在哪一侧由指派对象决定：

| 指派对象 | 计入 |
|---|---|
| 成员 | 人 |
| 智能体或小队 | 智能体 |
| 无人 | 两侧都不计，单独显示为未指派 |

未设置容量时只显示负载，不画进度条。这与容量为 0 不同，也不会因此被判为超出容量。

## 负载：按任务数还是按数字属性

默认一个任务算一个单位，界面会明确说明。选择一个工作区数字属性（故事点、预估工时等）后，负载变成这些属性值的合计。没有值或值不是数字的任务按 0 计算。

## 燃尽图

燃尽图从开始日期到结束日期，每天一个点，中间没有空缺：

- **过去的日子**来自每日快照。没有快照的那天沿用上一次的数值。
- **当天**实时计算，因此在两次快照之间也与看板一致。
- **未来的日子**只画理想线——那些日子还什么都没发生。

理想线从周期*当前*的总量出发，到最后一天归零。以当前值为基准是有意为之：中途加入的范围会抬高团队面对的标准，而不是悄悄消失。

<Callout type="info">
周期的历史从它创建后的第一份每日快照开始。更早的日期以平铺方式绘制，并在图上说明。Multica 不会编造自己没有记录过的过去。
</Callout>

## 把任务放进周期

设置任务的 **周期** 属性，或者选中多个任务后使用批量工具栏里的周期操作。周期只接收自己项目的任务：指定其他项目的周期会被拒绝，而批量工具栏只在所选任务同属一个项目时才显示周期操作。

周期页面提供与项目页面相同的看板、列表、表格和时间线，范围限定为该周期的任务。

## 周期结束时会发生什么

结束日期过去而无人关闭时，Multica 会关闭它。若顺延处于开启状态，未完成的任务会移到同一项目的下一个周期（开始日期最近的后续周期），每一次移动都会记录在任务上。

如果没有下一个周期，这些任务将不再属于任何周期，并通知项目负责人，以免未被规划的工作悄悄挂在一个已经结束的计划上。

关闭会固定燃尽图。已完成的任务保持原样：一个已关闭的周期保留着它交付了什么的记录。

## 周期与目标

周期回答*何时*，[目标](/goals)回答*为何*。目标跨越多个项目，比任何单个周期都活得更久，并且会跨所有关联项目汇总进度——这正是目标可以当作跨项目战役来用的原因。一个任务可以同时服务于某个目标并处在某个周期里，两者互不影响。
