A workspace is Multica's top-level boundary. Members, issues, projects, agents, skills, and run history all belong to one workspace and are fully isolated from every other.

## What a workspace contains

| Category | Contents |
|---|---|
| **Work** | Issues, projects, comments, attachments, run history |
| **Team** | Members, roles, invitations |
| **Agents** | Agent configuration, skills, runtimes, automations |
| **Shared settings** | Context, labels, custom properties, integrations |

**Context** is provided to every agent in the workspace — the place for team background, product conventions, and long-lived requirements. One-off run requirements belong in the corresponding issue.

## Create a workspace

Creating a workspace asks for three things:

- **Name**: shown to members; can be changed later.
- **Workspace URL**: the slug in the address — the `my-team` in `multica.ai/my-team`. Lowercase letters, digits, and hyphens only; it cannot collide with an existing workspace or a reserved address, and it cannot be changed after creation.
- **Issue prefix**: pre-filled from the workspace URL and editable before you create — with the prefix `MUL`, issue numbers appear as `MUL-1`, `MUL-2`, counting up independently within the workspace. Uppercase letters and digits, up to 10 characters; it can be changed later in settings.

The creator automatically becomes an `owner`. A new workspace can also start from a [pack](/packs) — the function's types, views, rules and colleagues are installed as its first act.

## Change settings

`owner` and `admin` can change the name, icon, description, context, and issue prefix; `member` can only view them.

![Workspace settings: name, context, slug, issue prefix, and the danger zone](/images/docs/workspace-settings.webp)

<Callout type="warning">
After the issue prefix changes, every issue immediately switches to the new number (`MUL-5` becomes `NEW-5`), but the old numbers in PRs, branch names, and chat history do not update.
</Callout>

## Compose an organization

Open **Organization** to group people and agents into teams. Each structure applies to one project or serves as the workspace default.

- **Compose**: select a team in the chart, then assign members, roles and a human owner. The inspector separates team membership, autonomy and relationships. Pan the canvas or use the zoom controls to explore larger structures.
- **Activity**: inspect routing, escalations, actual spending and suggested corrections from the server.
- **History**: compare saved definitions and restore one as a new revision. Restoration keeps the current status, owner, budget and dates, and runs current validations. It works after activation; dissolved structures remain read-only.
- **Settings**: edit the structure’s name, budget and end conditions. Advanced JSON remains available for model-specific configuration.

Save before activating. Changes stay in the editor until saved; activation still requires a human owner and an evaluation attestation. A conflicting revision is rejected instead of overwriting another member’s save.

**New structure** offers five prepared teams: customer support, product and engineering, a content agency, operations and finance, and research. Installation uses the workspace import preview and requires an owner or admin. Each team includes three agents, a shared skill, a project, an organization, a starter task and a weekly review. Connect the imported agents to runtimes before execution; the organization starts as a draft and the review is paused. Name conflicts are renamed.

**Import / export** opens the existing workspace transfer flow, including its preview, conflict handling and transfer history. The same two steps from the terminal: `multica workspace export --out bundle.zip`, then `multica workspace import bundle.zip --preview` before `multica workspace import bundle.zip --strategy rename`.

**Packs** go one step further than a prepared team. A [pack](/packs) is one file that sets up a whole function — helpdesk, ops, support, sales, marketing, leadership, research, HR, finance, legal — with that function's work item types, statuses, labels, properties, views, rules, a doctrine section, a project and its agents as paused colleagues. Installing one never overwrites what the workspace already has, and because every row it creates is recorded against the pack, it can be upgraded in place or uninstalled later. **Settings → Packs** holds the catalogue.

## Switch and leave

One account can join multiple workspaces. Switching only changes what you are currently viewing; it moves no data.

After leaving a workspace, you need a new invitation to return. Leaving also deactivates the runtimes you own, archives the agents bound to them, and cancels their unfinished runs.

The last `owner` cannot leave; promote another member to `owner` first.

## Delete a workspace

Only an `owner` can delete a workspace. Deletion permanently removes all of its work, members, agent configuration, and run history, and cannot be undone. If you are only stepping away for a while, leave instead of deleting.

### Teams, people, and agents in Organization

Creating an agent opens the agent setup flow. Creating a team adds an empty organizational group; choose its human owner and parent team explicitly. Add existing people or agents through **Add members**. Removing a membership keeps the workspace identity intact. Moving a member to another team clears their previous team role and receiving-agent designation.

The **People & agents** view distinguishes team membership from human ownership. A linked execution squad takes routing priority; otherwise the designated receiving agent, first agent, or human owner receives the request. Use **Test a request** to inspect routing before activating. Changing the request or chart invalidates the displayed test result.

Creation and editing drafts are saved on the current device, separately for each workspace. Creating an organization never replaces an existing scope. Publishing changes to an active organization requires reviewing the changes; activation attestation remains a manual declaration of testing.
