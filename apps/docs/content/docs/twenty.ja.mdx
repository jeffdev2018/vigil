[Twenty](https://twenty.com) はオープンソースの CRM です。ワークスペースに接続すると、次の 4 つの形でチームの仕事の一部になります。

- **エージェントが CRM の中で働きます。** すべてのエージェント実行は、ワークスペースの API キーを使って `twenty` という名前の Twenty 自身の [MCP](/mcp-server) サーバーを持ちます。エージェントはプラグインやキーのコピーなしに、人物や会社を検索したり、opportunity を更新したり、ノートを記録したりできます。
- **CRM のイベントがトリアージキューに届きます。** Twenty の Webhook（人物の作成、opportunity のステージ移動など）は、レコードへのリンクと変更されたフィールドの一覧を持つ [トリアージ](/triage) 項目になります。何を課題にするかは人が決めます。
- **承認された項目はリンクして戻ります。** CRM の項目が承認されると、Multica はそのレコードに Task を記録し（`Vigil ONE-42: <title>` のように課題をリンクします）、CRM 側にもそこから生まれた作業が見えるようにします。
- **両方で 1 つの ID。** ワークスペースのメンバーは、メールアドレスで Twenty のメンバーと対応付けられます。両方の製品を同じ identity provider にサインインさせれば（**設定 → セキュリティ**のワークスペース SSO）、どちらの側でも同一人物になります。対応付けは設定画面で確認できます。

Multica は Twenty の公開 REST、GraphQL、Webhook、MCP インターフェースを通じて通信します。Twenty の内部では何も実行されません。

## ワークスペースを接続する

ワークスペースのオーナーまたは管理者が、**設定 → 連携 → Twenty CRM** の下で接続します。

1. Twenty で API キーを作成します（**設定 → APIs & Webhooks**）。このキーは作成したワークスペースメンバーの権限で動作するため、Multica 専用のメンバーを用意しておくと監査ログが読みやすくなります。
2. Multica でインスタンス URL（`https://crm.example.com`、Twenty Cloud の場合は `https://api.twenty.com`）とキーを貼り付けます。
3. 受け取るイベントと、エージェントが CRM を使えるかどうかを選びます。既定では opportunities（すべての操作）、新しい人物、新しい会社、新しい task を購読し、CRM をエージェントに公開します。
4. 接続します。Multica はインスタンスに対してキーを検証し、暗号化して保存し、Twenty に Webhook を登録し、接続内容（インスタンス、状態、イベント、MCP エンドポイント、受信パス）を表示します。

API キーと Webhook のシークレットは `MULTICA_TWENTY_SECRET_KEY` で暗号化して保存されます。どちらも二度と表示されません。**接続を確認**するとキーを再検証して結果を記録し、拒否されたキーは再接続するまで接続をエラー状態のままにします。

<Callout title="セルフホスト">
運用者が `MULTICA_TWENTY_SECRET_KEY` を設定するまで、この連携はオフのままです（[環境変数](/environment-variables) を参照）。Twenty は Webhook を `MULTICA_PUBLIC_URL` に配信します。これが未設定でも接続はエージェントへのサービスを続け、設定画面には受信パスが表示されるので、Twenty 側で購読を手動登録できます。
</Callout>

## エージェントが得られるもの

**エージェントに公開**がオンの間、そのワークスペースのすべての実行は、Multica のツールと並んで Twenty の MCP サーバーが最初からマウントされた状態で始まります。Twenty のサーバーは動的で、エージェントはまずカタログを一覧表示し、その中の 1 つのツール（`find_many_people`、`update_one_opportunity` など）を実行します。組み込みのプラットフォームスキルは、エージェントに書き込む前に読み取ること、変更したすべてのレコードをクロージングステータスで名指しすること、キーやレコードのダンプをコメントに貼り付けないことを指示します。

公開をオフにすると、次の実行からサーバーが取り除かれます。すでに進行中の実行はそのまま保持します。エージェントの信頼ダイヤルは何も変わりません。CRM への書き込みは、そのキーの権限で Twenty が行う外部アクションなので、エージェントにできるようにしたいことに合わせた権限を持つメンバーにキーを紐づけてください。

## トリアージ内のイベント

各配信は受け入れられる前に検証されます。Webhook パス内のトークンがワークスペースを特定し、HMAC 署名（`${timestamp}:${body}` に対する `X-Twenty-Webhook-Signature`、購読用に Twenty が発行したシークレットを使用）が送信元を証明し、5 分より古いタイムスタンプは拒否されます。署名がない、または誤って署名された配信は拒否され、送信元のレート制限にカウントされます。

受け入れられたイベントは、`Twenty · Opportunity updated: Acme renewal` のようなタイトルの保留項目になり、レコードへのリンク、変更されたフィールド、本文中の短い要約を持ちます。生のイベントはその項目に残ります。この取り込み元は [メール取り込み](/triage#email-intake) と同じようにゲートされます。人が承認、却下、またはマージします。イベントパターンは Twenty の `object.operation` 形式でワイルドカードを使えます（`opportunity.*`、`*.created`、`person.updated`）。リストを変更すると、同じ受信アドレスで Twenty 側の購読が再登録されます。

項目を承認すると、通常どおり課題が作成され、バックグラウンドでそのレコードにバックリンクの Task が記録されます。CRM が落ちていても承認はブロックされません。

## メンバー

**設定 → 連携 → Twenty CRM → メンバー** には、同じメールアドレスを持つ Twenty のメンバーと対応付けられたすべてのワークスペースメンバー、および対応するものがない Twenty のメンバーが一覧表示されます。対応付けはメールアドレスのみで行われ、どちら側にもアカウントを新規作成する必要はありません。両方の製品で同じ identity provider を設定していれば、1 回サインインするだけでどちらでも認識されます。

## 接続を解除する

切断すると、Twenty 側の Webhook 購読が削除され、受信トークンが失効し、キーは破棄されます。すでにキューにある項目とすでに作成された課題は履歴を保持します。Twenty にすでに記録された Task はそのまま残ります。
