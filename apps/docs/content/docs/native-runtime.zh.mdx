每个工作区都有一个**原生运行时**——一条服务器内置的执行路径，直接在 Multica API 进程内运行智能体的工具调用循环。它不需要[守护进程](/daemon-runtimes)，不需要连接电脑，也不需要 AI 编程工具 CLI。

## 什么时候选择它而不是守护进程运行时

守护进程运行时驱动一款真正的 AI 编程工具（Claude Code、Codex 等）在检出的仓库上工作，拥有完整的文件系统和 shell 访问权限。原生运行时两者都没有：它只能通过一小组固定的、限定在任务范围内的工具进行读写（见下文）。适合不需要仓库检出或 shell 访问的轻量任务分诊、状态变更和评论工作；写代码的工作仍然留给守护进程运行时。

因为不需要安装守护进程或 CLI，原生运行时始终可用，也不会显示 CLI 版本——绑定它的智能体在工作区创建的那一刻就已就绪。

## 运行方式

原生运行时会为每个工作区生成一条 `agent_runtime` 记录（`runtime_mode = 'native'`，provider 为 `native`），并像其他运行时一样出现在运行时选择器和列表中——目前 UI 中没有特殊标记。

一个名为 `native_agent_tick` 的定时任务每 10 秒运行一次，为每个工作区的原生运行时，通过与守护进程轮询相同的资格判断路径领取排队中的运行。每个被领取的运行都在自己的 goroutine 中执行，超时时间为 10 分钟，与 tick 本身相互独立。在一次运行内，工具调用循环最多 12 轮，每个工具结果在返回给模型前最多保留 8 KB。

<Callout type="info">
原生运行时在服务器上所有工作区之间共享一个全局并发上限：8 次运行，而不是按工作区单独设置上限。
</Callout>

## 原生工具

工具调用循环只能调用一小组刻意封闭的工具：

| 工具 | 作用 |
|---|---|
| `get_issue` | 读取一个任务及其最近的评论（默认是当前运行所属的任务）。 |
| `list_issues` | 列出任务，可按状态和优先级筛选，一次最多 50 条。 |
| `add_comment` | 以智能体身份发表评论。 |
| `update_issue` | 更新标题、描述或优先级——不包括状态，状态变更请用 `transition_issue`。 |
| `transition_issue` | 通过与 UI 相同的受控路径变更任务状态。 |
| `create_sub_issue` | 在当前运行所属的任务下创建一个子任务。 |
| `create_issue` | 创建一个新的顶层任务，默认分配给智能体自己。 |

模型提供的任何任务 ID 在使用前都会重新对照运行所属的工作区校验——工具不会仅凭模型输出就信任一个任务引用。

## 护栏

- **受控的状态变更。** `transition_issue` 会执行与 HTTP handler 相同的状态流转规则判断，以该智能体作为操作者——智能体不携带任何工作区角色，因此不能继承 owner 或 admin 的流转权限。根据工作区规则，变更可能立即生效、被拒绝并把原因返回给模型，或者作为待审批请求保留，此时状态保持不变。
- **创建时不会静默改变状态。** `create_issue` 和 `create_sub_issue` 总是以默认状态创建任务，绝不会直接落在一个原本会被工作区规则拦截的状态上。创建之后的任何状态变更仍然要经过 `transition_issue`。
- **不会自我触发运行循环。** `create_issue` 不会为它创建的任务入队运行，因此一次原生运行不会级联出立即重新触发自己的工作。

## LLM 要求

原生运行时调用的是与[对话自动生成标题和后续提问辅助层](/environment-variables#服务端-llm)相同的服务端 LLM 客户端：必须配置 `MULTICA_LLM_API_KEY` 或 `MULTICA_LLM_BASE_URL`。未配置时，tick 什么都不做——原生运行时上排队的运行只会持续等待，不会报错，直到这一层被启用。
