課題は Multica で作業を進める基本単位です。機能、バグ、調査など、メンバーまたはエージェントが責任を持って進める作業はすべて課題になります。関連する議論、ステータスの変化、実行のたびの記録が同じ場所に残るため、チャット履歴やターミナルのログからコンテキストを組み立て直す必要はありません。

## 課題の構成

| 内容 | 役割 |
|---|---|
| **タイトルと説明** | 目的、背景、要件、受け入れ条件。 |
| **ステータスと優先度** | 作業がどの段階にあり、何を先に進めるか。 |
| **担当者** | ワークスペースのメンバー、エージェント、またはスクワッド。 |
| **日付、ラベル、カスタムプロパティ** | 計画、分類、チーム独自のフィールド。 |
| **プロジェクトと親子関係** | より大きな作業への所属、または子課題への分割。 |
| **アクティビティと実行ログ** | コメント、ステータス変更、実行、エージェントが返した結果。 |

![課題詳細: 説明、ディスカッション、右側のプロパティと実行ログ](/images/docs/quickstart-run-result.webp)

## 課題の作成

**課題** ページまたはプロジェクト内で作成します。タイトルだけで作成でき、ほかのプロパティは後からいつでも補えます。

各課題には `MUL-123` のような番号が付きます。数字はワークスペース内で増えていき、管理者がワークスペースの課題プレフィックスを変更すると、番号は新しいプレフィックスで表示されます。詳細は[ワークスペース](/workspaces#ワークスペースの作成)を参照してください。

## 担当者の選択

| 担当者 | 効果 |
|---|---|
| **メンバー** | そのメンバーが作業を進めます。実行は作成されません。 |
| **エージェント** | そのエージェントの実行が 1 件作成されます。 |
| **スクワッド** | スクワッドのリーダーが受け取り、誰に任せるかを決めます。 |

エージェントまたはスクワッドに割り当てると、課題が `backlog` にない限り即座にキューへ入ります。ランタイムがオフラインの場合、実行はキューで待機します。アーカイブ済みのエージェントとスクワッドには割り当てられません。

割り当てはエージェントのアクセス範囲（Access）を回避しません。スクワッドに割り当てる場合は、リーダーの Access が検証されます。詳細は[課題をエージェントに割り当てる](/assigning-issues)を参照してください。

## ステータス

どのワークスペースにも 7 つの組み込みステータスが用意されており、4 つのライフサイクルカテゴリに分類されます。

| カテゴリ | 組み込みステータス | 意味 |
|---|---|---|
| `unstarted` | `backlog`、`todo` | まだ始まっていない作業。計画済みでも保留中でも同じです。 |
| `started` | `in_progress`、`in_review`、`blocked` | 着手済み、確認待ち、または今は先に進めない状態。 |
| `done` | `done` | 無事に完了した終了状態。 |
| `closed` | `cancelled` | もう追いかけない終了状態で、成功による完了ではありません。 |

カテゴリはライフサイクルの判断を単純に保つためのものです。ボード、リスト、フィルタ、並び替えはいずれも個々のステータスを見ており、具体的なステータスにはエージェントや自動化が依存する細かい挙動が残ります。

| ステータス | 意味 |
|---|---|
| `backlog` | まだ着手しない。エージェントに割り当て済みの課題は、`backlog` を離れて初めて実行が作成されます。 |
| `todo` | 内容が固まり、開始を待っている。 |
| `in_progress` | 作業中。 |
| `in_review` | 結果が出て、確認待ち。 |
| `done` | 完了。 |
| `blocked` | 今は先に進めない。 |
| `cancelled` | 中止したが、記録は残す。 |

ステータス間に固定のフローはなく、メンバーもエージェントも直接変更できます。

エージェントは、作業がタスクに与えた実際の変化をそのままステータスに書き込みます。タスクが求めているもの（コードでも、調査でも、設計でも、タスク自身が求めるレビューでも）を作り始めた時点で `in_progress` に進め、実行中からボードに反映させます。納品したら `in_review` に進め、ターンを越えて作業が続く場合は `in_progress` のままにします。そのタスク自身の成果物を生まないターン（質問への回答、他所が持つ作業への助言）では、最初から最後までステータスを変更しません。これらの変更は、実行中にエージェントが Multica CLI から明示的に書き込むものです。実行の開始や完了でサーバーがタスクのステータスを切り替えることはありません（下記の 2 つのシステム例外を除く）。`done` は通常、人による確認か、クローズ意図付き PR のマージのような連携によって設定されます。

<Callout type="info">
次の 2 つの変更はシステムが行います。

- 実行が失敗し、その課題にほかの実行がなく、リトライも起動しなかった場合、`in_progress` は `todo` に戻ります。
- 紐づく GitHub PR がクローズ意図付きでマージされ、open または draft のまま残る紐づき PR がほかにない場合、課題は `done` になります。
</Callout>

### カスタムステータス

ワークスペースの owner または admin は、**設定 → ステータス**から独自のステータスを追加できます（`Code Review`、`QA`、`Rework` など）。どのステータスも 4 つのライフサイクルカテゴリのいずれかに属します。

| カテゴリ | ライフサイクル上の意味 |
|---|---|
| `unstarted` | まだ始まっていない。組み込みの `backlog` と `todo` を含みます。 |
| `started` | 進行中。確認待ちや返信待ちも含みます。 |
| `done` | 無事に完了した終了状態。 |
| `closed` | 中止、またはもう追いかけない終了状態で、成功による完了ではありません。 |

カスタムステータスが引き継ぐのはライフサイクル上の意味だけで、組み込みステータスの個別の挙動は引き継ぎません。`backlog` の保留、`in_review` による[オートパイロット](/autopilots)実行の完了、`blocked` の失敗処理、`in_progress` の失敗からの復帰は、いずれも引き継がれません。その挙動が必要な場合は、対応する組み込みステータスを使ってください。以前に作られたカスタムステータスも同じルールに従います。Awaiting Response は進行中の作業であり、レビューの自動完了ではありません。割り当てと作成は、これまでどおり一般的なエージェントのトリガールールに従います。

プラットフォーム自身がステータスを設定するとき（`todo` への差し戻しや、マージされた PR による `done`）に書き込まれるのは、常に組み込みステータスです。

インストール済みのクライアント向けに、API の既存のカテゴリフィールドは 7 値の転送用 enum を返し続けます。新しいクライアントはそれを 4 つのカテゴリに正規化します。転送上の値が挙動の継承を与えることはありません。データベースに保存されるのは 4 つのライフサイクル値だけです。

ここから次の 4 点が導かれます。

- **カテゴリは作成後に変更できません。** 変更すると、すでにそのステータスにある課題の挙動を黙って書き換えることになるため、編集画面では読み取り専用です。まず挙動を決めてから名前を付けてください。
- **ステータスによるグループ化は個々のステータスを使います。** ボードの列、リストのセクション、スイムレーンのステータス列は、組み込みステータスとカスタムステータスをそれぞれ区別します。`Code Review` と `QA` はどちらも `started` に属していても、別々の列になります。カテゴリは内部的なライフサイクルの分類であり、列名の代わりではありません。
- **組み込みステータスはロックされています。** 名前・色・カテゴリは変更できず、アーカイブもできません。このページを一度も開かないワークスペースのボードは、これまでとまったく同じままです。
- **アーカイブは無効化であり、削除ではありません。** すでにそのステータスにある課題は、名前も色も挙動もそのままです。次に誰かがステータスを設定するときに、選択肢として出てこなくなるだけです。

組み込みステータスは表示言語に合わせて翻訳されますが、カスタムステータスは入力した名前がそのまま表示されます。API と CLI はキーで参照します: `multica issue status MUL-42 code_review`。設定ページではキーを名前から生成します。API では明示的に指定でき、省略した場合だけ名前から生成されます。いずれの場合もキーは作成時に確定し、あとで名前を変更してもキーは変わりません。

## 課題と実行

課題は継続して存在する作業の記録であり、[実行](/tasks)はエージェントによる 1 回の具体的な実行です。1 つの課題からは、最初の実装、追加の修正、再度の確認というように、複数の実行が順に生まれることがあります。実行の完了はその 1 回の実行が終わったことを意味するだけで、課題が完了したかどうかは課題のステータスで判断します。

## 試行のレース

課題に有力な進め方が複数あるときは、それらを同時に実行して 1 つだけを残せます。各試行はそれぞれ専用のブランチ上で行う通常の実行であり——4 件のレースは 4 回分の実行を消費します——同じエージェントが異なる 2 つのモデルで 2 回登場することもあります。

```bash
multica issue race start ENG-42 --attempt "Backend Dev" --attempt "Backend Dev:opus" --attempt "Refactor Bot"
multica issue race list ENG-42
```

`--attempt` は `<agent>[:<model>]` の形式を取り、2〜5 回繰り返せます。レースは課題ごとに同時に 1 件しか実行できません。現在のレースが終わるまで、新しいレースの開始は拒否されます。

勝者を選ぶのは人の判断です。勝者となった実行はそのまま残ります。まだ開いているほかの試行はすべて取り消され、それによってデーモンがそのブランチと worktree を破棄します。

```bash
multica issue race settle ENG-42 --group <race-id> --winner <run-id>
multica issue race abandon ENG-42 --group <race-id>
```

`race list` は各試行の差分を表示します。`stat only (too large)` は、パッチがサーバーの保存できる上限を超えたことを意味します——変更自体は存在するので、ブランチを確認してください。

## プロジェクトと子課題

課題は最大 1 つの[プロジェクト](/projects)に属し、プロジェクトはその中の実行に共有の説明とリソースを提供します。別のプロジェクトへ移してもコピーは作られません。

大きな作業は子課題に分割できます。親課題が全体の目標を保持し、子課題はそれぞれ独立して進みます。親子のステータスは連動しません。

子課題には**ステージ**（stage）を設定でき、1、2、3 とバッチごとに進められます。未完了の最も早いステージのすべての子課題が `done` または `cancelled` に到達すると、親課題に子課題完了の通知が届きます。親課題の担当者がエージェントの場合は、そのエージェントが起こされ、次のステージへ進むかどうかを判断します。ステージ未設定の子課題は同じバッチとして扱われ、すべて終了したときに一度だけ通知されます。

## 作業アイテムタイプ

**作業アイテムタイプ**は課題が何であるかを示します——バグ、ストーリー、エピック、課題、またはワークスペース独自のタイプ。どのワークスペースもこの 4 つから始まり、オーナーと管理者は **設定 → 作業アイテムタイプ** で追加・改名・色変更・並べ替えができます。

タイプは動作を伴いません。実行を開始せず、ステータスも変えず、何も妨げません。作業の分類と絞り込みを行い、どのカスタムプロパティが適用されるかを決めます。

タイプのない課題は**タイプなし**で、これは正常な状態です。タイプ機能より前に作成された課題はすべてタイプなしで、動作に支障はありません。分類が実際に分かっているときにタイプを設定してください。

カスタムプロパティは 1 つ以上のタイプに**限定**できるため、バグ専用の項目がすべてのストーリーに並ぶことはありません。限定のないプロパティはタイプなしの課題を含めどこでも適用されます。課題のタイプを変えても値は削除されません。新しいタイプが対象としない値は折りたたまれますが読み取れるままで、タイプを戻せば再び表示されます。

## 繰り返す課題

戻ってくる作業があります。週次のレビュー、月次のレポート、前回が終わったらまた実行するチェックリストなどです。課題を手でコピーする代わりに **繰り返しルール** を設定してください。その課題がシリーズの *起点* になり、次の発生分は Multica が登録します。

課題を開き、プロパティの **繰り返し** を設定します。

| 選択肢 | 動作 |
|---|---|
| **毎日**、**平日**、**毎週**、**毎月** | プリセット。時刻を選ぶとスケジュールは Multica が書きます。 |
| **カスタム** | 5 フィールドの cron 式を自分で書きます。次の 3 回がプレビューされます。 |
| **タイムゾーン** | スケジュールを読む IANA タイムゾーン。既定は UTC なので、9:00 をチームの現地時刻にしたい場合は必ず設定してください。 |
| **クローズしたとき** | 時計を使いません。現在の発生分が `done` または `cancelled` のステータスに達した時点で次が作成されます。 |
| **一時停止** | ルールは課題に残したまま、誰かが再開するまで発火しません。 |

繰り返しルールを設定、変更、解除できるのはワークスペースのメンバーだけです。エージェントは担当している課題のルールを読んで提案できますが、恒久的な指示を自分で有効化することはできません。

### 発生分が引き継ぐもの

各発生分は、元の課題ではなくシリーズの **直近** の発生分からコピーされた新しい課題です。そのため、途中でチームが加えた修正がそのまま引き継がれます。

- タイトルと説明。markdown のチェックボックスはすべて未チェックに戻ります。
- 優先度、担当者と協力者、プロジェクト、ラベル、カスタムプロパティ、受け入れ基準。
- 期限。前の発生分が作成日と期限の間に持っていた間隔を保ったままずらされます。

新しい課題は `todo` で始まり、作成元としてそのルールを記録します。コメント、添付ファイル、実行履歴はコピーされません。発生分は新しい作業であって、会話の複製ではないからです。

<Callout type="info">
課題がエージェントに割り当てられている場合、発生分ごとに他の課題と同じように実行が始まります。毎日のルールは、誰かが止めるまで 1 日 1 回の実行です。有効化したら [実行](/tasks) を確認してください。
</Callout>

### シリーズ

シリーズのすべての課題に繰り返しバッジが付き、どれを開いても同じルールが表示されます。ルールが設定された課題、すでに作成された発生分（新しい順）とそのステータスおよび期限、そして次回以降の実行予定です。スケジュールの変更、一時停止、シリーズの停止はどの課題からでも行えます。

シリーズを停止してもルールが消えるだけです。すでに登録された発生分は通常の課題として残り、コメントも実行履歴もそのままで、次が作られなくなるだけです。

ルールの設定と解除はどちらもワークスペースの監査ログに記録されます（`issue.recurrence_set`、`issue.recurrence_cleared`）。「この課題はなぜ何度も戻ってくるのか」には必ず名前付きの答えがあります。

### CLI とエージェントから

```bash
multica issue recurrence show MUL-42
multica issue recurrence set MUL-42 --cron "0 9 * * 1" --timezone Europe/Paris
multica issue recurrence set MUL-42 --weekdays 09:00
multica issue recurrence set MUL-42 --mode on_close
multica issue recurrence clear MUL-42
```

`--daily`、`--weekdays`、`--weekly "MON 09:00"`、`--monthly "1 09:00"` は画面と同じプリセットです。明示的な `--cron` はプリセットより優先され、`--disabled` はルールを一時停止の状態で登録します。MCP では同じ 3 つの操作が `vigil_issue` のアクション `recurrence_get`、`recurrence_set`、`recurrence_clear` です。読み取りはエージェントにも開かれていますが、2 つの書き込みはメンバー以外に `403` を返します。

繰り返す課題は [オートパイロット](/autopilots) とは異なります。繰り返しは同じ作業を担当者のためにもう一度登録するものであり、オートパイロットは指示をスケジュールで実行するもので、課題をまったく作らないこともあります。

## ビューの切り替え

課題ページには、リスト、ボード、テーブル、ガント、スイムレーン、カレンダーの 6 つのビューがあります。ステータス、担当者、プロジェクト、作業アイテムタイプなどのプロパティで絞り込み・並べ替えでき、表示されるのはどれも同じ課題です。カレンダーは各課題を期限日に配置します。

## 課題の削除

ワークスペースのメンバーは誰でも課題を削除できます。

<Callout type="warning">
削除は元に戻せません。課題とそのコメント、添付ファイル、関連レコードは完全に削除され、終了していない実行はキャンセルされます。作業を続けないだけであれば、ステータスを `cancelled` に変更してください。議論と結果は引き続き参照できます。
</Callout>

## 次のステップ

- [プロジェクト](/projects) — 複数の課題で完了する作業を整理します。
- [コメント](/comments) — 課題を中心に議論、返信、@メンションを行います。
- [課題をエージェントに割り当てる](/assigning-issues) — 作業をエージェントに渡して最初の実行を開始します。
- [実行](/tasks) — キュー、実行、リトライ、キャンセルの仕組みを理解します。
