有些判断只应该由人来做：两种方案该选哪一个、一步破坏性操作是否真的要执行、一个描述模糊的任务实际想要什么。智能体不必猜测或停滞，而是可以发一张带选项的结构化问题——**Decision Card**——拿到答案后再继续。

## Decision Card

一张卡片包含一个问题、2 到 8 个选项（每个选项有 id、标签，以及可选的一句话影响说明）、一个可选的推荐选项，以及紧急度（`low`、`normal`、`high`）。成员也可以在任务上手动发起一张。

待处理的卡片会出现在任务的**决策**区块中，每个选项各有一个按钮（推荐选项排在最前），并附带一个自由文本的替代方案（"给出其他回答…"），供所有选项都不合适时使用。如果读者本人对这类问题有过往回答记录，卡片会一并显示（例如"对于此类请求，你在 4 次中有 3 次选择了「重试」"）；这只是提示，不是默认值，两者都只需一次点击即可到达。

回答只会被记录一次：对同一张卡片的第二次尝试会被拒绝。当任务分配给智能体时，回答会开始一次新的运行，问题和所选答案会放在其交接说明的最前面；分配给人的任务没有需要恢复的运行，只会保留已记录的回答。

<Callout type="info">
如果工作区设置了 Decision SLA（一项管理员设置），卡片会带有截止时间。逾期后卡片会升级——先通知指定的替补人选，再通知工作区的所有者和管理员——卡片本身也会显示"已逾期"以及通知了谁。升级只会增加通知，不会自动替你回答卡片。
</Callout>

## 需求访谈

在着手处理一个描述模糊的任务之前，智能体可以一次性提出最多三个选择题，而不是一个接一个地问。这些问题是共享同一个分组的 Decision Card；等待期间任务会被放入**等待产品回答**状态（该工作区首次使用时自动创建，属于 `blocked` 分类）。只有当分组内所有问题都得到回答后，运行才会恢复——只开始一次新的运行，按顺序在交接说明最前面列出每个问题及其答案。只回答了分组中的一个问题、其余仍待处理时，暂时不会发生其他事情。

一个任务同一时间只能有一场进行中的访谈；在有访谈待处理时再次发起会被拒绝。

## 在哪里回答

每一个需要人来裁定的请求——一张 Decision Card、一次运行正在等待的审批关卡（git push、敏感工具调用、支出）、一次被流转规则挡住的状态变更、来自目标循环的问题——都是一次**审批**，无论你在哪里遇到它都可以就地裁定：

- **任务的时间线**——待处理的请求会在被提出的那一刻出现在时间线中并带有按钮，时间线上方的横条会显示有多少在等待并可跳转到每一个。已回答的请求作为历史保留在**决策**区块中。
- **收件箱**——`decision_request`、`transition_approval_requested` 或 `goal_question` 项的一行会带有同一张卡片：无需打开任务即可在列表或详情面板中裁定。**收件箱 → 待你决定**保留你可见的所有任务中最紧迫的五个，排序方式与[需要你处理列表](/inbox#需要你处理)相同。
- **聊天**——与智能体聊天时，该智能体提出的请求会显示在输入框上方。
- **移动端**——同样的卡片出现在任务时间线和收件箱详情中，此外还有**收件箱 → 决策**下的滑动列表。
- **聊天频道**——当工作区配置了简报频道时，Slack、Lark、Telegram 和 WeCom 会收到带有批准/拒绝按钮的请求（DingTalk 收到的按钮会打开该任务）。点击即可回答卡片，消息会更新为结果；点击被拒绝时，回复会说明原因（账号未绑定、已决策等）。

只有人可以回答；智能体尝试回答会被拒绝——这与谁可以发起请求的限制正好相反。

### 卡片中的审批关卡

关卡背后的卡片会先展示这次运行打算做什么，再让你裁定：关卡类型、工具的参数（密钥已遮蔽）、涉及的路径、智能体信任刻度允许的影响范围，以及在双重审批下已集齐所需审批中的几份。卡片还会倒计时到关卡的过期时间：在工作区超时时间内（**设置 → 审批关卡**）无人回答的关卡会被拒绝，其卡片由服务器代为回答，因此会从每个收件箱和时间线中消失，而不会一直悬着。

**设置 → 审批关卡 → 谁可以裁定关卡**可以把关卡限定给所有者和管理员（`owner_admin`），也可以交给能看到该任务的任意成员（`any_member`，默认值）。无法裁定的成员仍会看到该请求，并标注原因——因为"谁能裁定它"本身就是"这次运行为什么在等待"的一部分。被阻止的状态变更遵循各自规则自己的审批人角色设置。

### 停止所有智能体

**设置 → 审批关卡 → 停止所有智能体**会让新运行不再被接手，并把已在进行中的运行的所有关卡操作连同原因一起拒绝。停止会以横幅显示在任务列表和每个任务上，注明是谁设置的及原因；所有者和管理员可以从横幅解除停止。每一个被拒绝的请求都会说明停止是原因。

## CLI

发起卡片由智能体（或直接调用 API 的任何人）完成；回答是人的操作，只能通过界面进行。

```bash
multica decision ask <issue-id> \
  --question "重试失败的部署，还是回滚？" \
  --option "retry=重试|如果成功可以保留今天的修复" \
  --option "rollback=回滚|更安全，但会丢失今天的修复" \
  --recommend retry \
  --urgency high
```

`--option` 可重复指定，格式为 `id=Label` 或 `id=Label|impact`；至少需要两个。

```bash
multica interview ask <issue-id> --file questions.json
```

`questions.json` 的形式是 `{"questions": [...]}`，包含 1 到 3 个条目，每个条目为 `{"question": "...", "options": [{"id": "a", "label": "..."}, ...], "recommended_option_id": "a"}`，选项数为 2 到 8 个。`--file -`（或省略 `--file`）会改为从标准输入读取。

## API

| 方法 | 路由 | 操作者 | 请求体 |
| --- | --- | --- | --- |
| `GET` | `/api/issues/{id}/decisions` | 成员 | — |
| `POST` | `/api/issues/{id}/decisions` | 智能体或成员 | `{question, options[], recommended_option_id?, urgency?}` |
| `POST` | `/api/issues/{id}/decisions/{decisionId}/respond` | **仅限人类** | `{option_id}` 或 `{modified_text}`——二选一 |
| `POST` | `/api/issues/{id}/interview` | 智能体或成员 | `{questions: [...]}` |
| `GET` | `/api/inbox/decisions` | 成员 | 当前用户最多五张待处理卡片 |

## 限制

- 每张卡片需要 2 到 8 个选项；每个 id 必须唯一，问题最多 4 KB，每个标签或影响说明最多 512 字节。
- 一场访谈包含 1 到 3 个问题，每个问题有 2 到 8 个选项；一个任务同一时间只能有一场访谈进行中（`409 interview_pending`）。
- 回答已回答过的卡片会返回 `409 already_decided`。
- `urgency` 为 `low`、`normal` 或 `high`（默认 `normal`）。
