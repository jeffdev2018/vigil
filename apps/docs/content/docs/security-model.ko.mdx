에이전트가 실행을 맡으면 데몬은 AI 코딩 도구(Codex, Claude Code 등)를 자식 프로세스로 실행합니다. 이 프로세스가 무엇에 접근할 수 있는지 이해하는 것이 보안 모델의 전부입니다.

## 경계는 데몬을 실행하는 사용자

기본적으로 실행은 **데몬을 실행하는 운영체제 사용자의 모든 권한**으로 동작합니다. 해당 사용자가 읽고 쓸 수 있는 파일은 모두 읽고 쓸 수 있으며, 그 사용자의 자격 증명을 사용할 수 있고, 네트워크에도 제한 없이 접근합니다.

Multica는 파일 시스템 샌드박스를 보장하지 않습니다. 현재 예외는 하나뿐으로, Windows에서 Codex의 네이티브 샌드박스를 명시적으로 활성화한 경우입니다. 게다가 어떤 플랫폼과 설정 조합에서 샌드박스가 적용되는지는 도구 버전에 따라 달라지는 호환성 세부사항입니다. 모든 실행을 샌드박스가 없는 것으로 간주하고, 경계는 데몬 바깥에 두세요.

<Callout type="warning">
Multica는 파일 시스템 샌드박스를 제공하지 않습니다. 데몬을 개인 계정으로 실행 중이라면 실행이 SSH 키를 읽고, 셸 설정을 수정하고, 문서를 삭제할 수 있습니다. 격리는 데몬 바깥에 직접 마련해야 합니다.
</Callout>

이는 의도된 설계입니다. 에이전트는 의존성 설치, 빌드 실행, 클라우드 CLI 사용을 요구받으며, 이런 도구들은 정상적인 홈 디렉터리를 전제로 동작합니다. 불완전한 파일 시스템 샌드박스는 이런 작업을 진단하기 어려운 방식으로 망가뜨립니다(도구가 "로그인되지 않음"이라고 하거나, 조용히 잘못된 계정을 사용). 그러면서도 정작 가장 중요한 것은 보호하지 못합니다. 실행이 자격 증명을 읽어 네트워크로 내보내는 것은 막을 수 없기 때문입니다.

그래서 Multica는 스스로를 경계라고 주장하지 않습니다. 바깥에 경계를 두세요.

## 권장 구성

인프라에 맞는 것을 선택하세요. 가벼운 순서대로 나열했습니다:

1. **전용 Unix 사용자.** `multica` 사용자를 만들고 에이전트에 필요한 저장소와 자격 증명만 부여한 뒤 그 사용자로 데몬을 실행합니다. 본인 계정은 영향을 받지 않습니다.
2. **컨테이너.** 필요한 마운트와 시크릿만 제공한 컨테이너에서 데몬을 실행합니다.
3. **가상 머신.** 가장 강력한 격리이지만 머신을 따로 준비해야 합니다.

어떤 방식을 선택하든, 그 환경에서 접근 가능한 자격 증명은 에이전트가 사용할 수 있는 자격 증명으로 간주하세요. 토큰 권한은 최소로 좁히고, 개인 SSH 키 대신 용도별 배포 키를 사용하며, 무관한 프로덕션 자격 증명을 해당 사용자의 홈에 남겨두지 마세요.

## Multica가 실제로 격리하는 것

아래는 실제로 존재하는 격리이지만 편의성과 영향 범위 축소를 위한 것이며, 능동적으로 탈출을 시도하는 실행에 대한 보안 경계는 **아닙니다**:

- **실행별 작업 디렉터리.** 각 실행은 `~/multica_workspaces/` 아래에 전용 workdir를 가지므로 동시에 진행되는 실행이 같은 체크아웃에서 충돌하지 않습니다.
- **실행별 에이전트 상태.** Codex 실행은 설정, 세션, 스킬을 담는 실행 범위 `CODEX_HOME`을 가지므로 `~/.codex/`를 오염시키지 않습니다.
- **실행 범위 API 토큰.** 실행에 전달되는 `MULTICA_TOKEN`은 서버가 해당 에이전트와 실행에 바인딩하므로, 실행이 Multica API에서 사용자나 다른 에이전트로 행세할 수 없습니다.

## 경계가 아닌 것

- **코딩 도구 자체의 샌드박스와 승인 설정.** Multica는 에이전트를 무인으로 실행하므로 승인 요청은 자동 응답됩니다. 기본 경로에서는 파일 시스템 샌드박스도 꺼져 있어 Codex는 `sandbox_mode = "danger-full-access"`, Claude Code는 `--permission-mode bypassPermissions`로 동작합니다. 예외는 Windows입니다. Codex의 네이티브 샌드박스(`windows.sandbox = "unelevated"` 또는 `"elevated"`)를 명시적으로 설정하면 Multica는 그 옵트인을 존중해 해당 실행에 `workspace-write`를 유지합니다. 적용 가능한 환경에서는 권장하지만, 한 플랫폼의 한 도구에 국한된 이야기이며 데몬 사용자의 권한을 얼마나 좁혀야 하는지는 달라지지 않습니다.
- **`HOME` 디렉터리 구성.** 실행은 데몬 사용자의 실제 `HOME`과 `XDG_*` 변수를 그대로 상속합니다. 덕분에 `gh`, `aws`, `kubectl`, `gcloud`, `glab` 같은 호스트 CLI가 셸에서와 동일하게 실행 안에서도 동작합니다. 동시에 그 홈 아래의 모든 것에 접근할 수 있다는 뜻이기도 합니다.

<Callout>
Linux에서 Codex 실행은 이전에 `workspace-write` 샌드박스와 실행별로 리디렉션된 `HOME` 아래에서 실행되었습니다. 이 방식은 제거되었습니다. 호스트 CLI가 실행 안에서 미설정 상태가 되는 데다, 쓰기만 제한했기 때문에 자격 증명을 읽어 유출하는 것은 애초에 막지 못했기 때문입니다. 이제 Linux는 macOS 및 Windows의 기본 동작과 같습니다.
</Callout>

## 검토와 액션 인가

Multica는 **워크플로 신호**, **전달물 평가**, **액션 인가**를 구분합니다. 섞어 생각하면 존재하지 않는 잠금을 가정하게 됩니다.

| 신호 | 의미 | **하지 않는** 일 |
| --- | --- | --- |
| 보드 상태 `in_review`(또는 같은 카테고리의 커스텀 상태) | 결과가 사람의 관심을 기다리는 중 | 전달물 수락; 머지·배포 권한 부여; 코딩 도구 승인 다시 켜기 |
| 전달물 **수락** / **수정 요청** | 해당 스냅샷의 기준과 증거에 대한 사람 평가 기록 | GitHub/GitLab 머지 권한 변경; 배포; 도구 승인 프롬프트 복구 |
| 보드 상태 `done` | Multica 보드에서 범위가 닫힘(대개 사람 확인, 또는 Multica가 종료 의도가 있는 PR 머지를 관찰) | 프로덕션 배포 성공 증명 |

태스크를 `in_review`로 옮기면 Multica 안의 부작용만 있습니다: 오토파일럿 실행 마무리, 과거 "실행 실패" 알림 자동 보관. 그래도 머지·배포 권한은 되지 않습니다.

코딩 도구는 무인으로 실행됩니다. 승인 프롬프트는 자동 응답됩니다(기본 경로의 `bypassPermissions` / `danger-full-access` — [경계가 아닌 것](#경계가-아닌-것) 참고). Multica 검토 버튼은 이미 실행 중인 에이전트 프로세스에 그 프롬프트를 되돌릴 수 없습니다.

### Multica가 실제로 거부하는 경계

다음은 통제된 Multica 전선입니다 — 프롬프트도 보드 라벨도 아닙니다:

- **워크스페이스 멤버십** — 비멤버는 리소스를 읽거나 쓸 수 없습니다.
- **비공개 에이전트 호출** — 태스크를 볼 수 있다고 비공개 에이전트를 트리거할 권한(할당·멘션·재시도)이 생기지는 않습니다.
- **실행 범위 `MULTICA_TOKEN`** — 실행은 Multica API에서 사용자나 다른 에이전트로 행세할 수 없습니다.
- **전달물 검토 CAS** — 오래된 스냅샷이나 동시 검토는 충돌로 실패합니다. 머지를 잠금 해제하지 않습니다.
- **결정은 수신자만** — 구조화 결정 요청에 답할 수 있는 사람은 지정된 수신자뿐입니다.
- **CLI 인증은 인가된 운영자만** — 머신의 로그인/로그아웃 코드는 인가된 사람 운영자에게만 있습니다.
- **메모리 평가는 사람이 채택** — 오프라인/연결 평가 보고서는 사람 채택 경로 없이 메모리를 자동 승격하지 않습니다.

머지·배포를 강하게 막아야 한다면 VCS 호스트, 배포 자격 증명, 또는 외부 정책 엔진에 두고 데몬 사용자 환경 권한 밖의 제한된 ID를 쓰세요. Multica는 `in_review` 라벨로 그 경계를 만들지 않습니다.

## 실행에 실제 적용된 모드 확인하기

실행이 샌드박스 없이 시작되면 데몬이 warn 레벨 로그를 남깁니다:

```bash
multica daemon logs --lines 200 | grep "codex sandbox"
```

Codex의 실제 적용 설정을 확인하려면 해당 실행의 `CODEX_HOME` 아래 `config.toml`에 있는 관리 블록을 보세요. `# BEGIN multica-managed`와 `# END multica-managed` 사이의 내용은 실행할 때마다 데몬이 작성합니다.
