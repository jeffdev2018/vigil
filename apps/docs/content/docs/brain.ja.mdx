Brain は、ワークスペースが共有する短いノートの集まりです。下した決定とその理由、誰も書き残していない慣習、コードベースについての確かな事実、誰が何を担当しているか。

そこにあるものはすべて、エージェントのすべての実行に渡されます。それがこの仕組みの狙いです — デプロイ手順をすでに知っているエージェントは、それを改めて発見する必要も、来週また教えられる必要もありません。

## まず集めて、整理は後で

知識ベースを殺すのは摩擦です。何かを書き残すたびに、適切なタイトルとタグを考え、既存のどのノートに入れるかまで決めなければならないなら、人は一度やって二度とやりません。

そのため Brain は 2 つの半分に分かれています。

- **収集トレイ（Inbox）**は、残す価値のあるものをひと手間で受け取ります。1 行のテキスト、リンク、スクリーンショット、ボイスメモ、ファイル、TODO。タイトルもタグも判断も不要です。
- **ノート**は整理された側であり、実行が受け取るのはこちらだけです。

収集したもの（キャプチャ）は、誰かがそれをノートにする、すでに同じ主題を扱っているノートに統合する、あるいは破棄するまで、収集トレイにとどまります。誰の背後でも勝手に整理されることはなく、エージェントが集めたものは、誰かがそうすべきだと判断するまで他の実行に届きません。

間違ったキャプチャのコストはクリック 1 回です。間違ったノートは、その後のすべての実行に読まれます。

## 何を書くべきか

あるノートがここに置かれるに値するのは、次の実行のときにもまだ正しく、まだ役に立つ場合です。

良いノートの例:

- 「デプロイはリリースタグ経由で行う: `main` に `v0.x.x` を push する。`release.yml` がバイナリと Homebrew tap を公開する。」
- 「マイグレーションはトランザクションの外で実行する。そうすることで `CREATE INDEX CONCURRENTLY` が機能する。」
- 「デーモンは 5432 ではなく 6432 の pgbouncer 経由で Postgres に到達する。」

ノートではないもの:

- 実行が何をしたか。それは実行の出力です。
- 来週には誤りになるもの: ブランチ名、進行中の PR 番号、「ビルドが赤い」など。
- すでにリポジトリにあるもの — 二重に持つと、片方がもう片方からずれていきます。
- シークレット、トークン、認証情報。

1 つのノートには 1 つの事実だけ。タイトルには話題（`Deploys`）ではなく事実そのもの（`Deploys go through the release tag`）を書きます — タイトルは一覧で誰もが最初に目を通すものであり、エージェントがそのノートを開くかどうか決める前に読むものです。

収集トレイの基準は意図的に緩めてあります。まだ判断がついていないものこそ集めてください。判断は整理するときに下します。

## アプリでの操作

サイドバーで **Brain** を開きます。タブは 2 つあります。未整理のキャプチャ件数がバッジで示される **Inbox** と、**Notes** です。

### 収集トレイ

入力欄は Inbox の上部にあります。入力して Enter を押すだけです。同じ欄から TODO、添付またはページにドロップしたファイル、その場で録音したボイスメモも送れます。リンクだけのメッセージは、文章ではなくリンクとして扱われます。

各キャプチャのカードには、種類（テキスト、リンク、画像、ボイスメモ、ファイル、TODO）と出どころ（Web、デスクトップ、モバイル、CLI、MCP、チャットチャネル、エージェント、API）が表示されます。カードからできること:

- **ノートとして保存**すると、ノートが作られます。タイトルはキャプチャのタイトルヒント、次にその 1 行目が既定値になり、本文はキャプチャそのもの — リンク、テキスト、そしてファイル — が既定値になります。
- **ノートに統合**すると、選んだノートの末尾にキャプチャが追記され、そのタグがノートに追加されます。すでに同じ主題のノートがあるなら、これが正しい選択です。
- **破棄**すると何も作られません。破棄したキャプチャは専用のフィルタに残り、**再オープン**できます。
- **削除**はキャプチャを完全に消し、すでにノートが保持していない限りファイルも一緒に消します。破棄は取り消せますが、削除は取り消せません。

### ノート

- **検索**は関連度順です（後述）。タイトルと本文の両方が対象になります。
- **タグ**は絞り込み用のチップです。小文字化と重複排除が行われるため、`Deploy` と `deploy` は 1 つのタグとして扱われます。
- **ピン留め**すると、そのノートは古さに関係なくすべての実行に送られます。多用は禁物です — ピン留めしたノートは、最近のノートを押しのけてしまいます。
- 正しくなくなったノートは**アーカイブ**します。実行への送付とデフォルトの一覧からは外れますが、読むことはできます。
- **削除**は取り消せません。ワークスペースの管理者と、そのノートの作成者本人だけに許されています。

編集には楽観的並行性制御を使っています。開いている間に別の誰か — あるいは夜間のキュレーション処理 — がそのノートを変更していた場合、保存は拒否され、黙って上書きするのではなく再読み込みを求められます。

## どこから集められるか

収集トレイは 1 つのキューで、ワークスペースが存在するあらゆる場所から届きます。

| 経路 | 方法 |
| --- | --- |
| Web / デスクトップ | Brain の **Inbox** タブの入力欄。テキスト、TODO、添付またはドロップしたファイル、その場で録音するボイスメモ。 |
| iPhone | More の **Brain**。入力、リンクの共有、写真の撮影またはライブラリからの選択、ファイルの添付。アプリ内録音はありません — キーボードのマイクキーで音声入力でき、添付した音声ファイルは文字起こしされます。 |
| CLI | `multica brain capture`（後述）。 |
| MCP クライアント | `vigil_brain` ツールの `capture` アクション。この経路のキャプチャは出どころが **MCP** になり、クライアントが別の出どころを主張することはできません。 |
| チャットチャネル | Lark、Slack、WeCom、DingTalk、Telegram で `/capture <テキストまたはリンク>`。ボットが 1 行で確認を返すだけで、他には何も起きません — エージェントの応答もイシュー作成もありません。 |
| エージェント | ネイティブランタイムの `capture_note` ツール、および任意の実行からの `multica brain capture`。 |

どの経路でも、キャプチャは出どころが記録された状態で同じ収集トレイに入ります。電車で自分が入力したものと、エージェントが作業中に置いていったものを区別できます。

<Callout>
エージェントに与えられた取り決めは明確です。ノートにすべきか確信が持てないときは集める、確信があり、かつすでに検索したときだけノートとして保存する。「これは重要かもしれない」に対する誠実な答えがキャプチャです。
</Callout>

## 提案

ワークスペースに assist 層の LLM（`MULTICA_LLM_*`）が設定されていると、キャプチャが届いた直後に提案が付きます。タイトル、タグ、1 行の要約、そしてどう扱うか — 新しいノート、特定の既存ノートへの統合、あるいは破棄 — が理由付きで示されます。

提案はカード上の提案にとどまり、実行されることはありません。カードから、あるいは `multica brain suggest` で、いつでも作り直せます。モデルがない場合は提案が単に無効になるだけで、収集トレイの他の機能はまったく同じように動きます。

## 探し方

ノート検索は絞り込みではなく順位付けです。関連度の高い順に返り、それぞれにスコアと一致箇所のスニペットが付きます。

クエリは少しだけ構文を解釈します。

- `"引用したフレーズ"` — その語をその順序でまとめて。
- `-単語` — その語を含むノートを除外。
- `a OR b` — どちらか。

2 つのランカーが融合されます。1 つ目はタイトルと本文に対する語彙的なもの。2 つ目は意味的なもので、ワークスペースに埋め込みモデル（`MULTICA_LLM_EMBEDDING_MODEL`）が設定されていれば各ノートにベクトルも保持され、クエリの語に一致したノートが意味でも並べ替えられます — 検索 UI はその順位付けを **semantic** と示します。表示されるにはクエリと語を共有している必要があります。最も近いベクトルは、どのノートも答えないクエリにも必ず存在するためです。このモデルがない場合、検索は純粋に語彙的になり、その旨が表示されます。

ベクトルはノートの保存時と編集時に書かれます。10 分ごとのバックグラウンド処理が、ベクトルが欠けている・古い・別のモデル由来であるノートを最大 200 件ずつ追いかけます。障害やモデル変更のあとに検索を元通りにするのはこの処理で、手動での再取り込みは不要です。

## ボイスメモ

Web またはデスクトップで録音したボイスメモ — あるいはどこからでも添付した音声ファイル — は、サーバーに音声認識プロバイダー（`MULTICA_STT_BASE_URL`、`MULTICA_STT_API_KEY`、`MULTICA_STT_MODEL`、任意で `MULTICA_STT_LANGUAGE` のヒント）が設定されていれば文字起こしされます。カードには **文字起こし中…** と表示され、その後、文字起こし結果がキャプチャのテキストになります。これにより検索でき、他のキャプチャと同じように整理できます。音声そのものは添付されたまま残ります。

プロバイダーがない場合も録音は保存され、再生もできます。欠けるのは文字起こしだけで、カードにそう表示されます。

## 実行が受け取るもの

各実行は、ピン留めされたすべてのノートに加え、直近に更新された他のノート 20 件を、作業ディレクトリに書き込まれた状態で受け取ります:

```
.multica/knowledge/README.md        索引: タイトル、タグ、id、ファイル名
.multica/knowledge/<slug>-<id8>.md  ノート 1 件
```

実行のブリーフはノートを埋め込むのではなくこのディレクトリを指すため、Brain が大きくなってもプロンプトの費用は数行で済み、内容全体を抱えることはありません。合計は 200 KB が上限で、省かれたノートがある場合は索引がその件数を示します。

キャプチャは実行が受け取るものに**含まれません**。それは誰かの未整理の考えであり、実行がそれを読んで動くのは、まだ誰も保証していないものに基づいて動くことになります。

## エージェントも書き込む

エージェントは学んだことを CLI 経由で保存し、組み込みの `multica-workspace-brain` skill がいつ保存すべきかを教えます。

```bash
# 何かを探すとき: 関連度順、最良の一致が先頭
multica brain search "release tag" --output json
multica brain show <note-id>

# 探すのではなく眺めるとき
multica brain list --tag deploy

multica brain save \
  --title "Deploys go through the release tag" \
  --tags deploy,release \
  --content "Push v0.x.x on main; release.yml publishes the binaries."

# 長い本文はファイルから（`-` で標準入力から）
multica brain save --title "Scheduler leasing model" --tags backend --content-file ./note.md

# 重複させずに更新する
multica brain save --id <note-id> --content-file ./note.md

multica brain archive <note-id>
```

収集トレイ側:

```bash
multica brain capture "the daemon reaches Postgres through pgbouncer on 6432"
multica brain capture --url https://example.com/locking --title-hint "Locking article"
echo "a longer thought" | multica brain capture
multica brain capture --file ./whiteboard.png

multica brain inbox                            # 未整理のもの、新しい順
multica brain inbox --status all --limit 50
multica brain suggest <capture-id>

multica brain organize <capture-id> --as note --title "…" --tags deploy
multica brain organize <capture-id> --as merge --note <note-id>
multica brain organize <capture-id> --as discard
multica brain reopen <capture-id>
multica brain delete <capture-id> --yes
```

実行から保存されたノートは、保存したエージェントに帰属し、その実行にリンクされます。意外なノートを見つけたら、それを書いたものまで 1 クリックです。キャプチャも同じで、カードにエージェントとその実行が示されます。

<Callout>
この skill はエージェントに、保存の前に Brain を検索し、ほぼ重複するノートを足すのではなく該当するノートを更新するよう指示します。知識ベースを何よりも速く腐らせるのは重複です。
</Callout>

## 夜間のキュレーション

1 日 1 回、Brain に実際に変更があったワークスペースでキュレーション処理が走ります。コーパス全体を読み、次の計画を適用します:

- ほぼ重複するノートを、すでにそれを扱っているノートに**統合**する;
- タイトルが事実を述べていないノートを**改題**する;
- 同じ主題が同じタグを持つように**タグ付け**する;
- 誤りになった、置き換えられた、あるいはもともと持続的な知識ではなかったノートを**アーカイブ**する。

統合は履歴を残します。元のノートは、統合先を指すポインタとともにアーカイブされ、削除されることはありません。誤った統合は復旧できます。この処理がノートの本文を書き換えることはなく、事実を作り出すこともありません。

キュレーションには assist 層の LLM（`MULTICA_LLM_*`）が必要です。ない場合は何もせず、Brain の他の部分はまったく同じように動きます。この処理が収集トレイに触れることはありません — キャプチャの整理は人が決めることです。
