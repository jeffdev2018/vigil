**規範**はワークスペースの恒常的な規則です。ここでエージェントが何をしてよく何をしてはいけないか、仕事はどう届けられるか、人を介さずには決して起きないことは何か。ワークスペースのオーナーが書く 1 つの文書が、すべてのエージェントのブリーフに注入されます。ワークスペースコンテキストが大人になったもの — バージョン管理され、レビューでき、引用できます。

## どこに現れるか

すべての実行のブリーフは、課題やコメントより前に、`## Workspace Doctrine (revision N)` という見出しで規範を全文載せます。チャットの実行、課題の実行、自動化の実行、クイック作成の実行 — 同じ本文、同じリビジョンです。

ブリーフの他のブロックはすべてデータです — 課題の本文、コメント、Brain のノート、CRM のレコード。エージェントが*について*読むものです。規範はその逆で、指示そのものであり、ブリーフもそう明言します。規範は**あらゆるレコードより上位**です。コメントが規範の禁止することを認可することはできず、規範と矛盾するノートは例外ではなく古くなったノートです。規範と並ぶのはエージェント自身の[指示](/agents#エージェントの設定項目)だけです。

規範が覆さないのはプラットフォーム自身の拒否です — ワークスペースが禁じる[ステータス遷移](/issues)、しきい値を超える支出、承認ゲート。それらは変わらず有効です。

## 書き方

**設定 → 規範**にエディタ、リビジョン番号、履歴があります。公開できるのはワークスペースの `owner` と `admin` で、閲覧はすべてのメンバーができます。上限は **32 000 バイト** — ブリーフは規範を丸ごと運ぶので、数ページを超えて育った規範はすべての実行で代金を払っていることになります。

公開には自分が読んだリビジョン（`expected_revision`）が必要です。あなたが書いている間に誰かが公開していた場合、書き込みはマージされるのではなく拒否されます。読み直してから、もう一度公開してください。

<Callout title="入口は 2 つ、台帳は 1 つ">
`multica workspace update --context` は今も動作し、抜け道ではありません。同じ台帳を通り、同じ監査エントリを残して規範のリビジョンを公開します。
</Callout>

## 第二のレビュアー

**設定 → 規範 → 第二のレビュアーを必須にする**を有効にすると、公開は提案になります。本文はライブにならず**保留中**として登録され、他のオーナーと管理者に `doctrine_review` のインボックス項目が届き、そのうちの 1 人が承認または却下します。承認されればライブのリビジョンになり、却下されれば規範はそのままで、レビュアーのメモが記録に残ります。

オーナーまたは管理者が 1 人だけのワークスペースは自己承認します — そうでなければこの設定を入れた時点で規範が凍結してしまいます。保留中の提案は一度に 1 つだけです。次を公開する前に承認または却下してください。

## 履歴、差分、復元

すべてのバージョンが保持されます。本文、書いた人、メモ、レビューした人、そして `active` / `pending` / `rejected` / `superseded` のどれであるか。履歴は新しい順にページングされます。

**差分**は任意の 2 つのバージョンを行単位で比較します — 追加、削除、変更なし。相手を指定せずに尋ねた場合、保留中または却下された提案はライブの規範と比較され、有効化されたリビジョンはその 1 つ前のリビジョンと比較されます。

**復元**は過去のリビジョンの本文を*新しい*リビジョンとして公開し直します（どのリビジョンから来たかは台帳に記録されます）。他の公開と同じレビュー方針を通り、その場で書き換えられるものは何もありません。

## 報告 — 規則に従えないとき

壁に当たったエージェントは、その場で解釈を作らず、黙って作業を続けることもしません。**規範レポート**を提出します。

| 種別 | 意味 |
| --- | --- |
| `refusal` | 規則を破らなければ作業を完了できない。 |
| `conflict` | 2 つの規則が同時に適用され、両方には従えない。 |
| `ambiguity` | 規則は存在するが、行動するには内容が足りない。 |

レポートには要約、任意で問題になっている箇所の引用、由来する実行と課題、そして**エージェントが動いていたリビジョン**が載ります。後で規範が編集されても、レポートは当時の本文に対して正しく読めます。メンバーも提出できます。

各レポートは `doctrine_report` のインボックス項目とプッシュとして、すべてのオーナーと管理者に届きます。オーナーはそれを**承認**（実在する問題であり対処中）するか**棄却**（規範は書かれたとおりで正しい）し、どちらの場合もメモを添えます。レポート自体は何も変えません。統治文書に人の判断が必要だという合図であって、その実行で規則を免除してもらう手段ではありません。

## ツールと CLI

- ネイティブランタイム: `report_doctrine_conflict` — 実行の効果的な予算の外にあるので、予算を使い切った実行でも規則に阻まれたことを伝えられます。
- MCP: `vigil_doctrine`（アクション `get`、`versions`、`report`）。公開、承認、復元は意図的に公開されていません — 実行が自分を縛る規則を書き換えることはできません。
- CLI: `multica doctrine show | publish | history | diff | approve | reject | restore | report | reports | acknowledge | dismiss`。

```bash
multica doctrine show
multica doctrine publish --file DOCTRINE.md --expected-revision 7 --note "adds the release rule"
multica doctrine diff <version-id>
multica doctrine reports --status open
```

## API

- `GET /api/workspace/doctrine` → 本文、リビジョン、`byte_limit`、`require_review`、`can_publish`、保留中のバージョン、未対応レポート数。
- `PUT /api/workspace/doctrine {content, expected_revision, note?}` → `200` 公開、`202` レビュー保留、`409` 古いか提案がすでに保留中。
- `GET /api/workspace/doctrine/versions?cursor&limit`、`GET .../versions/{id}`、`GET .../versions/{id}/diff?against={id}`。
- `POST .../versions/{id}/approve | reject | restore`。
- `GET .../reports?status=open|acknowledged|dismissed|all`、`POST .../reports {kind, summary, passage?, issue_id?}`、`POST .../reports/{id}/acknowledge | dismiss`。
- 監査アクション `doctrine.published`、`proposed`、`approved`、`rejected`、`reported`、`report_resolved`。インボックスタイプ `doctrine_review` と `doctrine_report`。`doctrine:changed` イベントが開いているページを最新に保ちます。
