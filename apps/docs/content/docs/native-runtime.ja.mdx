すべてのワークスペースには 1 つの**ネイティブランタイム**があります。これは、エージェントのツール呼び出しループを Multica API プロセスの内部で直接実行する、サーバー内実行パスです。[デーモン](/daemon-runtimes)も、接続されたコンピュータも、AI コーディングツールの CLI も必要ありません。

## デーモンランタイムより優先すべき場面

デーモンランタイムは、チェックアウト済みのリポジトリに対して実際の AI コーディングツール（Claude Code、Codex など）を、フルのファイルシステムとシェルアクセス付きで動かします。ネイティブランタイムはどちらも行いません。読み書きできるのは、課題に限定された小さく固定されたツールセットだけです（下記参照）。リポジトリのチェックアウトやシェルアクセスを必要としない、軽量な課題のトリアージ、ステータス変更、コメント対応に選んでください。コーディング作業はデーモンランタイムに残してください。

デーモンも CLI のインストールも不要なため、ネイティブランタイムは常に利用可能で、CLI バージョンが表示されることもありません。ネイティブランタイムに紐づいたエージェントは、ワークスペースが存在した瞬間から準備完了です。

## 実行のしくみ

ネイティブランタイムはワークスペースごとに 1 件の `agent_runtime` 行を登録し（`runtime_mode = 'native'`、プロバイダーは `native`）、他のランタイムと同じようにランタイムのピッカーや一覧に表示されます。今のところ UI 上で特別扱いされる表示はありません。

`native_agent_tick` というスケジュールジョブが 10 秒ごとに実行され、各ワークスペースのネイティブランタイムについて、デーモンのポーリングと同じ選定経路を通じてキュー済みの実行を取得します。取得した各実行は、ティック自体とは独立した専用の goroutine 内で、10 分のタイムアウト付きで実行されます。1 回の実行の中で、ツール呼び出しループは最大 12 ターンに制限され、各ツール結果はモデルへ返す前に 8&nbsp;KB に制限されます。

<Callout type="info">
ネイティブランタイムは、サーバー上の全ワークスペースを通じて 8 実行というグローバルな同時実行上限を共有します。ワークスペースごとの上限ではありません。
</Callout>

## ネイティブツール

ツール呼び出しループが呼び出せるのは、意図的に閉じられた小さなツールセットだけです。

| ツール | 内容 |
|---|---|
| `get_issue` | 課題とその直近のコメントを読み取ります（デフォルトはその実行自身の課題）。 |
| `list_issues` | ステータスと優先度で絞り込みながら課題を一覧表示します。一度に最大 50 件まで。 |
| `add_comment` | エージェントとして署名されたコメントを投稿します。 |
| `update_issue` | タイトル、説明、優先度を更新します — ステータスは対象外で、そちらは `transition_issue` を使います。 |
| `transition_issue` | UI と同じゲート付きの経路で課題のステータスを変更します。 |
| `create_sub_issue` | 実行対象の課題の下にサブ課題を作成します。 |
| `create_issue` | 新しいトップレベルの課題を作成します。デフォルトではエージェント自身に割り当てられます。 |

モデルが渡す課題 ID は、使用前に必ず実行のワークスペースに対して再検証されます。ツールがモデルの出力だけを信頼して課題参照を扱うことはありません。

## ガードレール

- **ゲート付きのステータス遷移。** `transition_issue` は HTTP ハンドラーが使うのと同じ遷移ルール判定を、エージェントを行為者として通ります — エージェントはワークスペースのロールを一切持たないため、owner や admin の遷移権限を継承することはできません。ワークスペースのルールに応じて、変更は即座に適用されるか、理由付きでモデルに拒否が返されるか、ステータスを変えないまま承認待ちとして保留されます。
- **作成時の暗黙のステータス変更なし。** `create_issue` と `create_sub_issue` は常にデフォルトのステータスで課題を作成し、ワークスペースのルールがゲートするようなステータスに直接着地させることはありません。作成後の遷移はすべて引き続き `transition_issue` を通ります。
- **自己誘発の実行ループなし。** `create_issue` は、自分が作成した課題に対して実行をキューに入れることはありません。そのため、ネイティブ実行が自分自身をただちに再トリガーする作業を連鎖的に作り出すことはありません。
- **予算はステータスで終わり、打ち切りにはしません。** 最終ターン、および予算を使い切った後の最初のターン（1 回の実行につき状態を変更するツール呼び出し 10 回まで）は、まとめのターンです。ツールは提供されず、モデルには何をしたか、何が残っているか、何が妨げになったかという短いクロージングステータスが求められます。そのステータスが実行の最終回答になります。
- **同一の呼び出しは拒否されます。** 同じツールを同じ引数で呼び出すと、3 回目で警告、5 回目で拒否となり、まとめのターンに入ります。

## 長時間タスク：ゴールループ

課題に対する 1 回の実行だけで、課題が完了することはめったにありません。課題への実行が完了すると——ネイティブランタイムでもデーモンランタイムでも同様に——サーバーはツールを使わない 2 つ目の質問をモデルに投げます。クロージングステータスは課題のゴールを満たしているか、という質問です。ゴールとは、メンバーが課題のゴールカードに書いた完了の定義、それがなければ課題のタイトル・説明・受け入れ基準です。回答は型付きで、`satisfied`、または `goal_not_met_yet`、`missing_evidence`、`needs_user_input`、`run_failed`、`external_wait` のいずれかであり、根拠の一文と次のステップの提案が添えられます。これは実行のトランスクリプトに `Goal check` の行として残り、実行結果の `goal_loop` の下に、そして課題のゴール状態にも反映されます。

- `goal_not_met_yet` と `missing_evidence` は、同じ課題への次の実行を前回の**継続**として実行キューに入れます。前回のステータスと妨げになった点を伝える引き継ぎメモが添えられ、最初の実行から数えて最大 8 回まで継続できます。後続の実行はプロンプトの中でゴール状態——ゴール、反復回数、妨げになった点、次のステップ、これまでに集まった根拠——を読み取ります。
- 連続する 2 回の継続が同じステータスで終わると、停滞とみなしてチェーンを止めます。
- `satisfied` は、エージェントを行為者としてワークスペースの遷移ルールを通じて課題を完了に移動します。承認を必要とするルールがある場合は、代わりに承認リクエストが作成されます。設定で `propose_done: false` にすると、課題を移動せずに判定結果だけを記録します。
- `needs_user_input`——または、エージェント自身が使う `ask_user` ツール（CLI の実行では `POST /api/issues/{id}/goal/question`）——は、その課題に責任を持つ人向けの受信箱アイテムと、質問とその選択肢を記載したコメントを作成します。チェーンはここで待機し、ゴールカードでの回答があると、それを添えて後続の実行がキューに入ります。
- `external_wait` と `run_failed` はチェーンを止め、コメントを投稿します。次のステップは人間側にあるためです。
- 実行が進行中の課題を人間が再割り当てしたりクローズしたりすると、チェーンは止まります。人間が起点となる実行（コメント、新しい割り当てなど）は新しいチェーンを開始します。

この状態はメモリ上ではなく課題自体に保存されます（`GET /api/issues/{id}/goal`）。2 回の実行の間にサーバーが再起動しても失われません。メンバーはゴールとその上限を書き込み（`PUT`）、チェーンを一時停止・再開し（`POST .../pause`、`.../resume`）、質問に回答できます（`POST .../answer`）。ワークスペース設定の `goal_loop` は `max_continuations`（最大 20、`0` で判定をオフ）と `propose_done` を保持します。

## LLM の要件

ネイティブランタイムは、[チャットの自動タイトル付けとフォローアップ支援レイヤー](/environment-variables#サーバーサイド-llm)と同じサーバーサイド LLM クライアントを呼び出します。`MULTICA_LLM_API_KEY` または `MULTICA_LLM_BASE_URL` の設定が必要です。設定がない場合、ティックは何もしません — ネイティブランタイム上のキュー済み実行は、エラーも出ないままこのレイヤーが有効になるまで単に待機し続けます。
