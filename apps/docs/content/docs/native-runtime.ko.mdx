모든 워크스페이스에는 **네이티브 런타임**이 하나 있습니다 — Multica API 프로세스 안에서 에이전트의 도구 호출 루프를 직접 실행하는 서버 내장 실행 경로입니다. [데몬](/daemon-runtimes), 연결된 컴퓨터, AI 코딩 도구 CLI가 전혀 필요하지 않습니다.

## 데몬 런타임 대신 선택하는 경우

데몬 런타임은 checkout된 저장소를 대상으로 실제 AI 코딩 도구(Claude Code, Codex 등)를 구동하며 전체 파일시스템과 셸 접근 권한을 가집니다. 네이티브 런타임은 둘 다 사용하지 않습니다 — 이슈에 한정된 작고 고정된 도구 집합(아래 참고)을 통해서만 읽고 쓸 수 있습니다. 저장소 checkout이나 셸 접근이 필요 없는 가벼운 이슈 분류, 상태 변경, 댓글 작업에는 이를 선택하고 코딩 작업은 데몬 런타임에 맡기세요.

데몬도 없고 설치할 CLI도 없기 때문에 네이티브 런타임은 항상 사용할 수 있으며 CLI 버전을 표시하지 않습니다 — 여기에 연결된 에이전트는 워크스페이스가 생성되는 순간 바로 준비됩니다.

## 실행 방식

네이티브 런타임은 워크스페이스마다 `agent_runtime` 행을 하나씩 생성하며(`runtime_mode = 'native'`, provider `native`), 다른 런타임과 마찬가지로 런타임 선택기와 목록에 나타납니다 — 오늘 기준으로 UI가 이를 특별히 표시하는 요소는 없습니다.

예약 작업인 `native_agent_tick`은 10초마다 실행되며, 각 워크스페이스의 네이티브 런타임에 대해 데몬 폴링이 사용하는 것과 같은 적격성 경로를 통해 큐에 있는 실행을 가져갑니다. 가져온 각 실행은 tick 자체와 독립적으로 10분 타임아웃을 가진 자체 goroutine에서 실행됩니다. 실행 안에서 도구 호출 루프는 최대 12턴으로 제한되며, 각 도구 결과는 모델에 돌아가기 전에 8&nbsp;KB로 제한됩니다.

<Callout type="info">
네이티브 런타임은 워크스페이스별 제한이 아니라 서버의 모든 워크스페이스에 걸쳐 공유되는 전역 동시 실행 상한 8개를 사용합니다.
</Callout>

## 네이티브 도구

도구 호출 루프는 의도적으로 제한된 작고 고정된 도구 집합만 호출할 수 있습니다.

| 도구 | 하는 일 |
|---|---|
| `get_issue` | 이슈와 최근 댓글을 읽습니다(기본값은 실행 자신의 이슈). |
| `list_issues` | 이슈 목록을 조회하며 상태와 우선순위로 필터링할 수 있고 한 번에 최대 50개까지 가져옵니다. |
| `add_comment` | 에이전트 명의로 서명된 댓글을 작성합니다. |
| `update_issue` | 제목, 설명, 우선순위를 수정합니다 — 상태는 대상이 아니며 상태 변경에는 `transition_issue`를 사용하세요. |
| `transition_issue` | UI와 동일한 게이트 경로를 통해 이슈 상태를 변경합니다. |
| `create_sub_issue` | 실행의 이슈 아래에 하위 이슈를 만듭니다. |
| `create_issue` | 새 최상위 이슈를 만들며 기본적으로 에이전트 자신에게 할당됩니다. |

모델이 제공하는 모든 이슈 ID는 사용 전에 실행의 워크스페이스를 기준으로 다시 검증됩니다 — 도구는 모델 출력만으로 이슈 참조를 신뢰하지 않습니다.

## 가드레일

- **게이트가 적용된 상태 전환.** `transition_issue`는 HTTP 핸들러가 사용하는 것과 동일한 전환 규칙 판단을 거치며, 행위자는 에이전트입니다 — 에이전트는 워크스페이스 역할을 갖지 않으므로 owner나 admin의 전환 권한을 물려받을 수 없습니다. 워크스페이스의 규칙에 따라 전환은 즉시 적용되거나, 사유와 함께 모델에 거부되어 반환되거나, 상태는 그대로 유지된 채 승인 대기 요청으로 보류됩니다.
- **생성 시 상태를 몰래 바꾸지 않습니다.** `create_issue`와 `create_sub_issue`는 항상 이슈를 기본 상태로 생성하며, 워크스페이스 규칙이 게이트로 막을 상태로 곧바로 이동시키지 않습니다. 생성 이후의 모든 전환은 여전히 `transition_issue`를 거칩니다.
- **스스로를 재트리거하는 실행 루프가 없습니다.** `create_issue`는 자신이 만든 이슈에 대해 실행을 큐에 넣지 않으므로, 네이티브 실행이 자신을 즉시 다시 트리거하는 작업을 연쇄적으로 만들어낼 수 없습니다.
- **예산은 상태로 끝나지, 중간에 끊기지 않습니다.** 마지막 턴과 예산 소진(실행당 상태를 변경하는 도구 호출 10회) 이후 첫 턴은 마무리 턴입니다: 도구는 제공되지 않고 모델에게는 무엇을 했는지, 무엇이 남았는지, 무엇에 막혔는지를 담은 짧은 마감 상태가 요청됩니다. 그 상태가 해당 실행의 최종 답변이 됩니다.
- **동일한 호출은 거부됩니다.** 같은 인자로 같은 도구를 호출하면 세 번째 호출에서 경고를, 다섯 번째 호출에서 거부를 받으며 마무리 턴이 트리거됩니다.

## 장기 작업: 목표 루프

이슈에 대한 한 번의 실행으로 이슈가 끝나는 경우는 드뭅니다. 이슈에 대한 실행이 종료되면 — 네이티브 런타임이든 데몬 런타임이든 마찬가지로 — 서버는 도구 없이 모델에게 두 번째 질문을 던집니다: 마감 상태가 이슈의 목표를 충족하는가? 목표는 멤버가 이슈의 목표 카드에 작성한 완료의 정의이며, 없다면 이슈의 제목, 설명, 인수 조건입니다. 답변은 타입이 지정되어 있습니다 — `satisfied`, 또는 `goal_not_met_yet`, `missing_evidence`, `needs_user_input`, `run_failed`, `external_wait` 중 하나 — 근거 한 줄과 제안된 다음 단계가 함께 붙습니다. 이는 실행 기록에 `Goal check` 줄로, 실행 결과에는 `goal_loop` 아래에, 그리고 이슈의 목표 상태에 남습니다.

- `goal_not_met_yet`와 `missing_evidence`는 같은 이슈에 대한 다음 실행을 이전 실행의 **연속** 구간으로 큐에 넣습니다. 이전 상태와 막힌 지점을 담은 인계 메모가 함께 전달되며, 첫 실행 이후 최대 8번까지 이어질 수 있습니다. 후속 실행은 프롬프트에서 목표 상태 — 목표, 반복 횟수, 막힌 지점, 다음 단계, 지금까지 모은 근거 — 를 읽습니다.
- 연속으로 두 번 이어진 실행이 같은 상태로 끝나면 정체로 간주해 체인을 멈춥니다.
- `satisfied`는 에이전트를 행위자로 하여 워크스페이스의 전환 규칙을 거쳐 이슈를 done으로 이동시킵니다: 승인이 필요한 규칙이 있다면 대신 승인 요청을 제출합니다. 설정의 `propose_done: false`는 이슈를 이동하지 않고 판정 결과만 기록합니다.
- `needs_user_input` — 또는 에이전트 자체의 `ask_user` 도구(CLI 실행의 경우 `POST /api/issues/{id}/goal/question`) — 는 해당 이슈를 책임지는 사람들에게 인박스 항목을 생성하고, 질문과 선택지를 담은 댓글을 남깁니다. 체인은 여기서 대기하며, 목표 카드에 답변이 달리면 그 답변과 함께 후속 실행을 큐에 넣습니다.
- `external_wait`와 `run_failed`는 체인을 멈추고 댓글을 남깁니다. 다음 단계는 사람의 몫이기 때문입니다.
- 실행이 진행 중인 동안 사람이 이슈를 재할당하거나 닫으면 체인이 멈춥니다. 사람이 유발한 실행(댓글, 새 할당)은 새로운 체인을 시작합니다.

이 상태는 메모리가 아니라 이슈에 저장됩니다(`GET /api/issues/{id}/goal`): 두 실행 사이에 서버가 재시작되어도 아무것도 사라지지 않습니다. 멤버는 목표와 그 상한을 작성하고(`PUT`), 체인을 일시 중지·재개하며(`POST .../pause`, `.../resume`) 질문에 답합니다(`POST .../answer`). 워크스페이스 설정 `goal_loop`는 `max_continuations`(최대 20, `0`이면 판정을 끔)와 `propose_done`을 가집니다.

## LLM 요구 사항

네이티브 런타임은 [채팅 제목 자동 생성과 후속 질문 레이어](/environment-variables#서버-측-llm)와 같은 서버 측 LLM client를 호출합니다. `MULTICA_LLM_API_KEY` 또는 `MULTICA_LLM_BASE_URL`이 설정되어 있어야 합니다. 설정하지 않으면 tick은 아무 동작도 하지 않습니다 — 네이티브 런타임에 큐로 들어온 실행은 오류 없이 이 레이어가 활성화될 때까지 그냥 대기합니다.
