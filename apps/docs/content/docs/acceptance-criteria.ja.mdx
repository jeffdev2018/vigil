説明は課題が何を望むかを述べますが、受け入れ基準は誰か — 人でもエージェントでも — がそれが実際に起きたことをどう確認するかを述べます。各基準は自分自身の証拠を持ち、いずれかが証拠を満たしていない間、サーバーは課題を `done` へ移すことを拒否します。誰かが読むのを忘れないよう管理するチェックリストではなく、課題自身が自分を縛る契約です。

## 証拠の種類

| 種類 | 何を示すか | `satisfied` になる条件 |
| --- | --- | --- |
| `test` | テストコマンド | コマンドが記録される（サーバーは結果を再実行しない） |
| `file` | パス | パスが記録される |
| `screenshot` | 画像へのパスまたは URL | 参照が記録される |
| `url` | リンク | リンクが記録される |
| `human_validation` | 何も指定しない — 本人のクリックそのもの | メンバーが「自分で確認済みにする」をクリックする |

`test`・`file`・`screenshot`・`url` はすべて同じ仕組みです。それを添付した人 — 多くの場合その作業をしたエージェント — が参照そのものについて信頼されます。サーバーはテストを実行したり URL を取得したりしません。`human_validation` は意図的に異なります。エージェントが要求することはできますが、それだけでは `pending_human` にしかなりません。証拠が存在するのはメンバー自身がクリックしたときだけで、機械しか見ていない基準が証明済みを名乗ることはできません。

## 証拠の状態

| 状態 | 意味 |
| --- | --- |
| `missing` | まだ証拠が添付されていない。 |
| `pending_human` | `human_validation` の証拠が要求されているが、まだ誰もクリックしていない。 |
| `satisfied` | 有効な証拠を持つ基準。 |

## 管理する場所

課題の**受け入れ基準**セクションには、各基準がその状態（点・時計・チェック）と、あればその証拠とともに並びます。ここから次のことができます。

- **追加** — 基準を 1 件ずつインラインで入力する。
- **証拠を添付** — 種類（`test`、`file`、`screenshot`、`url`）を選び、参照を入力する。
- **自分で確認済みにする** — `human_validation` のショートカット。クリックできるのはメンバーのみで、これ 1 回の操作で証拠の要求と充足の両方を行う。
- **削除** — 基準を削除する。

<Callout type="info">
基準の言い直しはリセットされます。id が一致する（または id がない場合は元のテキストと完全に一致する）場合にのみ証拠が保持されます。テキストを変えると `missing` からやり直しになります — 読み方が変わった約束は新しい約束です。
</Callout>

## `done` をブロックする

課題を（1 件ずつでもバッチでも）カテゴリが `done` であるステータスへ移そうとする操作は、いずれかの基準がまだ証拠を満たしていない間 `409 unsatisfied_acceptance_criteria` で拒否されます。これは組み込みの `done` だけでなく、`done` カテゴリに属するすべてのステータス（[カスタムステータス](/issues#カスタムステータス)を参照）に適用されます。拒否には証拠が足りない基準がすべて列挙されるため、その応答だけで何が足りないか分かります。

Observer の信頼モードのエージェントは証拠を添付したり主張したりできません — コメントと提案のみで、これは課題の他の部分に対する Observer モードの制約と同じです。

## CLI

```bash
multica criteria list <issue-id>
multica criteria set <issue-id> --text "Safari でチェックアウトが成功する" --text "新しいコンソールエラーがない"
multica criteria prove <issue-id> <criterion-id> --type test --ref "go test ./checkout/..."
multica criteria prove <issue-id> <criterion-id> --type human_validation
```

`criteria set` はリスト全体を置き換えます — `--text` は繰り返し指定でき、基準ごとに 1 つ、順番どおりです。テキストが変わっていない基準は証拠を保持し、言い直した基準は上記のルールどおり証拠なしから始まります。

## API

| メソッド | ルート | アクター | ボディ |
| --- | --- | --- | --- |
| `GET` | `/api/issues/{id}/acceptance-criteria` | メンバー | — |
| `PUT` | `/api/issues/{id}/acceptance-criteria` | メンバー | `{criteria: [{id?, text}]}` |
| `PATCH` | `/api/issues/{id}/acceptance-criteria/{criterionId}/proof` | エージェントまたはメンバー | `{proof_type, proof_ref?}` — `proof_type` を空にすると証拠がクリアされる |

## 制限

- 課題あたり最大 50 件の基準、各基準のテキストは最大 2 KB。
- 証拠の参照（`proof_ref`）は最大 2 KB で、`human_validation` を除くすべての `proof_type` で必須です。
