Multica は作業の記録と調整を担い、接続されたコンピュータが実行を担います。コンピュータ上の**デーモン**（daemon）が実行を取得し、そのマシンにインストールされた AI コーディングツールを呼び出します。

## デーモンとランタイムの違い

- **デーモン**は、1 台のコンピュータで動く Multica のバックグラウンドプロセスです。サーバーへの接続、ローカルツールの検出、実行の取得、結果の報告を担当します。
- **ランタイム**は、ワークスペースが利用できる 1 つの具体的な実行環境を表します。1 台のコンピュータと、そのコンピュータ上の 1 つの AI コーディングツール（またはカスタムランタイムプロファイル）の組み合わせに対応します。

たとえば、Claude Code と Codex の両方をインストールした 1 台のコンピュータが、2 つのワークスペースに接続しているとします。デーモンはそれぞれのワークスペースに Claude Code と Codex のランタイムを登録します。デーモンを再起動すると既存のレコードが更新されるだけで、同じ組み合わせに対して新しいランタイムが増え続けることはありません。

## 実行場所とデータ境界

ローカルランタイムが呼び出す AI コーディングツール、それらのツール自身のログイン認証情報、ローカルのコードディレクトリは、いずれも接続されたコンピュータに残ります。Multica サーバーがローカルツールの代わりにコマンドを実行することはなく、作業ディレクトリ全体を自動でアップロードすることもありません。

チームが協働できるように、サーバーはタスク、コメント、エージェント設定、実行のコンテキスト、実行記録、エージェントが書き戻した結果を保存します。これらには、エージェントが自ら読み取って返信に含めたコードスニペットやその他のプロジェクトコンテキストが含まれることがあります。

<Callout type="warning">
エージェントのカスタム環境変数はサーバー側に保存され、実行時にランタイムへ送られます。「ローカル実行」を「すべてのシークレットがこのマシンにしか存在しない」と読み替えないでください。カスタム環境変数と MCP 設定はサーバー側にあり、その表示は機密値のルールによって制限されます。
</Callout>

## デーモンの起動

Multica Desktop を使う場合、アプリがデーモンを自動的に起動するため、追加のコマンドは不要です。

Web、リモートのコンピュータ、ヘッドレス環境では、先に [Multica CLI をインストール](/cli)してから実行します。

```bash
multica daemon start
```

デーモンはデフォルトでバックグラウンドで動きます。よく使うコマンド:

| コマンド | 役割 |
| --- | --- |
| `multica daemon status` | デーモンと接続の状態を表示する |
| `multica daemon logs -f` | ログを追跡表示する |
| `multica daemon restart` | デーモンを再起動し、ローカルツールを再検出する |
| `multica daemon stop` | デーモンを停止する |
| `multica daemon start --foreground` | デバッグ用に現在のターミナルで実行する |

実行用の作業ディレクトリを別のディスクに置くには、`multica config set workspaces_root <path>` で現在のプロファイルにルートを保存するか、`daemon start` または `daemon restart` に `--workspaces-root <path>` を渡します。フラグは `MULTICA_WORKSPACES_ROOT` より優先され、環境変数はプロファイル設定より優先されます。ルートを変更しても既存の実行ディレクトリは移動されません。

起動時、デーモンは `PATH` 上の対応する AI コーディングツールを検出し、あなたが接続を許可されているワークスペースにランタイムを登録します。ツールをインストールまたはログインした直後の場合は、デーモンを再起動すると再検出されます。

デーモンは、組み込みで対応している AI コーディングツールを少なくとも 1 つ検出できないと起動しません。インストール方法と実行コマンド名は [AI コーディングツールのインストール](/install-agent-runtime)を参照してください。

## ディスパッチとオンライン状態

登録されたランタイムは接続を維持し続けます。新しい実行がキューに入ると、サーバーは対応するデーモンに通知します。デーモン側も定期的にポーリングし、接続断のあとの補完として機能します。そのため、ランタイムがオンラインで空き容量があれば、実行は通常すぐに開始されます。

デーモンは 15 秒ごとにハートビートを送ります。サーバーはハートビートと接続状態を組み合わせてランタイムのオンラインを判定し、デーモンが予期せず終了した場合、通常は遅くとも約 3 分以内にオフラインと表示されます。

![オンラインのコンピュータ 1 台のランタイム詳細: 同じデーモンが 7 個のランタイムを登録し、検出された AI コーディングツールごとに 1 行、いずれもオンライン状態と CLI バージョンを表示している](/images/docs/runtime-machine-detail.webp)

ランタイムがオフラインのとき:

- キュー済みの実行はランタイムの復帰を待ちます。失敗するのは、そのランタイムが再接続猶予を超えてハートビートを停止し、**かつ**実行自身も同じ時間キューで待った場合のみです。したがって単に取り込み中のランタイムは滞留分を保持し続け、すでにオフラインのランタイムに割り当てられた実行にも猶予がまるまる 1 回分残ります。
- 進行中だった実行は失敗します。条件を満たすタスクまたはチャットの実行は自動リトライできます。
- デーモンが再起動すると、ランタイムを再登録し、前回正常に終了しなかった実行を回収します。
- 7 日を超えてオフラインで、（アーカイブ済みを含め）どのエージェントにも紐づいていないランタイムは、自動的にクリーンアップされます。

詳細な状態とリトライのルールは[実行](/tasks)を参照してください。

## 同時実行の上限

1 つのデーモンはデフォルトで最大 20 件の実行を同時に処理します。各エージェントはデフォルトで最大 6 件です。実効的な同時実行数は両者の小さい方になります。

上限に達すると、新しい実行はキューで待ち続けます。個々のエージェントの同時実行数はエージェント設定で、マシン全体の上限は `MULTICA_DAEMON_MAX_CONCURRENT_TASKS` で調整できます。並列実行は、マシンの性能、ツールアカウントのクォータ、同じ作業ディレクトリを同時に取り合います。

## プライベートと公開

ローカルランタイムはデフォルトで**プライベート**です。その上にエージェントを作成できるのはランタイムの所有者だけで、ワークスペースの owner・admin も例外ではありません。ランタイムは他のメンバーのコンピュータであり、そこでエージェントを動かすことはそのメンバーのマシンとツール認証情報を消費するためです。

ランタイムを**公開**に変更できるのは所有者だけです。ワークスペースの管理者はランタイムの名前変更や削除はできますが、共有するかどうかは所有者が決めます。公開すると、ワークスペースの他のメンバーもこのランタイムを選べるようになります。これは基盤の AI コーディングツールのログイン認証情報を共有するものではなく、メンバーがエージェントの実行をこのコンピュータにルーティングできるようになるだけです。

## カスタムランタイムプロファイル

チームで社内 wrapper やバージョン固定の実行ファイルを使う場合、あるいは互換ツールに固定引数を追加したい場合は、**カスタムランタイムプロファイル**を作成できます。

カスタムプロファイルが新しい通信プロトコルを追加することはありません。作成時には、Multica がすでに対応しているプロトコルファミリー（ツールの連携プロトコルの種類。[AI コーディングツール対照表](/providers)を参照）を選ぶ必要があり、コマンド自体がそのプロトコルファミリーと互換でなければなりません。

### 作業ランタイム環境

デーモンがエージェントの作業を開始すると、作業コンテキストをランタイムプロセスに注入します。これらの値はデーモンが管理するため、エージェントのカスタム環境では `MULTICA_` 変数や作業用一時ディレクトリ変数を上書きできません。

次の表は、カスタムランタイムが現在利用できる変数を示しています。完全な一覧ではなく、バージョン保証された API でもありません。連携処理では**連携契約**と記載された 5 つの変数だけを使用してください。それ以外は参考情報であり、今後変更される可能性があります。

| 変数 | 作業内の値 | 安定性 |
| --- | --- | --- |
| `MULTICA_TOKEN` | 作業スコープの `mat_` API 認証情報 | **連携契約** |
| `MULTICA_TASK_ID` | 実行中の作業の ID | **連携契約** |
| `MULTICA_AGENT_ID` | 割り当てられたエージェントの ID | **連携契約** |
| `MULTICA_WORKSPACE_ID` | 作業が属するワークスペースの ID | **連携契約** |
| `MULTICA_SERVER_URL` | デーモンが選択した Multica サーバー URL | **連携契約** |
| `MULTICA_TASK_CONFIG_ROOT` | 作業専用の Multica CLI 設定ルート | 参考情報 |
| `MULTICA_TASK_WORKSPACES_ROOT` | デーモンが管理する作業用ワークスペースのルート | 参考情報 |
| `MULTICA_AGENT_NAME` | 割り当てられたエージェントの表示名 | 参考情報 |
| `MULTICA_DAEMON_PORT` | `multica repo checkout` など作業専用コマンドが使うローカルデーモンのヘルス/API ポート | 参考情報 |
| `MULTICA_TASK_SLOT` | デーモン全体の同時実行プール内のスロット。GPU などスロット番号付きリソースに使用可能 | 参考情報 |
| `MULTICA_PORT_BASE` | この実行に予約されたポートブロックの先頭。同時に動く他の実行とは重なりません。worktree モードでのみ設定されます | **統合契約** |
| `MULTICA_PORT_COUNT` | `MULTICA_PORT_BASE` から連続して確保されるポート数 | **統合契約** |
| `TMPDIR` | 実行中の作業専用の一時ディレクトリ。クロスプラットフォームツール向けに `TMP` と `TEMP` でも提供 | 参考情報 |

`MULTICA_TOKEN` を使ったリクエストの作成者はサーバーが決定し、タスクへのコメントなどの書き込みは、割り当てられたエージェントと実行中の作業に帰属します。認証情報の完全な紐付け、権限、帰属、最長 24 時間の有効期間、クリーンアップについては、[エージェント実行用の一時トークン](/auth-tokens#エージェント実行用の一時トークン)を参照してください。

<Callout type="warning">
これらの値はランタイムプロセスの実際の環境に存在します。ランタイムが起動する子プロセスは、`MULTICA_TOKEN` を含むすべての値をデフォルトで継承します。子プロセスに認証情報を渡すべきでない場合は、明示的に削除してください。存在しないプロセス分離を前提にしてはいけません。逆に、独自に子プロセス環境をフィルタするツールでは、変数の明示的な許可が必要な場合があります。たとえば Codex の shell ツールは、名前に `TOKEN`、`KEY`、`SECRET` を含む変数を除外するため、デーモンは必要な作業変数を許可する管理対象の shell ポリシーを設定します。トークンはプロセス環境内だけに保持し、prompt、ログ、リポジトリファイル、永続設定には書き込まないでください。子プロセスは親の作業と同じ ID と権限を共有し、独立した新しいスコープ ID は受け取りません。
</Callout>

### プロファイルの作成

カスタムランタイムプロファイルを作成・変更・削除できるのは、ワークスペースの owner と admin だけです。

1. **ランタイム**を開き、対象のコマンドがインストール済みのコンピュータに移動します。
2. **カスタムランタイムを追加**をクリックします。
3. コマンドが実際に互換のあるプロトコルファミリーを選びます。
4. 名前、コマンド、固定引数を入力して保存します。

プロファイルはワークスペース内で共有されます。接続済みの各コンピュータが自分でこのコマンドを探し、`PATH` 上で解決できたコンピュータだけが対応するランタイムを登録します。プロファイルを作成してもコマンドはインストールされず、他のメンバーのツールログインが代行されることもありません。

ここに入力するのは実行ファイルと引数であり、shell スクリプトではありません。通常の引数、引用符、バックスラッシュによるエスケープは使えますが、パイプ、リダイレクト、`&&`、`;`、バッククォート、環境変数の展開は使えません。これらの挙動が必要な場合は wrapper script にまとめ、そのスクリプトをコマンドとして指定してください。

Desktop が起動したデーモンが、ターミナルでは実行できるコマンドを見つけられない場合は、現在のコンピュータに絶対パスを設定できます。

```bash
multica runtime profile set-path <profile-id> --path /absolute/path/to/command
```

パスの上書きを解除するには:

```bash
multica runtime profile unset-path <profile-id>
```

プロファイルの変更は、それ以降に取得される実行にのみ影響します。プロファイルを削除する前に、対応するランタイムにまだ紐づいているアクティブなエージェントを先に処理してください。あるコンピュータ上のランタイムインスタンスだけを削除してもプロファイルは消えず、実行中のデーモンが再登録します。

## ターンのチェックポイント、巻き戻し、ライフサイクルスクリプト

以下は **worktree** モードのプロジェクトリソースに適用されます。このモードでは、各実行は作業コピーを編集せず、自分のリポジトリのブランチとして成果を届けます。

### ターンのチェックポイント

すべての実行は、ブランチをどこまで進めたかを `refs/multica/turn/<run>` に記録します。記録は 2 つを保持します。その実行が届けたコミットと、その時点でブランチが運んでいた作業ディレクトリです。途中で失敗した実行も記録を残します — 戻したくなるのは、まさにその実行です。

チェックポイントは削除して構いません。ふつうの ref であり、ブランチがなくなれば自動的に整理されます。削除しても Multica は壊れず、その実行が巻き戻しを提供しなくなるだけです。

### ターンへの巻き戻し

チェックポイントを持つ完了済みの実行には **このターンに戻す** が表示されます。実行すると、会話のブランチはその実行が残した位置に戻り、それ以降の実行とメッセージが削除されます。

作業コピー、インデックス、スタッシュには一切手を加えません。動くのはブランチのポインタだけなので、そのブランチをチェックアウトしている場合は、あとで `git status` に差分が出ます。どうするかはあなたが決めます。

次の 2 つは強行せず、理由を示して拒否されます。

- **ブランチがそのチェックポイントから外れている。** 実行のあとに誰かが rebase、reset、または強制移動しています。巻き戻すと Multica のものではない作業を捨てることになるため、何も変更しません。
- **その会話ですでに巻き戻しが進行中。** 1 つのブランチで巻き戻しが競合するのが、作業を失うケースです。

巻き戻しはリポジトリを所有するマシンで実行されるため、そのデーモンがオンラインで、対応するバージョンである必要があります。そうでない場合、この操作は表示されません。

### ライフサイクルスクリプト

worktree はチェックアウトであり、チェックアウトは通常そのままでは使えません。worktree モードのローカルディレクトリリソースには、最大 3 つのコマンドを設定できます。

| スクリプト | 実行タイミング | 失敗したとき |
| --- | --- | --- |
| セットアップ | worktree 作成後、エージェント開始前 | 出力を理由として実行が失敗します |
| 実行 | セットアップの後、エージェントと並行して起動し、実行終了時に停止します | プレビューが失敗として記録され、実行は続行します |
| アーカイブ | ブランチを届ける前 | ログに記録され、配信は続行します |

いずれもシェル行ではなくコマンドです。最初の語がプログラム、残りが引数になります。シェルを介さないため、`;` や `&&` を含む値は 2 つ目のコマンドではなくただの引数です。パイプライン、変数、条件分岐が必要なら、スクリプトファイルを書いてここで指定してください。

セットアップとアーカイブは 5 分で打ち切られます。実行は設計上長時間動き続け、実行終了時にプロセスグループごと停止されます。3 つとも出力全体は実行の `logs/` ディレクトリに保存されます。

### 実行プレビュー

リソースに実行スクリプトが設定されていると、デーモンはセットアップの後にそれを起動し、`127.0.0.1` の `MULTICA_PORT_BASE` を最大 90 秒間プローブします。応答があると、その実行に**プレビュー**が付きます。実行の行にチップが表示され、詳細パネルにアプリの場所が表示されます。

固定ポートではなく `MULTICA_PORT_BASE` にバインドしてください。ポートを固定した開発サーバーはプレビューを得られず、次の並行実行と衝突します。

プレビューへの到達方法はデーモンによって異なります。

- **リレー。** サーバーがデーモンの既存接続を通じてリクエストをあなたのマシンへ中継します。リンクはスコープ付きで期限があり、取り消せます。マシンのネットワークインターフェースで待ち受けることはなく、受信ポートも開きません。リンクを取り消すと次のリクエストから配信が止まります。
- **ローカル。** デーモンが古くてリレーできない場合、またはデプロイで `MULTICA_PREVIEW_RELAY=off` が設定されている場合、アドレスは `http://127.0.0.1:<port>` となり、実行したマシン上でのみ意味を持ちます。デスクトップアプリはこれを開けますが、Web アプリは機能しないリンクを渡す代わりにローカルであることを表示します。

プレビューは実行とともに終了します。プロセスグループは停止され、開いたままのリンクは「終了しました」と応答します。WebSocket はリレーされないため、リレー経由のプレビューではホットリロードは動作しません。ページを再読み込みしてください。

### ポート

同じマシンで 2 つの実行が同じ開発サーバーを起動しようとするのは、並行実行で最初に壊れる点です。そこで各実行には専用のポートブロックが割り当てられます。`MULTICA_PORT_BASE` がブロックの先頭ポート、`MULTICA_PORT_COUNT` がその個数です。固定ポートではなくこの範囲内でバインドすれば、同時実行が互いに干渉しません。

ブロックは実行開始前に検査され、すでに使われていればずらされます。範囲はデーモンの環境変数 `MULTICA_DAEMON_TASK_PORT_BASE`（既定 21000）と `MULTICA_DAEMON_TASK_PORT_COUNT`（既定 10）で変更できます。

## CLI authentication

Claude Code と Codex のランタイムでは、ランタイムページからデーモン側マシンのサインインを開始できます。認証 URL を開いてワンタイムコードを入力し、CLI が完了するまでダイアログを開いたままにしてください。プロバイダートークンはそのマシンの CLI 設定にだけ保存され、Multica には機密でない認証状態と時刻だけが保存されます。

認証はマシン全体に適用されます。1 つのデーモンが複数のワークスペースを担当している場合、接続または切断はその CLI を使うすべてのワークスペースに影響します。その他のプロバイダーはホストのターミナルで認証してください。

## ランタイムがオフラインのときの確認手順

次の順に確認します。

1. `multica daemon status` を実行し、デーモンが起動していることを確認する。
2. `multica daemon logs -f` を実行し、ログイン、ネットワーク、ツール検出のエラーを確認する。
3. 同じ実行環境で `command -v <ツールコマンド>` を実行し、デーモンがコマンドを見つけられることを確認する。
4. Multica の**ランタイム**ページを開き、対象のコンピュータと対応する AI コーディングツールがオンラインと表示されているか確認する。
5. ツールのインストール直後、パスの変更直後、プロファイルの更新直後は `multica daemon restart` を実行する。

それでも解決しない場合は[トラブルシューティング](/troubleshooting)を参照してください。
