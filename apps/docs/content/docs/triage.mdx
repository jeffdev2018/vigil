Not everything that wants to become an issue should become one. A webhook that
fires on every deploy, a support group where anyone can type `/issue`, an agent
that files what it finds, a forwarded email — each of these can put work in
front of your team without anyone deciding it belongs there.

Triage is the queue that holds that material. An item in the queue is **not an
issue**: it consumes no issue number, appears in no list, no rollup and no
duplicate check. Accepting it is the only thing that creates the issue.

## The queue

**Triage** in the sidebar shows the pending items, newest first, each with the
source it came from and the content that arrived. From there you accept an item
(it becomes an issue through the ordinary funnel — duplicate guard, quota,
events, agent assignment) or dismiss it.

Repeats collapse: a source that sends the same title twice while the first is
still pending increments a counter on the existing item instead of adding a
second one.

## What you can do with an item

Accepting is not the only outcome, and the tabs above the queue (Pending,
Snoozed, Accepted, Dismissed, Merged) are where the resolved ones stay
readable.

- **Accept** creates the issue. **Accept as…** sets who it goes to, which
  project it lands in and at what priority, instead of inheriting whatever the
  origin autopilot would have given it. An empty choice keeps the inheritance.
- **Merge into…** folds the item into an issue that already tracks the work.
  No second issue is created: the item becomes `merged` and the target gets a
  system comment naming what was folded in.
- **Snooze** parks the item until a time you pick (an hour, this evening,
  tomorrow, next Monday, or a date of your own — at most 30 days out). A
  snoozed item is still `pending`: a snooze hides work, it never resolves it.
  It leaves the Pending tab, is counted separately in the queue's stats, and
  comes back on its own when its time passes.
- **Dismiss** takes a reason. It is optional, and it is what the Dismissed tab
  and the auto-classifier read afterwards, so it is worth typing.
- **Reopen** sends a dismissed item back to pending, whoever dismissed it — a
  human, a rule, or the classifier.

Selecting several pending items with their checkboxes accepts or dismisses
them together, with one shared reason for a batch dismiss. A batch answers with
one outcome per item, so the summary names what did *not* go through.

### Agent verdicts

An agent may suggest a verdict on a pending item and nothing more: the item
stays pending, its state is unchanged, and the suggestion shows up as
"Agent suggests: Accept/Dismiss" with the agent's reason. Deciding stays
human-only — every state transition endpoint refuses an agent actor, and the
verdict endpoint refuses a human one.

From the CLI:

```bash
multica triage list --pending
multica triage list --state dismissed --include-snoozed --output json
multica triage verdict <item-id> --accept --reason "matches last week's outage"
```

`multica triage verdict` requires exactly one of `--accept` or `--dismiss`.

### Keyboard

The queue is a list you walk without the mouse. `J` / `K` (or Up / Down) move
through the rows, `Enter` opens the focused one, `Esc` closes the detail. On the
open item: `A` accepts, `X` dismisses, `S` opens the snooze menu, `M` opens the
merge picker, and `R` reopens a dismissed one. None of them fires while you are
typing in a field or while a menu is open, and all of them are rebindable in
**Settings → Keyboard shortcuts**.

## Sources

A **source** is one place inbound material comes from. Every source is
independent, so you gate the noisy one without touching the others.

| Source | One per | Arrives when |
| --- | --- | --- |
| Autopilot webhook | Autopilot trigger | An external system posts to the trigger's webhook URL |
| Autopilot schedule | Autopilot | A cron trigger fires |
| Channel | Installed channel | Someone types `/issue` in Slack, Telegram, Lark, DingTalk or WeCom |
| Agent create | Agent | An agent files an issue on its own initiative |
| Quick create | Workspace | Natural-language capture creates an issue |
| Meeting | Meeting | A recorded meeting's summary yields an action item |
| Email | Workspace | A message is forwarded to the workspace's intake endpoint |

The same autopilot is two sources: its webhook and its schedule are gated
separately, because an unattended cron and a signed webhook are not the same
level of trust.

A source appears the first time it delivers anything. You do not create sources
by hand.

## Modes

Each source has one of three modes. **Direct** is the default everywhere except
email.

- **Direct** — the issue is created immediately, exactly as if triage were not
  there. Channels also record a shadow item so the source shows real volume in
  the queue's stats before you decide whether to gate it.
- **Gate** — nothing is created. The material waits in the queue. A gated
  channel tells the sender their report is waiting for review; a gated agent or
  quick create answers the API with `202` and the queue entry instead of the
  issue.
- **Blocked** — the material is refused and the refusal is recorded, so a
  blocked source is auditable rather than invisible.

<Callout type="warn">
Blocked is a refusal, not a pause: nothing is queued for later. Use gate when
you want to read what arrives.
</Callout>

The **Sources** button in the queue header lists every source with what it put
in the queue — items still pending, seen in the last 24 hours, dropped in the
last 24 hours — next to the settings that produced those numbers. A source
dropping deliveries is where you raise its cap.

Three more settings live on each source:

- **Auto-accept** — resolve the source's items into issues without a human. It
  goes through the ordinary accept path, so the issue funnel, the events and
  the quota are unchanged. Off by default.
- **Cap per hour** — an anti-flood ceiling. Past the cap, further items are
  recorded as `rate_limited` drops instead of burying the queue. `0` means no
  cap.
- **Retention (days)** — how long an unresolved item survives; see below.

## Email intake

**Settings → Workspace → Email intake** mints one endpoint per workspace:

```
POST /api/triage/inbound/email/{token}
```

The token in the path is the whole credential — no session, no workspace
header. It is shown once, when you create or rotate it: the server stores only
its digest, so a lost token is rotated, never recovered. Rotating revokes the
previous token immediately.

The body is a small JSON object:

```json
{
  "from": "reporter@example.com",
  "subject": "Checkout returns 500 on Safari",
  "text": "Since this morning, paying with Apple Pay fails.",
  "html": "<p>Since this morning…</p>",
  "message_id": "<abc@example.com>"
}
```

`from` is required, along with a `subject` or a `text`. The subject becomes the
item's title (the first line of the text stands in when there is no subject),
and the text becomes its body.

This is the common denominator of the JSON inbound webhooks the email providers
post, so a forwarding rule needs a field mapping rather than a parser:

| Multica | Mailgun | Postmark | SendGrid |
| --- | --- | --- | --- |
| `from` | `sender` | `From` | `from` |
| `subject` | `subject` | `Subject` | `subject` |
| `text` | `body-plain` | `TextBody` | `text` |
| `html` | `body-html` | `HtmlBody` | `html` |
| `message_id` | `Message-Id` | `MessageID` | from `headers` |

Email intake is created **gated**, and deliberately has no direct mode: a
forwarded message is the least authenticated material in the product, so it
always waits for a human.

## Rules

A workspace rule can resolve an item the moment it is captured, before anyone
sees it. Rules attach to the `webhook.received` point and read the item's
source kind and name, its title, body and payload, the collapse count, and the
time of day. The first rule whose condition holds applies its action —
**dismiss**, or **accept** with an optional priority and assignee.

Rules live in **Settings → Workspace → Business rules**, and **Create a rule**
in an item's detail opens the same editor prefilled with that item's source and
a keyword from its title — a rule is usually recognized in the queue, looking at
the delivery that made the case. An accept action can route to a member or to
an agent. An item no rule matches stays pending.

## Auto-classification

Every accept and dismiss is a decision the queue can learn from. With
auto-classification on (**Settings → Workspace → Triage auto-classification**,
off by default), an item whose nearest past decisions agree above the
confidence threshold is classified without a click. It needs a minimum number
of human decisions to exist first, and a dismissed item can always be reopened.

Suggestions are shown either way; only their automatic application is gated
behind the setting.

An automatic decision is recorded as the system's, not as a person's: the item
shows "Auto-accepted by the queue" with the confidence that justified it,
rather than the name of someone who never clicked. The issue an auto-accept
creates still needs a creator, and that is the source's creator.

## Retention

An item nobody resolves is **expired** after its source's retention window (14
days by default). Expiring frees the title so the same report can be captured
again, and the row is kept rather than deleted: resolved and expired items are
what auto-classification learns from.
