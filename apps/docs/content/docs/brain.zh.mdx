Brain 是工作区共享的一组简短笔记：你做过的决定及原因、没人写下来的约定、关于代码库的确凿事实、谁负责什么。

它里面的一切都会交给每一次智能体运行。这正是它的意义——已经知道你的部署流程的智能体，不必再去重新摸索，也不必下周再被告知一遍。

## 先捕获，后整理

杀死一个知识库的是摩擦。如果每次想记下一件事，都要先想好标题、标签，还要决定放进哪条已有笔记，那么人只会做一次，然后再也不做。

所以 Brain 分成两半：

- **收集箱**用一个动作接住任何值得留下的东西：一行文字、一个链接、一张截图、一段语音备忘、一个文件、一条 todo。不需要标题，不需要标签，不需要判断。
- **笔记**是整理过的那一半，也是运行唯一会收到的那一半。

一条捕获会一直留在收集箱里，直到有人把它变成笔记、合并进已经覆盖这个主题的笔记，或者丢弃它。没有任何东西会在谁背后被擅自整理；智能体捕获的东西，在有人认定它该进笔记之前，不会到达其他运行。

一条错误的捕获代价是一次点击。一条错误的笔记，会被之后每一次运行读到。

## 什么该写进来

一条笔记值得留在这里的标准是：到下一次运行时，它依然为真，而且依然有用。

好的笔记：

- "部署走发布 tag：在 `main` 上推 `v0.x.x`，`release.yml` 会发布二进制和 Homebrew tap。"
- "迁移在事务外执行，这样 `CREATE INDEX CONCURRENTLY` 才能工作。"
- "守护进程通过 6432 端口的 pgbouncer 连 Postgres，不是 5432。"

不是笔记的：

- 某次运行做了什么。那是运行的产出。
- 下周就不再成立的东西：分支名、正在进行的 PR 编号、"构建是红的"。
- 仓库里已经有的东西——第二份副本一定会和第一份逐渐分叉。
- 密钥、token、凭据。

一条笔记只讲一件事。标题里写事实（`Deploys go through the release tag`），而不是话题（`Deploys`）——标题是所有人在列表里扫过的东西，也是智能体决定要不要打开这条笔记前读的东西。

收集箱的标准刻意放松。把你还没想清楚的东西捕获进来，判断留到整理的时候做。

## 在应用中使用

在侧边栏打开 **Brain**。它有两个标签页：**收集箱**（角标显示还有多少条待整理）和**笔记**。

### 收集箱

输入框在收集箱顶部：输入，回车。同一个框还能接住 todo、你附加或拖进页面的文件，以及就地录制的语音备忘。只有一个链接的消息会被当作链接归类，而不是当作文字。

每条捕获的卡片会显示它是什么（文本、链接、图片、语音备忘、文件、todo）以及它从哪来（网页、桌面端、移动端、CLI、MCP、聊天频道、智能体、API）。从卡片上可以：

- **存为笔记**，新建一条笔记。标题默认取捕获的标题提示，其次取它的第一行；正文默认就是捕获本身——它的链接、文本，然后是文件。
- **合并进...**，把捕获追加到你选的那条笔记末尾，并把它的标签并入该笔记。只要已经有笔记覆盖这个主题，这就是正确的做法。
- **丢弃**不会生成任何东西。丢弃的捕获留在自己的筛选项里，可以**重新打开**。
- **删除**会永久移除这条捕获；除非已有笔记引用，它的文件也会一并删除。丢弃可以撤回，删除不能。

### 笔记

- **搜索**按相关度排序（见下文），同时匹配标题和正文。
- **标签**是筛选用的小标签。它们会被统一转成小写并去重，所以 `Deploy` 和 `deploy` 会归为同一个标签。
- **置顶**一条笔记后，无论它多旧都会发给每一次运行。请节制使用：置顶的笔记会挤占最近笔记的位置。
- 对不再为真的笔记执行**归档**。它会退出运行和默认列表，但仍然可读。
- **删除**是永久性的，只有工作区管理员和笔记本人的作者才能操作。

编辑使用乐观并发控制。如果在你打开笔记期间，别人——或者夜间整理流程——修改了它，保存会被拒绝，系统会要求你重新加载，而不是悄悄覆盖对方的修改。

## 从哪里可以捕获

收集箱是同一个队列，工作区所在的每个地方都能送进来：

| 入口 | 方式 |
| --- | --- |
| 网页与桌面端 | Brain **收集箱**标签页的输入框：文本、todo、附加或拖入的文件、就地录制的语音备忘。 |
| iPhone | 更多里的 **Brain**：输入、分享链接、拍照或从相册选取、附加文件。没有应用内录音——键盘的麦克风键可以语音输入，附加的音频文件仍然会被转录。 |
| CLI | `multica brain capture`（见下文）。 |
| MCP 客户端 | `vigil_brain` 工具的 `capture` 动作。这条路径的捕获来源记为 **MCP**，客户端无法声称成别的来源。 |
| 聊天频道 | 在 Lark、Slack、WeCom、DingTalk 或 Telegram 里发 `/capture <文本或链接>`。机器人只回一行确认，其他什么都不会发生——不会有智能体回复，也不会建任务。 |
| 智能体 | 原生运行时的 `capture_note` 工具，以及任何运行都能用的 `multica brain capture`。 |

不论从哪个入口进来，捕获都会带着来源落进同一个收集箱，所以你能分清哪条是你在地铁上敲的，哪条是智能体干活时顺手放下的。

<Callout>
给智能体的约定很明确：不确定工作区是否想把它作为笔记时就捕获；只有在确定、并且已经搜索过之后，才存为笔记。对"这可能重要"这句话，捕获是诚实的答案。
</Callout>

## 建议

当工作区配置了 assist 层 LLM（`MULTICA_LLM_*`）时，捕获落地后不久会拿到一条建议：标题、标签、一行摘要，以及该怎么处理它——新建笔记、合并进某条具体的已有笔记，或者丢弃，并附上理由。

建议只是卡片上的建议，永远不会自己执行。你也可以随时从卡片上、或用 `multica brain suggest` 重新要一条。没有模型时建议功能只是关闭，收集箱其他部分照常工作。

## 怎么找东西

笔记搜索是排序，不是筛选：结果按相关度从高到低返回，每一条都带一个分数和命中片段。

查询支持一点语法：

- `"带引号的短语"` —— 这些词按这个顺序连在一起。
- `-词` —— 排除包含这个词的笔记。
- `a OR b` —— 任意一个。

两个排序器会被融合。第一个是词面的，作用于标题和正文。第二个是语义的：如果工作区配置了 embedding 模型（`MULTICA_LLM_EMBEDDING_MODEL`），每条笔记还会带一个向量，与查询词匹配的笔记也会按语义排序——搜索界面会把这种排序标为**语义**。笔记仍须与查询共享词语才会出现：即使没有任何笔记能回答查询，最近的向量也总是存在。没有这个模型时，搜索就是纯词面的，界面会说明这一点。

向量在笔记保存和编辑时写入。每 10 分钟一次的后台流程会追上最多 200 条向量缺失、过期或来自另一个模型的笔记——故障或换模型之后，让搜索重新完整的正是这个流程，不需要手工重新导入。

## 语音备忘

在网页或桌面端录制的语音备忘——以及从任何地方附加的音频文件——只要服务端配置了语音识别提供方（`MULTICA_STT_BASE_URL`、`MULTICA_STT_API_KEY`、`MULTICA_STT_MODEL`，以及可选的 `MULTICA_STT_LANGUAGE` 提示），就会被转录。卡片会显示**正在转录...**，转录结果随后成为这条捕获的文本，于是它可被搜索，也能像其他捕获一样整理。音频本身仍然作为附件保留。

没有配置提供方时，录音照样会被捕获，也照样能播放；缺的只是转录，卡片会写明。

## 运行会收到什么

每次运行都会拿到所有置顶笔记，加上最近更新的另外 20 条，写入它的工作目录：

```
.multica/knowledge/README.md        索引：标题、标签、id、文件名
.multica/knowledge/<slug>-<id8>.md  单条笔记
```

运行的简报只指向这个目录，而不是把笔记内嵌进去，所以即使 Brain 很大，占用提示词的也只是几行，而不是全部内容。总量上限是 200 KB；如果有笔记因此被省略，索引会写明省略了多少条。

捕获**不在**运行会收到的内容里。它们是某个人还没整理的想法；运行读了它们再去行动，等于依据还没有人为之背书的东西行动。

## 智能体也会写入

智能体通过 CLI 保存它们学到的东西，内置的 `multica-workspace-brain` skill 会告诉它们什么时候该保存。

```bash
# 要找某样东西：按相关度排序，最匹配的在最前
multica brain search "release tag" --output json
multica brain show <note-id>

# 只是浏览，不是搜索
multica brain list --tag deploy

multica brain save \
  --title "Deploys go through the release tag" \
  --tags deploy,release \
  --content "Push v0.x.x on main; release.yml publishes the binaries."

# 更长的正文从文件读（用 - 从标准输入读）
multica brain save --title "Scheduler leasing model" --tags backend --content-file ./note.md

# 更新已有笔记，而不是再建一条
multica brain save --id <note-id> --content-file ./note.md

multica brain archive <note-id>
```

以及收集箱：

```bash
multica brain capture "the daemon reaches Postgres through pgbouncer on 6432"
multica brain capture --url https://example.com/locking --title-hint "Locking article"
echo "a longer thought" | multica brain capture
multica brain capture --file ./whiteboard.png

multica brain inbox                            # 还待整理的，按时间倒序
multica brain inbox --status all --limit 50
multica brain suggest <capture-id>

multica brain organize <capture-id> --as note --title "..." --tags deploy
multica brain organize <capture-id> --as merge --note <note-id>
multica brain organize <capture-id> --as discard
multica brain reopen <capture-id>
multica brain delete <capture-id> --yes
```

从运行里保存的笔记会归属于保存它的那个智能体，并链接回那次运行，所以一条让人意外的笔记，离写下它的东西只有一次点击。捕获也是一样：卡片会写明是哪个智能体、哪次运行。

<Callout>
这个 skill 会告诉智能体：保存前先搜索 Brain，更新已有的对应笔记，而不是添加一条几乎重复的笔记。知识库的衰败，没有什么比重复更快。
</Callout>

## 夜间整理

每天一次，Brain 确实发生过变化的工作区会经历一轮整理。它会读完全部内容，并执行一套计划：

- 把几乎重复的笔记**合并**进已经覆盖它们的那一条；
- 给标题没有讲出事实的笔记**改标题**；
- 重新**打标签**，让同一个主题在各处带同样的标签；
- **归档**那些已经不再为真、被取代，或者本来就不属于持久知识的笔记。

合并会保留历史：源笔记会被归档，并带上指向合并目标的指针，而不是被删除，所以一次错误的合并是可以恢复的。这个流程从不重写笔记正文，也从不编造事实。

整理需要一个 assist 层 LLM（`MULTICA_LLM_*`）。没有配置时它什么也不做，Brain 的其余功能照常工作。这个流程也从不碰收集箱——整理捕获是人的判断。
