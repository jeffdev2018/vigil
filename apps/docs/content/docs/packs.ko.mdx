**팩**은 회사의 한 기능을 위해 준비된 워크스페이스 구성입니다. 헬프데스크 팩을 설치하면 `Ticket` 작업 항목 유형, 티켓이 실제로 머무는 상태, 데스크가 분류에 쓰는 라벨, "요청 팀" 속성, 대기열 저장 뷰, 데스크의 규칙을 적은 규범 섹션, 트리아지 에이전트, 오래된 티켓을 정리하는 오토파일럿이 한 번의 쓰기, 하나의 트랜잭션으로 들어옵니다.

팩은 [워크스페이스 이전 번들](/workspaces)에 manifest를 얹은 것입니다. 미리보기도, 충돌 전략도, 리포트도 같습니다. 팩이 더하는 것은 정체성입니다 —— 팩이 만든 모든 행이 그 팩의 id와 버전으로 기록되므로 팩은 제자리에서 **업그레이드**할 수 있고 **제거**할 수도 있습니다.

## 사람 팀이 먼저입니다

모든 팩은 **에이전트가 하나도 없어도** 동작합니다. 유형, 속성, 뷰, 규칙은 두 사람짜리 데스크가 첫날부터 쓰는 것들이고, 팩의 지표는 사람만으로도 움직일 수 있습니다. 에이전트는 동료로 도착합니다: 일시 정지, 런타임 미연결, `trust_mode: propose`, 비밀값 없음. 원할 때 연결하면 되고, 연결하지 않아도 됩니다.

팩은 어떤 자격 증명도 담지 않으며, 파일에 무엇이 적혀 있든 설치가 이를 강제합니다.

- **오토파일럿과 그 트리거는 비활성 상태로 들어옵니다.** 무언가를 설치했다는 이유로 실행되는 일은 없습니다.
- **비즈니스 규칙은 초안으로 들어옵니다.** 사람이 하나씩 활성화합니다.
- **에이전트는 환경 변수 키 없이**, 런타임 없이 들어옵니다.
- **트리아지 소스는 토큰 없이 들어옵니다.**

## 카탈로그

Multica에는 팩 10개가 기본 포함되어 있고 3개의 물결로 나뉩니다. 첫 물결은 이메일로 굴러가는 회사의 출발점이고, 세 번째 물결은 백오피스입니다.

| 팩 | 도메인 | 물결 | 무엇을 세팅하는가 | 지표 |
|---|---|---|---|---|
| `helpdesk-it` | helpdesk | 1 | 동료가 올린 티켓을 트리아지해 1 영업일 안에 답변. 에이전트가 초안을 쓰고 사람이 결정 | 첫 응답까지의 시간 |
| `ops` | ops | 1 | 반복 runbook, 장애, 벤더 후속, 변경 요청을 한곳에. 제때 해야 하는 단계가 보이게 | 기한 내 완료한 runbook 단계 |
| `customer-support` | support | 2 | 외부 티켓마다 SLA 등급, 환불과 에스컬레이션은 사람 승인을 기다리고, 에이전트는 답변을 초안만 쓰고 보내지 않음 | SLA 기준 첫 응답까지의 시간 |
| `sales` | sales | 2 | 리드와 딜마다 단계, 아무도 빠지지 않는 후속 주기, 제안서 초안 작성자, 할인에는 승인 | 리드에서 첫 검증 통화까지 |
| `marketing` | marketing | 2 | 캠페인은 프로젝트, 콘텐츠는 채널과 발행일이 붙은 이슈, 작성자와 팩트체커, 사람 승인 없이는 발행하지 않음 | 주당 발행 건수 |
| `leadership` | leadership | 2 | 의사결정을 담당자와 되돌릴 수 있는지 판단과 함께 작업 항목으로 기록, 주간 브리핑, 고르지 않고 선택지를 준비하는 분석가 | 근거를 적고 닫은 의사결정 비율 |
| `research` | research | 2 | 질문을 작업 항목으로, 출처를 Brain에, 확신도를 명시. 리서처가 초안을 쓰고 리뷰어가 출처를 검증 | 출처를 인용한 종합으로 답한 질문 비율 |
| `hr` | hr | 3 | 채용 단계는 속성, 온보딩은 날짜가 있는 단계들의 프로젝트, 휴가와 계약 요청은 티켓, 기밀 규칙 | 첫 출근일 전에 끝낸 온보딩 단계 |
| `finance` | finance | 3 | 청구서, 경비, 마감 작업을 작업 항목으로. 승인은 사람이 하고 기준선 위에서는 2차 서명, 대조를 돕는 어시스턴트 | N 영업일 안에 끝낸 마감 |
| `legal` | legal | 3 | 계약 검토에 상대방과 위험 등급, 조항 라이브러리를 Brain에, 모든 검토는 사람이 승인, 이탈 조항을 짚는 리더 | 검토 소요 기간 |

모든 팩은 **지표를 하나만** 선언합니다. 그 기능이 작동하는지 말해 주는 숫자입니다. 이름, 정의, 워크스페이스 어디에서 읽는지에 대한 힌트로 되어 있고 대시보드가 아닙니다. 설치 전에 읽어 보세요. 지표가 관심사가 아닌 팩은 필요하지 않은 팩입니다.

## 팩에 담긴 것

| 그룹 | 종류 |
|---|---|
| 작업의 형태 | 작업 항목 상태와 유형, 라벨, 커스텀 속성, 저장 뷰 |
| 규칙 | 상태 전이 규칙, 비즈니스 규칙, 담당 규칙, 규범 섹션 |
| 에이전트 | 권한 프로필, 스킬, 에이전트 |
| 콘텐츠 | 프로젝트, 목표, 오토파일럿, 트리아지 소스, 조직, Brain 노트, 예시 이슈 |

행은 **이름으로** 매칭됩니다 —— 에이전트, 라벨, 뷰, 상태 key. 그래서 업그레이드가 가능합니다. 다음 버전의 같은 이름은 같은 행입니다.

## 설치

**설정 → 팩**에 카탈로그와 이미 설치된 것이 나옵니다. 설치는 `owner`와 `admin`의 작업이고, 그 뒤의 엔드포인트는 사람만 받습니다. 에이전트가 시도하면 `403`입니다. 팩은 이후 모든 실행이 묶이는 유형, 규칙, 규범을 바꿔 쓰기 때문입니다.

**먼저 미리보기.** 미리보기는 충돌(팩의 이름 중 하나를 워크스페이스가 이미 쓰고 있는 것), 팩 자체의 검증 문제, 사용될 전략, 그리고 설치가 거부될 경우 그 이유를 알려 줍니다.

| 전략 | 무엇을 하는가 | 언제 기본값인가 |
|---|---|---|
| `skip` | 워크스페이스의 행은 그대로 두고 나머지를 설치 | 첫 설치 —— 팩은 이미 있는 것을 덮어쓰지 않습니다 |
| `merge` | 워크스페이스의 행을 팩의 버전으로 업데이트 | 업그레이드 —— 팩 자신의 행이 새 버전을 따라갑니다 |
| `rename` | 내 행 옆에 비어 있는 이름으로 팩의 행을 설치 | 자동으로 선택되지 않습니다. 필요하면 지정하세요 |

설치는 **리포트**로 답합니다: 종류별 생성 수와 병합 수, 건너뛴 행과 그 이유, 경고, 그리고 손댄 모든 행의 목록. 그 목록이 원장이며 `multica pack items <install-id>`가 종류, 이름, `created`인지 `merged`인지와 함께 다시 출력합니다.

<Callout title="팩은 스스로 아무것도 실행하지 않습니다">
설치 후에는 아무것도 돌지 않습니다. 오토파일럿은 비활성, 규칙은 초안, 에이전트에는 런타임이 없습니다. 첫 주는 당신의 것입니다 —— 실제 일을 뷰에 넣고, 그다음에 에이전트 하나를 켜세요.
</Callout>

## 업그레이드

업그레이드는 같은 팩 id의 더 새로운 버전을 설치하는 것입니다. 카탈로그가 이를 표시하고, 기본 전략이 `merge`가 되어 팩 자신의 행이 새 버전을 따라갑니다. 이전 설치의 행은 이어집니다 —— 예전 버전이 만들고 이번에 건너뛴 행도 여전히 팩의 것입니다.

이미 설치된 버전을 다시 설치하면 `409`로 거부됩니다. `--force`가 다시 적용합니다(이전은 `skip` 아래에서 멱등이므로 안전합니다). **더 낮은** 버전은 항상 거부됩니다. 팩은 다운그레이드하지 않습니다.

## 제거

제거는 팩이 설치한 **구성**을 없애고 **콘텐츠**를 남깁니다.

- **없어지는 것**: 담당 규칙, 저장 뷰, 상태 전이 규칙, 비즈니스 규칙. 에이전트와 오토파일럿은 보관 처리됩니다. 라벨, 속성, 상태, 작업 항목 유형은 아직 이슈가 쓰고 있지 않으면 삭제되거나 보관됩니다. 쓰고 있으면 남고, 리포트에 몇 건인지 적힙니다.
- **남는 것**: 프로젝트, 목표, Brain 노트, 이슈, 그리고 팩이 기존 행에 `merged`한 모든 것. 그것들은 애초에 팩만의 것이 아니었습니다.

리포트는 남은 모든 행을 이유와 함께 적으므로 "팩은 없어졌는데 유형은 아직 있다"는 놀라움이 아니라 답입니다.

## 사전 조건

팩은 있었으면 하는 것을 선언합니다 —— [네이티브 런타임](/native-runtime), 연결된 런타임, 연동, 채널 —— 그리고 미리보기가 각각을 `met`, `missing`, `unknown`으로 표시합니다. 강제되는 것은 없습니다. 런타임 사전 조건이 빠진 팩도 설치되고, 그 에이전트는 아직 돌릴 곳이 없을 뿐입니다. 선택적인 사전 조건은 그렇게 표시됩니다.

## 내 팩 쓰기, 또는 내보내기

팩은 YAML 파일 하나이므로 팀은 자기 팩을 코드 옆에 둘 수 있습니다.

```bash
multica pack download helpdesk-it --out helpdesk-it.pack.yaml   # 실제 팩에서 시작
multica pack preview-file my-desk.pack.yaml                     # 충돌, 문제, 전략
multica pack install-file my-desk.pack.yaml --strategy skip
```

반대 방향으로, `pack export`는 다듬어 놓은 워크스페이스를 당신이 제공한 manifest와 함께 팩 파일로 만듭니다.

```bash
multica pack export --id my-desk --version 1.0.0 --title "Our desk" \
  --summary "How we run support here." --domain support \
  --metric-label "First-response delay" \
  --metric-description "Median time to the first reply actually sent." \
  --include-notes --out my-desk.pack.yaml
```

서버는 앱에서든 CLI(`multica pack preview-file` / `install-file`)에서든 32 MB까지의 팩 파일을 받습니다. 연결된 컴퓨터에서 발견된 스킬은 내보내기에 포함되지 않으며(그 기기의 것이므로), `--include-skills=false`를 주면 스킬을 전부 제외합니다. 내보내기도 자격 증명을 담지 않습니다 —— 에이전트의 환경 변수 키는 남겨지고, 트리거는 비활성으로 돌아오며, 트리아지 소스는 토큰 없이 돌아옵니다.

## 팩 포맷

정식 규약은 내장 팩 옆에 리포지터리로 함께 배포되는 `FORMAT.md`입니다. 직접 쓸 때 실제로 중요한 규칙입니다.

- **본문은 영어.** 제품은 자기 UI를 번역하지, 당신의 팩을 번역하지 않습니다. 제목, 지시, 규범, 예시 이슈는 팀이 읽는 것입니다.
- **이름이 곧 정체성.** 버전을 넘겨 안정적으로 유지하세요. 그렇지 않으면 업그레이드가 첫 행을 업데이트하는 대신 두 번째 행을 만듭니다.
- **에이전트**: `trust_mode: propose`, `effect_mode: preview`, `runtime_mode: native`, `env_keys` 없음, 그리고 모든 에이전트가 그 팩의 절차 스킬을 나열할 것.
- **상태**: 기본 7개를 넘어 기능이 정말 필요한 것만 추가하고, 커스텀 상태마다 그중 하나를 `category`로 줄 것.
- **예시 이슈는 스스로 예시라고 말할 것** — 제목이나 첫 줄에서.
- **모든 팩은 `metric`을 선언**하고, 변경마다 semver `version`을 올릴 것.

### 알려진 한계

- 상태 전이 규칙은 상태 **카테고리**를 기준으로 합니다. 작업 항목 유형이나 속성이 아니므로, 승인 게이트는 그 카테고리 사이를 움직이는 모든 이슈에 걸립니다.
- 속성을 필수로 지정할 수 없고, 두 단일 선택 속성을 서로 묶을 수도 없습니다. 그런 규칙은 규범 섹션과 비즈니스 규칙에 쓰세요.
- `metric`은 이름 하나와 설명 하나입니다. 두 번째 숫자는 설명이나 힌트에 넣습니다.
- 스케줄 트리거는 cron 식과 고정된 타임존을 받습니다.
- 예시 이슈에는 마감일도 담당자도 없습니다.

## 팩으로 워크스페이스 시작하기

워크스페이스를 만들 때 `pack_id`를 받습니다. 새 워크스페이스는 첫 작업으로 그 카탈로그 팩에서 세팅됩니다. 실패해도 워크스페이스는 그대로 남고 롤백 대신 오류를 알려 줍니다 —— 막은 원인을 고친 뒤에 팩을 다시 설치하세요.

## CLI 사용

```bash
multica pack list --domain helpdesk
multica pack show helpdesk-it
multica pack preview helpdesk-it --strategy skip
multica pack install helpdesk-it
multica pack installed
multica pack items <install-id>
multica pack uninstall <install-id>
```

| 명령 | 내용 |
|---|---|
| `pack list [--domain]` | 카탈로그와 이 워크스페이스의 설치 상태, 업그레이드 여부 |
| `pack show <id>` | manifest, 지표, 상태가 붙은 사전 조건, 종류별 내용 |
| `pack preview <id> [--strategy]` | 충돌, 문제, 전략, 설치가 거부되는 이유 |
| `pack install <id> [--strategy] [--force]` | 적용하고 리포트를 출력 |
| `pack installed` | 설치 원장 |
| `pack items <install-id>` | 한 번의 설치가 만들거나 병합한 모든 행 |
| `pack uninstall <install-id>` | 무엇이 없어지고 무엇이 남았으며 왜 그런지 |
| `pack download <id> [--out]` | 팩 파일 자체 |
| `pack preview-file` / `pack install-file <file>` | 내 팩에 대한 같은 두 단계 |
| `pack export --id --version --title --summary …` | 이 워크스페이스의 구성을 팩 파일로 |

모든 명령이 `--output json`을 받습니다. 공통 플래그는 [CLI 사용](/cli)을 참고하세요.

## API

- `GET /api/packs` → 카탈로그: manifest, 개수, `installed_version`, `upgrade_available`, 상태가 붙은 사전 조건. `GET /api/packs/{id}`는 종류별 내용을 더하고, `GET /api/packs/{id}/download`는 파일을 반환합니다.
- `POST /api/packs/{id}/preview | install {strategy?, force?}` —— owner/admin, 그리고 사람만.
- `POST /api/packs/preview | install` —— 같은 것을 multipart로. 팩 파일은 `file` 필드에 넣습니다.
- `GET /api/packs/installed`, `GET /api/packs/installed/{id}` → 원장과 한 설치의 행들.
- `POST /api/packs/installed/{id}/uninstall` → 설치 기록과 제거／보존 리포트.
- `POST /api/packs/export {manifest, include_issues, include_notes, include_skills}` → `pack.yaml`.
- 감사 액션 `pack.installed`과 `pack.uninstalled`, 그리고 열려 있는 페이지를 최신으로 유지하는 `pack:changed` 이벤트.
