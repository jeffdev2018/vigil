Projects organize work that takes multiple [issues](/issues) to finish — a product launch, a migration, or a feature delivered in stages.

Work that a single issue can describe does not need a project. Projects fit a group of work that shares a goal, needs its progress tracked together, or needs shared repositories and working directories.

## Parts of a project

| Part | Purpose |
|---|---|
| **Name, icon, and description** | Goal, scope, and long-lived requirements; the description enters the execution context of agents working inside the project. |
| **Status** | `planned`, `in_progress`, `paused`, `completed`, or `cancelled`. |
| **Priority** | `urgent`, `high`, `medium`, `low`, or `none`. |
| **Lead** | A member or an agent — who coordinates the project. |
| **Start and target dates** | The project's planned time range. |
| **Issues and progress** | The work in the project and how much of it is finished. |
| **Resources** | Linked GitHub repositories or local directories on specific computers. |

## Projects and issues

A project can contain any number of issues; an issue belongs to at most one project. Create issues directly inside the project, or pick or change the project from the issue's properties.

Project progress is computed automatically from linked issues:

```text
progress = issues in done or cancelled ÷ all issues in the project
```

`cancelled` means that work has been closed out of the project's scope, so it counts toward progress. Project status and issue status are independent: finishing every issue does not automatically set the project to `completed`, and changing the project's status does not bulk-change its issues.

## Project description and execution context

When an agent runs an issue inside a project, the project's name and description are added to that run's context. The description is the place for information every related issue needs: the goal, technical boundaries, delivery conventions. Requirements that apply to only one issue belong in that issue.

## Add resources

Project resources tell agents which code and working directories to use:

- **GitHub repositories**: provide a repo the runtime can check out, with an optional ref.
- **Local directories**: let the runtime on a specific computer work in an existing directory, whose contents the agent modifies directly.

See [Project resources](/project-resources) for how to choose and for the safety boundaries.

## Blast radius: autonomy by path

A project can layer per-path autonomy rules on top of an agent's own permissions. Each rule matches a path pattern (`.gitignore`-style: `**` spans directories, `*` and `?` stay inside one segment) to one of three levels:

| Level | What it does |
|---|---|
| **Autonomous** | The action passes automatically — no approval gate opens for paths at this level. |
| **Read-only** | Any write to a matching path is refused before a gate is even opened. |
| **Dual approval** | The action needs two different humans to approve, not one — a first approval opens a second Decision Card addressed to someone else. |

A path with no matching rule falls back to the agent's own permissions, exactly as if blast radius were not configured.

When several rules could match the same path, the most specific one wins — literal characters count toward specificity, wildcards do not. Two rules of equal specificity and different levels cannot both exist: creating one that conflicts this way is refused, naming the rule it collides with, rather than leaving the outcome to insertion order.

Blast radius rules are visible to every project member and editable only by workspace `owner`s and `admin`s, from the project detail page. A preview box resolves any path against the current rules, so you can check which level would apply before an agent acts on it.

<Callout type="info">
Blast radius decides the outcome of the approval gates that ask before a git push, a sensitive MCP tool call, or a spend — it settles the path before a gate would otherwise open, rather than adding a new kind of gate. A dual-approval decision reaches you the same way any other approval request does: as a Decision Card on the issue.
</Callout>

## Epic mode

A project can carry an **epic**: four artifacts written in order, each one approved before the next opens.

`PRD` → `Technical plan` → `Wireframe` → `Tickets`

Each step is written by an agent run or typed by hand, reviewed as a draft, and then approved. **Only an approved step unlocks the next one**, and the panel names the approval a locked step is waiting on rather than only greying it out.

Editing or regenerating a step that was already approved creates a new draft and sends every later step back to superseded — they were approved against a premise that changed. The panel says how many steps that reopened.

The `Tickets` step is the only one with consequences. Approving it enables **Apply**, which creates one child issue per ticket under the project's epic issue and links them with blocking dependencies where the breakdown declares them. Apply previews what it would create first, and applying again only creates the tickets that are not issues yet — it never duplicates one.

<Callout>A wireframe is text: an ASCII layout or a Mermaid diagram. Images are not part of this step.</Callout>

## Project lead

The lead can be a member or an agent, and marks who coordinates the project. It is not a permission setting: it does not auto-assign the project's issues, and making an agent the lead does not automatically run it. Starting a run still takes an issue assignment, an @mention, or an automation trigger.

## Pin to the sidebar

A pinned project appears in your sidebar. Pinning is a personal preference and does not affect other members.

## Create, edit, and delete

Any workspace member can create and edit projects; only `owner` and `admin` can delete them.

<Callout type="warning">
Deleting a project does not delete its issues: they detach and stay in the workspace. The project's description, status, and resources are permanently deleted.
</Callout>
