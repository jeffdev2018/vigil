**パック**は、会社の 1 つの機能のために用意されたワークスペース構成です。ヘルプデスクのパックをインストールすると、`Ticket` 作業アイテムタイプ、チケットが実際に置かれるステータス、デスクが仕分けに使うラベル、「依頼元チーム」プロパティ、キューの保存ビュー、デスクの規則を書いた規範のセクション、トリアージのエージェント、放置チケットを掃除する自動化が、1 回の書き込み・1 つのトランザクションで入ります。

パックは[ワークスペース移行バンドル](/workspaces)に manifest を載せたものです。プレビューも、衝突時の戦略も、レポートも同じです。パックが加えるのは同一性です —— 作成された行はすべてパックの id とバージョンに紐付いて記録されるので、パックはその場で**更新**でき、**アンインストール**もできます。

## まず人のチームが動く

どのパックも**エージェントが 1 つもなくても**使えます。タイプ、プロパティ、ビュー、ルールは 2 人のデスクが初日から使うものですし、パックの指標は人だけでも動かせます。エージェントは同僚として到着します。一時停止、ランタイム未紐付け、`trust_mode: propose`、シークレットなしです。つなぎたくなったらつなげばよく、つながなくても構いません。

パックが認証情報を運ぶことはなく、ファイルに何が書かれていてもインストールがそれを強制します。

- **自動化とそのトリガーは無効の状態で入ります。** 何かをインストールしたせいで動き出すことはありません。
- **ビジネスルールは下書きとして入ります。** 1 つずつ人が有効にします。
- **エージェントは環境変数キーなし**、ランタイムなしで入ります。
- **トリアージのソースはトークンなしで入ります。**

## カタログ

Multica には 10 個のパックが同梱され、3 つの段階に分かれています。段階 1 はメールで回している会社の出発点、段階 3 はバックオフィスです。

| パック | ドメイン | 段階 | 何を用意するか | 指標 |
|---|---|---|---|---|
| `helpdesk-it` | helpdesk | 1 | 同僚から来るチケットをトリアージし、1 営業日以内に回答。エージェントが下書きし、人が決める | 初回応答までの時間 |
| `ops` | ops | 1 | 定期的な runbook、障害、ベンダー対応、変更申請を 1 か所に。期限どおりに実施すべき手順が見える | 期限内に終わった runbook 手順 |
| `customer-support` | support | 2 | 外部チケットすべてに SLA ティア。返金とエスカレーションは人の承認を待ち、エージェントは返信を下書きするだけで送信しない | SLA に対する初回応答までの時間 |
| `sales` | sales | 2 | リードと商談すべてにステージ。フォローの周期から誰も漏れず、提案を書くエージェント、値引きには承認 | リードから最初の見極め通話まで |
| `marketing` | marketing | 2 | キャンペーンはプロジェクト、コンテンツはチャネルと公開日を持つ課題。ライターとファクトチェッカーがいて、人の承認なしには公開しない | 週あたりの公開本数 |
| `leadership` | leadership | 2 | 意思決定を担当者と可逆性の判断つきで作業アイテムとして記録。週次ブリーフィング、選ばずに選択肢を用意するアナリスト | 根拠が書かれて完了した意思決定の割合 |
| `research` | research | 2 | 問いを作業アイテムに、出典を Brain に、確信度を明示。リサーチャーが下書きし、レビュアーが出典を検証 | 出典つき統合で答えられた問いの割合 |
| `hr` | hr | 3 | 採用ステージはプロパティ、オンボーディングは日付つき手順のプロジェクト、休暇と契約の申請はチケット、機密のルール | 初日までに終わったオンボーディング手順 |
| `finance` | finance | 3 | 請求書・経費・締め作業を作業アイテムに。承認は人が与え、閾値を超えたら 2 人目の署名、照合を手伝うアシスタント | N 営業日以内に終わった月次締め |
| `legal` | legal | 3 | 契約レビューに相手方とリスクレベル、条項ライブラリを Brain に、レビューは毎回人が承認、逸脱を指摘するリーダー | レビューの所要日数 |

どのパックも**指標を 1 つだけ**宣言します。その機能が機能しているかを語る数字です。ラベル、定義、そしてワークスペースのどこで読むかのヒントで構成され、ダッシュボードではありません。インストールする前に読んでください。指標に興味が持てないパックは、必要のないパックです。

## パックの中身

| グループ | 種類 |
|---|---|
| 作業の形 | 作業アイテムのステータスとタイプ、ラベル、カスタムプロパティ、保存ビュー |
| ルール | ステータス遷移ルール、ビジネスルール、オーナーシップルール、規範のセクション |
| エージェント | 権限プロファイル、スキル、エージェント |
| コンテンツ | プロジェクト、ゴール、自動化、トリアージのソース、組織、Brain のノート、サンプル課題 |

行は**名前で**照合されます —— エージェント、ラベル、ビュー、ステータスの key。だから更新が成り立ちます。後のバージョンの同じ名前は同じ行です。

## インストール

**設定 → パック**にカタログと、すでに入っているものが並びます。インストールは `owner` と `admin` の操作で、その裏側のエンドポイントは人しか受け付けません。エージェントが試すと `403` になります。パックは、その後すべての実行が縛られるタイプ・ルール・規範を書き換えるからです。

**まずプレビュー。** プレビューは衝突（パックの名前をすでに持っているもの）、パック自体の検証エラー、使われる戦略、そしてインストールが拒否される場合はその理由を挙げます。

| 戦略 | 何をするか | いつ既定になるか |
|---|---|---|
| `skip` | ワークスペースの行はそのままにし、残りを入れる | 初回インストール —— パックはすでにあるものを上書きしません |
| `merge` | ワークスペースの行をパックの版で更新する | 更新時 —— パック自身の行が新しいバージョンに追随します |
| `rename` | あなたの行の隣に、空いている名前でパックの行を入れる | 自動では選ばれません。必要なら指定します |

インストールは**レポート**を返します。種類ごとの作成数と統合数、スキップした行とその理由、警告、そして触れた行の一覧です。その一覧が台帳で、`multica pack items <install-id>` が種類・名前・`created` か `merged` かとともに読み返せます。

<Callout title="パックはそれ自体では何も動かしません">
インストール後、何も走りません。自動化は無効、ルールは下書き、エージェントにランタイムはありません。最初の 1 週間はあなたのものです。本物の仕事をビューに入れて、それからエージェントを 1 つ有効にしてください。
</Callout>

## 更新

更新とは、同じパック id の新しいバージョンをインストールすることです。カタログがそれを示し、既定の戦略が `merge` になってパック自身の行が新しいバージョンに追随します。前回のインストールの行は引き継がれます —— 古いバージョンが作り、今回スキップした行も、やはりパックのものです。

すでに入っているバージョンの再インストールは `409` で拒否されます。`--force` で再適用できます（移行は `skip` のもとで冪等なので安全です）。**より低い**バージョンは常に拒否されます。パックはダウングレードしません。

## アンインストール

アンインストールはパックが入れた**構成**を取り除き、**コンテンツ**を残します。

- **取り除かれるもの**: オーナーシップルール、保存ビュー、ステータス遷移ルール、ビジネスルール。エージェントと自動化はアーカイブされます。ラベル、プロパティ、ステータス、作業アイテムタイプは、まだ課題が使っている場合を除いて削除またはアーカイブされます。使われている場合は残され、レポートに件数が書かれます。
- **残るもの**: プロジェクト、ゴール、Brain のノート、課題、そしてパックが既存の行に `merged` したものすべて。それらは元からパックだけのものではありません。

レポートは残った行を理由とともに挙げるので、「パックは消えたのにタイプがまだある」は驚きではなく答えです。

## 前提条件

パックは欲しいものを宣言します —— [ネイティブランタイム](/native-runtime)、接続済みのランタイム、連携、チャネル —— そしてプレビューがそれぞれを `met`、`missing`、`unknown` と示します。何も強制されません。ランタイムの前提条件が満たされていないパックもインストールでき、そのエージェントはまだ走る場所がないだけです。任意の前提条件はそう明示されます。

## 自分のパックを使う、あるいは書き出す

パックは 1 つの YAML ファイルなので、チームは自分のパックをコードの隣に置けます。

```bash
multica pack download helpdesk-it --out helpdesk-it.pack.yaml   # 実物から始める
multica pack preview-file my-desk.pack.yaml                     # 衝突、問題、戦略
multica pack install-file my-desk.pack.yaml --strategy skip
```

逆向きに、`pack export` は作り込んだワークスペースを、あなたが与える manifest つきのパックファイルにします。

```bash
multica pack export --id my-desk --version 1.0.0 --title "Our desk" \
  --summary "How we run support here." --domain support \
  --metric-label "First-response delay" \
  --metric-description "Median time to the first reply actually sent." \
  --include-notes --out my-desk.pack.yaml
```

サーバーが受け付けるパックファイルは、アプリからでも CLI（`multica pack preview-file` / `install-file`）からでも 32 MB までです。接続したコンピューター上で見つかったスキルはエクスポートに含まれません（そのマシンのものだからです）。`--include-skills=false` を付けるとスキルをすべて除外します。エクスポートも認証情報を運びません —— エージェントの環境変数キーは置いていかれ、トリガーは無効で戻り、トリアージのソースはトークンなしで戻ります。

## パックのフォーマット

正式な取り決めは `FORMAT.md` で、内蔵パックの隣にリポジトリ同梱で配られます。自分で書くときに効いてくる規則は次のとおりです。

- **本文は英語。** プロダクトが翻訳するのは自身の UI で、あなたのパックではありません。タイトル、指示、規範、サンプル課題はチームが読むものです。
- **名前が同一性。** バージョンをまたいで安定させてください。さもないと更新は 1 行目を更新せず、2 行目を作ります。
- **エージェント**: `trust_mode: propose`、`effect_mode: preview`、`runtime_mode: native`、`env_keys` なし、そして各エージェントがパックの手順スキルを挙げること。
- **ステータス**: 7 つの組み込みステータスを超えて機能が本当に必要とするものだけを足し、カスタムステータスにはそのうちの 1 つを `category` として与えること。
- **サンプル課題は自分がサンプルだと述べる**こと。タイトルか 1 行目で。
- **どのパックも `metric` を宣言**し、変更ごとに semver の `version` を上げること。

### 既知の限界

- ステータス遷移ルールはステータスの**カテゴリ**を条件にします。作業アイテムタイプやプロパティは条件にできないので、承認ゲートはそのカテゴリ間を移動するすべての課題にかかります。
- プロパティを必須にはできず、2 つの単一選択プロパティを互いに束縛することもできません。そうした規則は規範のセクションとビジネスルールに書いてください。
- `metric` はラベル 1 つと説明 1 つです。2 つ目の数字は説明かヒントに入れます。
- スケジュールのトリガーは cron 式と固定のタイムゾーンを取ります。
- サンプル課題は期限も担当者も持ちません。

## パックからワークスペースを始める

ワークスペースの作成は `pack_id` を受け取ります。新しいワークスペースは最初の処理としてそのカタログのパックから立ち上がります。失敗してもワークスペースは残り、ロールバックせずにエラーを報告します —— 原因を直してからパックをもう一度インストールしてください。

## CLI を使う

```bash
multica pack list --domain helpdesk
multica pack show helpdesk-it
multica pack preview helpdesk-it --strategy skip
multica pack install helpdesk-it
multica pack installed
multica pack items <install-id>
multica pack uninstall <install-id>
```

| コマンド | 内容 |
|---|---|
| `pack list [--domain]` | カタログと、このワークスペースのインストール状態・更新の有無 |
| `pack show <id>` | manifest、指標、状態つきの前提条件、種類ごとの中身 |
| `pack preview <id> [--strategy]` | 衝突、問題、戦略、インストールが拒否される理由 |
| `pack install <id> [--strategy] [--force]` | 適用してレポートを表示 |
| `pack installed` | インストール台帳 |
| `pack items <install-id>` | 1 回のインストールが作成・統合した行のすべて |
| `pack uninstall <install-id>` | 何が取り除かれ、何が残り、それはなぜか |
| `pack download <id> [--out]` | パックファイルそのもの |
| `pack preview-file` / `pack install-file <file>` | 自分のパックに対する同じ 2 ステップ |
| `pack export --id --version --title --summary …` | このワークスペースの構成をパックファイルとして書き出す |

すべてのコマンドが `--output json` を取ります。共通の引数は [CLI](/cli) を参照してください。

## API

- `GET /api/packs` → カタログ: manifest、件数、`installed_version`、`upgrade_available`、状態つきの前提条件。`GET /api/packs/{id}` は種類ごとの中身を加え、`GET /api/packs/{id}/download` はファイルを返します。
- `POST /api/packs/{id}/preview | install {strategy?, force?}` —— owner/admin、かつ人のみ。
- `POST /api/packs/preview | install` —— 同じものを multipart で。パックファイルは `file` フィールドに入れます。
- `GET /api/packs/installed`、`GET /api/packs/installed/{id}` → 台帳と、1 回のインストールの行。
- `POST /api/packs/installed/{id}/uninstall` → インストール記録と、取り除かれた／残ったレポート。
- `POST /api/packs/export {manifest, include_issues, include_notes, include_skills}` → `pack.yaml`。
- 監査アクション `pack.installed` と `pack.uninstalled`。`pack:changed` イベントが開いているページを最新に保ちます。
