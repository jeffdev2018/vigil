すべてがタスクになるべきわけではありません。デプロイのたびに発火する Webhook、誰でも `/issue` と打てるサポートグループ、見つけたものを報告するエージェント、転送されたメール — これらはいずれも、誰かがそれを「タスクにすべきだ」と判断する前に、チームの前に作業を置いてしまう可能性があります。

Triage は、そうした素材を保持するキューです。キュー内の項目は**タスクではありません**: タスク番号を消費せず、どの一覧にもロールアップにも重複チェックにも現れません。承認して初めてタスクが作られます。

## キュー

サイドバーの **Triage** には保留中の項目が新しい順に表示され、それぞれにどの送信元から来たか、届いた内容が示されます。そこから項目を承認する（通常のファネル — 重複防止、クォータ、イベント、エージェントへの割り当て — を経てタスクになります）か、却下することができます。

繰り返しはまとめられます: 最初の項目がまだ保留中のうちに、同じ送信元が同じタイトルを再送すると、2 件目を追加するのではなく、既存の項目のカウンターが増えます。

## 項目に対してできること

承認だけが結末ではありません。キュー上部のタブ（保留中、スヌーズ中、承認済み、却下済み、統合済み）には、処理済みの項目が引き続き閲覧できる形で残ります。

- **承認**するとタスクが作られます。**次として承認…** では、元のオートパイロットが与えるはずだった内容を継承する代わりに、誰に割り当てるか、どのプロジェクトに入れるか、どの優先度にするかを指定できます。空欄のままにすれば継承されます。
- **課題に統合…** は、その項目を、すでに同じ作業を追跡しているタスクに畳み込みます。新しいタスクは作られません: 項目は `merged` になり、統合先には何が統合されたかを記したシステムコメントが付きます。
- **スヌーズ**は、選んだ時刻（1 時間後、今夜、明日、来週の月曜、または任意の日付 — 最長 30 日先まで）まで項目を一時的に脇に置きます。スヌーズ中の項目も状態は依然として `pending` です: スヌーズは作業を隠すだけで、解決するわけではありません。保留中タブからは外れ、キューの統計では別枠でカウントされ、指定した時刻が来ると自動的に戻ってきます。
- **却下**には理由を添えられます。任意入力ですが、却下済みタブと自動分類がその後参照するものなので、書いておく価値があります。
- **再開**は、却下済みの項目を保留中に戻します。誰が却下したか（人、ルール、分類器のいずれであっても）は問いません。

チェックボックスで複数の保留中項目を選択すると、まとめて承認・却下できます。一括却下の場合、理由は 1 つを全体で共有します。バッチ処理は項目ごとに 1 つの結果を返すため、サマリーには*通らなかった*ものだけが名指しされます。

### エージェントの判定

エージェントは保留中の項目に判定を提案できますが、それ以上のことはできません: 項目は保留中のままで状態は変わらず、提案は「エージェントの提案: 承認 / 却下」としてエージェントの理由とともに表示されます。決定は人間だけが行います — 状態遷移のエンドポイントはすべてエージェントによる操作を拒否し、判定のエンドポイントは逆に人間による操作を拒否します。

CLI から:

```bash
multica triage list --pending
multica triage list --state dismissed --include-snoozed --output json
multica triage verdict <item-id> --accept --reason "matches last week's outage"
```

`multica triage verdict` には `--accept` か `--dismiss` のどちらか一方が必須です。

### キーボード操作

このキューはマウスなしで操作できる一覧です。`J` / `K`（または上下キー）で行を移動し、`Enter` でフォーカス中の項目を開き、`Esc` で詳細を閉じます。項目を開いた状態では: `A` で承認、`X` で却下、`S` でスヌーズメニューを開く、`M` で統合先の選択を開く、`R` で却下済みの項目を再開します。いずれも、フィールドに入力中やメニューが開いているときは発動せず、すべて **設定 → キーボードショートカット** で再割り当てできます。

## 送信元

**送信元**とは、流入する素材が来る場所のことです。送信元はそれぞれ独立しているため、うるさい送信元だけを保留モードにして、他には手を触れずに済みます。

| 送信元 | 単位 | 届くタイミング |
| --- | --- | --- |
| オートパイロットの Webhook | オートパイロットのトリガー | 外部システムがトリガーの Webhook URL に POST したとき |
| オートパイロットのスケジュール | オートパイロット | cron トリガーが発火したとき |
| チャンネル | インストール済みのチャンネル | Slack、Telegram、Lark、DingTalk、WeCom のいずれかで誰かが `/issue` と入力したとき |
| エージェントによる作成 | エージェント | エージェントが自らの判断でタスクを作成したとき |
| クイック作成 | ワークスペース | 自然言語での入力からタスクが作られたとき |
| 会議 | 会議 | 録音された会議の要約からアクションアイテムが生まれたとき |
| メール | ワークスペース | ワークスペースの受信エンドポイントにメッセージが転送されたとき |

同じオートパイロットでも、送信元としては 2 つに分かれます: Webhook とスケジュールは別々に保留モードを設定できます。無人で動く cron と署名付きの Webhook では、信頼度のレベルが異なるからです。

送信元は、最初に何かを届けたときに初めて現れます。手動で送信元を作ることはありません。

## モード

各送信元は 3 つのモードのいずれかを持ちます。メール以外はすべて **直接** がデフォルトです。

- **直接** — Triage が存在しないかのように、タスクが即座に作成されます。チャンネルの場合はシャドー項目も記録されるため、保留モードにするかどうかを決める前に、送信元の実際の流入量をキューの統計で確認できます。
- **保留** — 何も作成されません。素材はキューで待機します。保留中のチャンネルは、送信者に「あなたの報告はレビュー待ちです」と伝えます。保留中のエージェントやクイック作成では、API はタスクの代わりに `202` とキューのエントリを返します。
- **ブロック済み** — 素材は拒否され、その拒否が記録されます。そのため、ブロックされた送信元は見えなくなるのではなく、監査可能な状態になります。

<Callout type="warn">
ブロックは拒否であって一時停止ではありません: 後で処理するためにキューに残ることはありません。届いた内容を読みたい場合は保留を使ってください。
</Callout>

キューのヘッダーにある**送信元**ボタンを開くと、それぞれの送信元がキューに何を投入したか — 保留中の件数、過去 24 時間で受信した件数、過去 24 時間で破棄した件数 — が、その数字を生んだ設定と並べて一覧表示されます。配信を落としている送信元があれば、そこがまさに上限を引き上げるべき場所です。

各送信元には、さらに 3 つの設定があります:

- **自動承認** — 人を介さずに、その送信元の項目をタスクとして解決します。通常の承認経路を通るため、タスクのファネル、イベント、クォータは変わりません。デフォルトはオフです。
- **1 時間あたりの上限** — 洪水対策の上限です。上限を超えた項目は、キューを埋め尽くす代わりに `rate_limited` として記録され、破棄されます。`0` は上限なしを意味します。
- **保持期間（日数）** — 未解決の項目がどれだけ生き残るか。詳しくは後述します。

## メールでの受信

**設定 → ワークスペース → メール受信**で、ワークスペースごとに 1 つのエンドポイントが発行されます:

```
POST /api/triage/inbound/email/{token}
```

パス中のトークンがそのまま認証情報のすべてです — セッションもワークスペースヘッダーも不要です。作成時またはローテーション時に一度だけ表示されます: サーバーはそのダイジェストしか保存しないため、トークンを失くした場合はローテーションするしかなく、復元はできません。ローテーションすると、以前のトークンは即座に無効になります。

ボディは小さな JSON オブジェクトです:

```json
{
  "from": "reporter@example.com",
  "subject": "Checkout returns 500 on Safari",
  "text": "Since this morning, paying with Apple Pay fails.",
  "html": "<p>Since this morning…</p>",
  "message_id": "<abc@example.com>"
}
```

`from` は必須で、`subject` か `text` のどちらかも必要です。件名（subject）が項目のタイトルになります（件名がない場合は本文の最初の行が代わりに使われます）。本文（text）はそのまま項目の本文になります。

これは、各メールプロバイダーが送ってくる JSON 形式の受信 Webhook の最大公約数です。そのため、転送ルールに必要なのはパーサーではなく、フィールドのマッピングだけです:

| Multica | Mailgun | Postmark | SendGrid |
| --- | --- | --- | --- |
| `from` | `sender` | `From` | `from` |
| `subject` | `subject` | `Subject` | `subject` |
| `text` | `body-plain` | `TextBody` | `text` |
| `html` | `body-html` | `HtmlBody` | `html` |
| `message_id` | `Message-Id` | `MessageID` | `headers` から |

メール受信は最初から**保留**として作成され、意図的に直接モードを持ちません: 転送されたメッセージは、このプロダクト内で最も認証されていない素材であるため、常に人による確認を待ちます。

## ルール

ワークスペースのルールは、誰かがそれを目にする前、取り込まれた瞬間に項目を解決できます。ルールは `webhook.received` の時点に紐付き、項目の送信元の種類と名前、タイトル、本文、ペイロード、まとめられた件数、時刻を参照します。条件が成立する最初のルールが、そのアクション — **却下**、または優先度と担当者を任意で指定した**承認** — を適用します。

ルールは **設定 → ワークスペース → ビジネスルール** にあります。項目の詳細にある**ルールを作成**を開くと、同じエディターがその項目の送信元とタイトルからのキーワードをあらかじめ入力した状態で開きます — 通常、ルールはキューの中で、実際にきっかけとなった配信を見ながら見出されます。承認アクションは、メンバーにもエージェントにもルーティングできます。どのルールにも一致しなかった項目は保留のままです。

## 自動分類

承認と却下は、いずれもキューが学習できる判断材料です。自動分類をオンにすると（**設定 → ワークスペース → Triage 自動分類**、デフォルトはオフ）、直近の類似した過去の判断が信頼度のしきい値を超えて一致する項目は、クリックなしで分類されます。それには一定数以上の人間による判断があらかじめ必要で、却下された項目はいつでも再開できます。

提案はどちらの場合でも表示されます。その設定によってゲートされるのは、あくまで自動適用の部分だけです。

自動的な判断は、人ではなくシステムのものとして記録されます: 項目には、実際にはクリックしていない誰かの名前ではなく、「キューによって自動承認されました」という表示と、その根拠となった信頼度が示されます。自動承認によって作られたタスクにも作成者は必要で、それはその送信元の作成者になります。

## 保持期間

誰にも解決されなかった項目は、その送信元の保持期間（デフォルトは 14 日）を過ぎると**期限切れ**になります。期限切れになるとタイトルが解放され、同じ報告を再び取り込めるようになります。行自体は削除されずに残ります: 自動分類が学習するのは、この解決済みおよび期限切れの項目からです。

## 滞留キューのダイジェスト

キューの統計にはすでに、最も古い保留中項目の経過時間が表示されています — ただしそれを見るのは、すでにキューを見ている人、つまりそのリマインダーを一番必要としていない人です。キューが静かに読まれなくなったとき、ワークスペースの他のメンバーには何も知らされません。

実質的に最も古い保留中項目（スヌーズ中のものはカウントしません）の待機時間が 48 時間を超えると、ワークスペースのすべてのオーナーと管理者は、Triage を指し示すインボックス通知を 1 日 1 件受け取ります。そこには保留中の件数と、最も古い項目がどれだけ待っているかが記載され、キューが滞留している間はこれが続きます。通知はワークスペース自身のタイムゾーンで暦日ごとに 1 回送られます — 通常の週末をまたいで残ったキューが、金曜の項目のために月曜の朝に誰かを呼び出すことはありません — そして、キューが追いつけば自動的に止まります。
